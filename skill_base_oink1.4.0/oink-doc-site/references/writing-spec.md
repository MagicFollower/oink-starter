# 写作规范与判据映射

规范全文在 `assets/scaffold/doc/技术文档编写规范.md`（462 行 / 21,153 字节 / MD5 前 10 位 `461b0fe424`，CRLF 行尾）。1.4.0 基线新增一节「OINK 1.4.0 排版增强（可选，不改变任何硬门槛）」，讲 `.wide`/`.expand` 表、`.td-code-command`、cards/steps 变体、PlantUML 不作图判据、以及图表懒渲染的验收口径。`scaffold.py` 会把它拷进新站 `doc/`，那是给站点读者的交付物；**写作子代理要读技能内的这一份**（骨架站里可能还没有或已被手改）。

本文只登记三件事：规范条目与机器判据的对应、分批写作的节奏、以及哪些话不能写进正文。

---

## 一、full 模式的 11 类文体判据

| 规范要求 | 判据代码 | 阈值/口径 |
|----------|----------|-----------|
| 问题驱动叙事 | `NO_PAIN_OPEN` | 首个真实 H2（跳过围栏代码里的 `##`）必须含「为什么」 |
| 新人小结 | `FEW_NEWBIE` | `💡 新人小结` ≥ 3 处 |
| 结构化信息 | `NO_MERMAID` / `FEW_TABLES` | mermaid 围栏 ≥ 1；以 `|` 开头的行数 ÷ 2 ≥ 2 |
| 代码规范 | `NO_CODE` | 带语言标注的 fence ≥ 1（mermaid 不计） |
| 内容完整性 | `SKIP_LANGUAGE` | 命中「限于篇幅 / 此处从略 / 自行查阅 / 待补充 / TODO / 感兴趣请 / 众所周知 / 不言而喻」即报 |
| 图表格式 | `BOX_CHARS` | 正文出现 `┌┐└┘├┤┬┴┼` 任一字符即报（代码块内也扫） |
| 结构模板 | `NO_SUMMARY` | 必须有「要点总结」 |
| 篇幅 | `TOO_SHORT` | 全文 < `--min-lines`（默认 260 行） |
| 排版语言 | `ENGLISH_HEADING` | H2 含 ≥4 连续英文字母且无汉字即报 |
| front matter 描述 | `THIN_DESC` | description < 20 字（结构判据，两种模式都生效） |
| 文章桩 | `STUB_PAGE` | 正文仍含 `OINK-STUB` 标记；full 模式报，skeleton 模式不报 |

## 二、两种模式都生效的 10 类结构判据

`MISSING_INDEX`、`NOT_WRITTEN`、`UNLISTED`、`NO_FRONT_MATTER`、`FM_FIELD`、`THIN_DESC`、`BROKEN_IMAGE`、`SELF_CHECK_LEAK`、`DUP_WEIGHT`、`WEIGHT_GAP`。

10 + 11 = 21，正好是 `audit_content.py` 的可达判据代码总数。`--mode skeleton` 只留 10 类，汇总行会打印 `genre_checks=0`；**不要把骨架模式的绿色当成成品质量结论**。

`BROKEN_IMAGE` 检查正文里所有 `![...](/<path>)`：`/images/a.png` 对应 `<site>/static/images/a.png`。外链图片不检查。

## 三、一篇成品的最低形状

- 首个真实 H2：`## 为什么需要 X？（痛点引入）`，用事故/具体场景开，不用定义开。
- 开头一个 💡 新人小结（具体日常类比），复杂概念处一个，结尾一个，共 ≥ 3。
- ≥ 1 张 mermaid；节点标签、边标签加引号；一图讲一件事。
- ≥ 2 组表格；代码块带语言标注，参数表与示例配套。
- `## 要点总结`，3–5 条。
- 全文 ≥ 260 行；description ≥ 20 字。
- 不写方框字符、不写省略式表达、不把审计报告的代码名/措辞抄进正文（`SELF_CHECK_LEAK`）。

## 四、分批写作

**按分类切批，不按字数平均。** 一批 4–8 篇，同一分类内优先。理由：同一批共享术语、图表与交叉链接，审计失败时原因也集中。

每批给写作子代理五样：

1. 目标文件的绝对路径；
2. 该篇在计划里的条目（title/desc/weight/sources）；
3. 技能内的写作规范绝对路径：`<技能目录>/assets/scaffold/doc/技术文档编写规范.md`；
4. 对应体裁的样章：`<技能目录>/assets/example-docs/00-骨架.md` + `01`~`04` 中对应那一份；
5. 事实来源（用户材料路径/官方链接/可运行命令），没有就明确写「没有来源，只写概念与结构，不写具体数值」。

分派词模板（把尖括号替换成真实值）：

```text
你是 <站点> 的文档作者。只写这一篇：<目标文章绝对路径>。

计划条目：<title / desc / weight / sources 的 JSON 片段>
事实来源：<来源清单>。没有来源的默认值、版本号、限制数值、异常语义一律不写，或写「上游未给出」；禁止按同类系统惯例推定。

必读（先读再写）：
- <技能目录>/assets/scaffold/doc/技术文档编写规范.md
- <技能目录>/assets/example-docs/00-骨架.md
- <技能目录>/assets/example-docs/<对应体裁>.md

硬门槛：首个 H2 以「为什么」开头；≥260 行；≥3 个「💡 新人小结」；≥1 个 mermaid；≥2 组表格；≥1 个带语言标注的代码块；必须有「要点总结」；description ≥20 字。
交付前在本地跑：
  python <技能目录>/scripts/audit_content.py --site <站点> --plan <计划> --mode full --min-lines 260
并贴出 articles=/problems=/by_kind= 三行实测输出。problems 非 0 不得交回。
```

每批交付后立刻跑一次 `audit_content.py --mode full`，绿色才派下一批。最后再跑 `verify_site.py --mode full` 统一验收。

## 五、事实来源纪律

写具体技术事实（默认值、版本号、命令输出、异常类型、限制数值）时：

- 只信用户材料、官方文档/仓库、真实运行输出。
- 上游没写的，写「上游未给出」，不要用「一般来说」「通常」补齐。
- 每批在 `doc/内容来源.md` 追加一行：文章 → 来源 → 用到的具体事实。交付时 `verify_site.py` 会把这份清单标成 MANUAL，需人工核对。
- 同一事实在表格、代码注释、要点总结中必须一致；改一处要全局搜。

## 六、体裁样章

`assets/example-docs/` 共 6 份：

| 文件 | 行数 | 用途 |
|------|------|------|
| `00-骨架.md` | 216 | 必需块的完整清单，含判据代码注释；写新文先拷它 |
| `01-概念机制型.md` | 247 | 「是什么/由哪些对象组成/怎么流转」 |
| `02-操作部署型.md` | 239 | 「装它、起它、验证跑通、失败怎么办」 |
| `03-命令参数参考型.md` | 249 | CLI/HTTP/配置项参考 |
| `04-FAQ排障型.md` | 244 | 按现象组织的排查清单 |
| `99-完整参考全文.md` | 540 | 一篇成品全貌；**内容是 RocketMQ 特定事实，只学结构，不抄事实** |

样章是体裁参考，不是事实来源。写自己的系统时，结构照它，内容必须换成自己的来源。

## 七、常见返工点

| 现象 | 处理 |
|------|------|
| 首段从定义开始 | 改成事故/痛点场景，首个 H2 用「为什么需要」 |
| 全文 260 行但小结只有 2 个 | 在复杂概念首次出现处补一个，结尾补一个 |
| 表格只有表头 | 表格行数按 `|` 行 ÷ 2 计算，至少 2 组完整表 |
| mermaid 括号/引号不配对 | 用浏览器解析台跑真解析，不要只靠肉眼 |
| 代码块没有语言标注 | ```` ```bash ```` / ```` ```yaml ````；裸 fence 不计入 `NO_CODE` |
| 正文出现 `┌─┐` | 改 mermaid；文本箭头只用 `→ ↓ ①` |
| description 写「本文介绍……」不足 20 字 | 改成「这篇解决什么问题」，≥20 字 |
| 把审计报告里的 `NO_MERMAID` 等代码名写进正文 | `SELF_CHECK_LEAK` 会报；用中文描述问题 |
