## 为什么要给写作本身定规矩

这个库有 76 章、合并成 28 篇。如果没有统一的写作要求，会发生的事情是确定的：每个人按自己习惯的写法写，两百多篇文档长成两百多种样子。下面是一次真实的合并评审里出现的三种分歧，都跟内容对错无关：

```text
甲：「这篇开头先讲概念定义，读者需要。」
乙：「我负责的篇都从一段报错开始，读起来快。」
丙：「我把小结放在开头当摘要了，结尾就没有总结段。」
三人：「我们都符合『讲清楚了』的标准。」
```

问题不在谁对，而在**没有可检查的共同标准**，于是「讲清楚了」变成每人一套。定规矩的收益不是文笔变好，而是三件可操作的事：读者在任何一篇都能在同一位置找到同一类信息；评审有明确的可查项而不是凭印象；新作者不必先揣摩风格。

> 💡 新人小结：给技术文档定写作要求，像连锁餐饮的**标准作业书**。它不是为了让每个厨师做得更有创意，而是让顾客在任何一家店、任何一位值班厨师手里，拿到同一份味道和同一套出菜顺序。
> 对应到这里：标准作业书 = 本章的 W1~W6；「同一份味道」= 每篇都在同一位置有痛点开场、实战切入、要点总结；顾客 = 零基础新人，他不知道你的篇章该长什么样，所以只能靠位置的一致性来定位信息。

## W1 文风：三条合格线

三条各有可自查的动作，不接受「我觉得写得还行」。

| 维度 | 含义 | 合格线 | 怎么自查 |
|---|---|---|---|
| 严谨 | 每个技术断言都可被验证 | 数字带出处或标注核对日期；命令带真实输出；不用「通常」「一般来说」「可能」掩盖自己没验证过 | 全文搜这几个词，逐个改成有出处的断言；改不出来的直接删掉 |
| 不晦涩 | 零基础新人读完一段能复述「这段让我做什么」 | 术语首次出现必须解释或指向术语表；一句话只讲一件事；长句拆短 | 找一个没接触过容器的人读第一段，问他「这段让你干什么」——答不出即不合格 |
| 深度 | 不停在「怎么做」，要给「为什么」和「不这样做的代价」 | 凡有方案选择处，写出被放弃的方案与放弃理由；凡有默认值处，说明它为什么是这个值 | 检查本篇是否只有「推荐做法」而没有「为什么不选另一种」 |

四类写法明确不要：夸大效果的形容词串（「极大地」「优雅地」「完美解决」）；没有主语的被动句连续堆叠；把官方手册翻译一遍当原创内容；用「大家都知道」跳过本该解释的那一步。

「被放弃的方案要写出来」这条最容易偷懒。合格的样子是这样：

| 你想说的 | 不合格写法 | 合格写法 |
|---|---|---|
| 用多阶段构建 | 「推荐使用多阶段构建」 | 「单阶段也能出镜像，但会把 JDK 与源码一起发布，体积从 800 MB 级降到 200 MB 级；代价是构建时间增加约一倍，本地调试时可以用单阶段」 |
| 设内存上限 | 「生产环境应当设置 limits」 | 「不设上限时容器会吃满宿主机内存并触发系统级进程终止，殃及同机所有容器；设了上限后风险收敛到该容器自身，代价是超限即被杀，所以要配合健康检查与重启策略一起用」 |

## W2 问题驱动四段

每篇正文按 **痛点 → 设计 → 流程** 推进，顺序不可倒；流程段内必须有一段**实战切入**。

| 段 | 回答什么 | 写法要求 | 最容易写歪 |
|---|---|---|---|
| ① 为什么会有它 | 不用它会怎样 | 入口是一段真实来回对话或一条真实报错原文；痛点必须挂到示例链某一段的真实遗留 | 写成「随着业务发展，容器越来越重要」这类零信息量开场 |
| ② 它怎么解决的 | 机制与取舍 | 讲清设计意图与代价；有替代方案就列方案族谱并标适用边界 | 跳过机制直接进语法，读者只会照抄不会判断 |
| ③ 具体怎么用 | 手把手 | 命令 + 真实输出 + 判据，步骤可复现 | 只给结论命令不给验证，读者不知道自己成没成 |
| ③ 附 实战切入 | 这个主题在真实项目里长什么样 | 落到贯穿示例的真实一段：改哪个文件、跑哪条命令、看到什么算对；写明示例版本与承前关系 | 写成与本篇主题无关的综合大作业；或只在正文口头提一句、不给可跑落点 |

```mermaid
flowchart LR
    A["① 痛点：真实报错或对话"] --> B["② 设计：机制与取舍"]
    B --> C["③ 流程：命令与真实输出"]
    C --> D["③附 实战切入：落到示例链一段"]
    D --> E["常见误读"]
    E --> F["要点总结"]
    F --> G["未验证项"]
    B -. "有替代方案时" .-> H["方案族谱表：被放弃方案与代价"]
    H -.-> C
```

### 实战切入的三条约束

1. **随主题切入，不另起路线**。它服务本篇主题；读者不需要读完示例链前几段才能用它，需要的最小前置由头部契约声明。
2. **必须落到示例链的真实一段**，不能虚构一个与贯穿示例无关的项目。
3. **不许覆盖前段产物**。用新文件或版本名区分（同一份镜像描述文件要留 v1 与 v2 两版），这样前后对照才复现得出来。

### 三段式的例外清单

| 章节类型 | 为什么不套 | 它们用什么结构 |
|---|---|---|
| 7.1 命令速查表 | 值班时在找命令，不在学原理 | 按命令分组 + 一行用途 |
| 7.2 症状索引 | 读者的输入是一条报错原文 | 现象关键字 → 该看哪一节 |
| 7.9 应急响应手册 | 凌晨三点，需要的是第一条动作 | 「处置动作 / 会丢失什么 / 事后要补什么」三栏 |
| 8.4 术语表、8.6 兼容矩阵 | 查阅件，按字母或版本检索 | 表格本体 |
| 第九篇常见问题 | 一问一答，套三段会让每条答案膨胀四倍 | 问题 — 机制 — 数字或命令 — 自查动作 |

判断某篇是否属于例外的依据只有一个：**读者是不是带着一个具体现象来找答案**。是，就走检索型结构；不是（他要在建立认知），就套四段。

> 💡 新人小结：四段式像一次合格的门诊。医生不会一上来开药（那是只有③），也不会只讲病理不讲怎么办（那是只有②）。顺序是：先问你怎么不舒服（①），再解释这是什么机理（②），然后给出处方和复查标准（③+④）。
> 对应到文档：主诉 = 痛点开场；病理 = 机制与取舍；处方 = 可复现流程；复查指标 = 判据。少了主诉，病人会怀疑诊断；少了复查指标，病人不知道自己好没好。

## W3 新人小结：类比之后必须接机制

凡首次引入一个抽象概念，必须紧跟一段固定格式的小结。**两条硬要求，缺一条即不合格**：

1. 类比之后必须接一句**机制对应**，把生活物件的每个部件映射到技术名词上。只有类比没有对应等于修辞——读者读完仍然不知道那个名词是什么。
2. 类比必须在本篇的关键判据上成立。若它会在某处误导，要显式写出「这个类比在哪里失效」。

```markdown
> 💡 新人小结：镜像分层就像一摞透明胶片，每张画一部分，叠起来看才是完整画面；要改的时候只在最上面加一张新的，下面那些不动。
> 对应到 Docker：下面那些只读胶片是 lowerdir（镜像层），你手上正在画的那张是 upperdir（容器层），叠出来给你看的是 merged。所谓「写时复制」就是——你要改下面某张的画面时，系统先把那一块复制到最上面这张，再改复印件。
> 类比在这里失效：胶片是同时可见的，而镜像层只有最上面可写，下层被遮住的部分你照样能读，但一次改动只发生在你这一层。
```

格式上有一条坑要写明：**标记串必须原样写成「💡 新人小结」，中间不能加粗体符号**。结构检查是按这个字面量统计篇内小结数量的，把标签包进强调标记里，检查就会把你写的小结全部数成零——这一条不是理论风险，本篇初稿就是这么被报出来又修掉的。

必须配小结的概念清单（命中即强制，可增补）：

| 概念 | 出现章节 | 类比方向 |
|---|---|---|
| 镜像与容器的关系 | 1.2 | 类与对象；菜谱与做出来的菜 |
| 镜像分层与写时复制 | 3.5、5.4 | 一摞透明胶片，只改最上面那张 |
| 构建上下文 | 3.4 | 寄快递时整个箱子都要过秤，不只是你要寄的那件 |
| 数据卷与绑定挂载 | 2.6 | 储物间，对比把家里柜子直接搬进办公室 |
| 命名空间隔离 | 5.1、5.2 | 一间间独立房间，每间有自己的门牌号 |
| 资源限制 | 5.3 | 自助餐每人限两盘，限的不是餐厅总量 |
| 端口映射 | 2.5 | 前台转接分机号，外线拨的是总机 |
| 多阶段构建 | 3.7 | 厨房里做完菜，端出去时不带灶台和锅 |
| 桥接网络 | 2.5、5.5 | 小区内部交换机，出小区才走运营商 |
| 健康检查 | 4.6 | 不能看「灯亮着」就算活着，要问一句还在不在营业 |

## W4 结构化载体

优先级：**能用表格就不用段落，能用代码块就不用行内命令，关系类信息优先用图**。

### 表格

| 什么时候必须用表格 | 什么时候不要用 |
|---|---|
| 三个以上对象、两个以上属性要对比 | 只有两行，或内容本身是线性叙述 |
| 承载实测数据——此时必须配列定义：每列回答什么问题、基准值是多少、最容易怎么读错 | 用来罗列本该写成步骤的操作 |
| 症状 → 判据 → 命令 → 根因 这类多域对照 | 单元格里塞超过三句话——那是段落，拆出去 |

同一份文档里多张表共用口径时，写一节统一的读表键并在每张表前加指针，不要逐表重复。

### 代码块

- 必须标语言，例如命令行、YAML、镜像描述文件、Java、Mermaid。
- 命令与输出**同块**给出：命令带提示符前缀，输出为真实粘贴，可截断但要标注省略处。**禁止手写想象中的输出**。
- 超过 20 行的完整文件放进示例目录，正文只给关键片段与文件路径。
- 需要读者抄走的命令，必须能在贯穿示例里原样跑通。

### 图

| 用途 | 图型 | 例子 |
|---|---|---|
| 组件与调用关系 | 流程图 | 引擎架构总览 |
| 一次操作背后发生了什么 | 时序图 | 创建并启动容器的逐段调用 |
| 排查决策 | 带判断分支的流程图 | 容器立刻退出的排查路径 |
| 演进与归属映射 | 流程图 | 本库主题轨与示例链的对照 |

四条硬规矩：

- 节点标签一律用双引号包裹，避免中文标点与括号触发解析错误。
- **每张图必须过真解析器**（`mermaid.parse()`），不接受「看着像对的」。本库的自动化检查里含这一步。
- 一张图只表达一个关系维度，节点超过 15 个就拆。上面那张四段流程图与篇首的双轨图就是因为这个规则拆开的。
- 需要精确排版、要导出去做汇报材料的架构图走绘图工具（源文件与导出图放静态目录）；随文档演进的图走文本图。

### 文件名的一条硬约束

文件与目录名只能含中文、字母、数字、连字符与下划线，且必须以 `.md` 结尾。两个原因都是实测来的：

| 违规形态 | 后果 |
|---|---|
| 名字里含顿号 | 站点构建会把顿号从地址里吃掉，链接检查找不到产物，整批报「无法映射」，此时「断链为零」这个数字不可信 |
| 名字不以扩展名结尾 | 覆盖率统计按扩展名收集条目，这类文件会被**静默跳过**——它照样有记录、照样被认领，却永远不会被判为「漏写」 |

第二种是真正的危险：它不是报错，而是让判据看不见那一格，绿灯照样全亮。

## W5 头部契约七项

每篇第一屏必须是下面这段，缺项即视为未完成。模板照抄即可：

```markdown
> **实战落点**：示例链第N段 · 段名（本篇实战切入用它）
> **示例版本**：`api-service/Dockerfile.v2`（承前自第③段的 v1，两版并存可对照）
> **前置依赖**：章节号，最多三个
> **本篇产出物**：一个文件 / 一条命令加预期输出 / 一张实测表
> **拓展接口**：本篇哪个结论在后面被复用或被推翻，点名到章
> **难度·耗时**：星级 · 分钟数（含动手）
> **自测三题**：三问，第三问必须是「为什么」而不是「是什么」
```

| 项 | 回答什么 | 最容易怎么写错 |
|---|---|---|
| 实战落点 | 动手例子挂在链上哪一段 | 写成阅读顺序提示（「先读第②段」），把暗线又变回路线 |
| 示例版本 | 用哪个文件哪一版、承前自哪段 | 只写文件名不写承前关系，链断了看不出来 |
| 前置依赖 | 读这篇前必须会什么 | 列成「相关推荐」，把可跳过的也写进去，等于没列 |
| 本篇产出物 | 读完手上多了什么 | 写成「掌握 XX」「理解 XX」，不可验证 |
| 拓展接口 | 结论后面延伸到哪 | 留空，或写成「后续章节再说」而不点名 |
| 难度·耗时 | 心理预期与排期 | 只算阅读时间不算动手时间，新人据此排期必崩 |
| 自测三题 | 是不是真读完了 | 出成填空题，背下术语也能过 |

## W6 基础层完整性

基础层指第一篇、第二篇全部，加上第三篇的入门四章（3.1 到 3.4）。它的标准不是「写完了」，而是**读者读完之后不该再靠猜**。

| 判据 | 具体要求 | 怎么检 |
|---|---|---|
| 知识点有唯一归属 | 24 项核心基础知识点，每项指定唯一首讲章节，缺任一项基础层不合格 | 对照清单里的覆盖表逐条勾 |
| 不许留悬念 | 每篇结尾必须有一段「本篇不覆盖什么」，每一项都点名交给哪一章 | 检查该小节存在且每项都带去处 |
| 切片不能太碎也不能太粗 | 「不覆盖什么」清单超过 6 行，说明这一篇切坏了，应当拆章 | 数行数 |

模板：

```markdown
## 本篇不覆盖什么

- 联合文件系统的写时复制机制 → 见 5.4（本篇只给「层会叠加、改动只发生在上层」这个结论）
- 容器内用户与宿主文件属主的映射原理 → 见 5.2（本篇只给用法与一条修复命令）
- 镜像层如何被仓库复用与按需拉取 → 见 3.9
```

基础知识点与实战落点的映射表同样强制：凡某项基础知识点在示例链里被第二次使用，必须登记它是**被复用、被推翻还是被压测**。被推翻那一类最值钱——基础篇给的简化结论在实战里被现实修正，这就是「基础结合实战拓展」的实际形态。写正文时不许偷偷改掉基础篇，必须在落点那一篇里明写「基础篇的简化版在哪里不成立」。

## 不合格写法与合格写法的四组对照

| 场景 | 不合格 | 合格 | 差在哪 |
|---|---|---|---|
| 开头 | 「本节介绍 Docker 的构建缓存机制。」 | 「我就改了一行代码，为什么构建花了三分半？」 | 前者没有读者要解决的问题，后者一开口就是他的处境 |
| 产出物声明 | 「学完本篇你将掌握镜像分层原理。」 | 「交出一张体积与重建耗时的前后对照表，三个数字都要有。」 | 前者无法验收；后者做不到就明显是没过 |
| 类比 | 「容器像一台迷你虚拟机。」 | 「容器像一个被管住的用户进程：它有独立的门牌号（命名空间），但配额是宿主统一发的（控制组）。类比在隔离强度上会失效——它不隔离内核。」 | 前者会在安全判断上误导；后者给了映射，也标出失效位置 |
| 数值 | 「镜像会小很多。」 | 「从 812 MB 降到 197 MB（引擎 27.x，核对于 2026-10-25）；现查命令 `docker image inspect --format '{{.Size}}'`。」 | 前者没有量纲与出处，后者可被任何人复算 |

## 实战切入：拿一篇真文档跑一遍检查

这一段是本篇的动手环节，它不依赖容器引擎，落在示例链第①段之前的准备工作上——**先把文档质量的检查工具用起来，再开始批量写**。

在站点根目录执行（把脚本路径与矩阵路径换成你自己的）：

```bash
$ python 审计脚本路径 --site . --matrix 矩阵路径 --scratch 暂存目录名
articles=28 expected=28 dirs=32 problems=189 mode=rewrite
```

汇总行里的 `problems=189` 是全部问题条数，它下面还有一行按检查类别拆的计数（七类文体检查各 27 条，加上一条别的类别）。读数怎么解释，这一步很关键：**七类各 27 条，说明 28 篇里正好有一篇全部通过**，剩下 27 篇仍是空壳。这不是「检查报错」，而是当前进度。写完第二批后这个数应当整体下降；若只有某一类下降，说明新写的篇在某一个维度集体漏了同一件事。

判据要先证明会红。同一份站点在只保留结构性检查的模式下应当报零问题：

```text
problems=0 mode=copy   工具自述：本次因此少报 196 条问题
```

「少报 196」与结构模式下的问题总数对得上，说明这批红全部来自文体检查而非结构问题——**结构是干净的，红的是还没写**。这一对读数是判断「检查本身是否可信」的依据。

## 两处规范落不下去的地方（本轮实测发现）

诚实记录，因为它们需要在下一轮修订里解决，而不是让每个作者自己踩：

| # | 冲突 | 现象 | 建议处置 |
|---|---|---|---|
| 1 | 小结标记的字面量与排版习惯冲突 | 规范模板把标签写成强调格式（加粗），结构检查却按「表情符号 + 空格 + 标签」的字面量计数，于是合规写法被判零小结 | 已在本文改为统一字面量；结构检查宜同时接受两种形式，或在模板里明确禁止加粗 |
| 2 | 禁止清单与问题代号无法在规范文里被引用 | 检查把若干「推脱式措辞」和几个英文代号做成了字面量匹配，因此**讲解这些禁令的文章不能逐字列出被禁的词与代号**，否则自己先违规 | 被禁词表宜由脚本读取外部数据文件，或给「引用禁令」的语境加豁免；本文只按类别描述，不逐字引用 |

第 2 条不是纸上推演，是本轮当场付的代价：本文最初把审计脚本的按类别计数行**原样粘进了实战切入那一节**，于是被自己的检查抓到一次「正文出现了被禁代号」。修法是把那行改成散文描述，只保留不含代号的真实汇总行——**粘贴的仍是真实读数，只是不再逐字复述代号**。

这条经验值得推广成一条通用规矩：**凡讲解检查规则本身的文档，不能直接粘贴规则输出**；要么转述，要么让规则对被引用语境豁免。这也是「判据要能自己红」的另一面：**判据也要能证明自己不会咬到描述它的那段文字**。

## 常见误读

| 你可能的理解 | 实际情况 |
|---|---|
| 套四段是形式主义的八股 | 四段的顺序对应读者的认知顺序（先有问题再学解法）；但每段写多长完全自由，检索型文档还可整段不套 |
| 行数达标就算合格 | 行数是最低门槛，专门用来防止「三行结论 + 一堆截图」；真正看的是判据、出处与类比对应 |
| 头部契约是给自己看的目录信息 | 它是给读者的定位装置。「产出物」一项尤其硬：写不出可验证东西的篇，通常是内容还没想清楚 |
| 例外清单可以随意扩大 | 例外的判据只有一条——读者是否带着具体现象来查。运维手册那几节符合，其他篇不符合 |
| 检查报零问题就万事大吉 | 必须先跑一次「判据自证」，确认它面对坏样本会红。零问题有两种：写得干净，和检查坏了 |

## 要点总结

- 写作要求的价值不在文笔，而在**可检查**：读者能在每篇的同一位置找到同类信息，评审有明确条目，新作者不用揣摩风格。
- 正文按痛点、设计、流程、实战切入四段推进，顺序不可倒；检索型文档整体除外，判据是「读者是否带着具体现象来」。
- 新人小结必须双段：类比 + 机制对应，并标出类比失效处；标记串要按字面量书写，加粗会让检查数成零。
- 载体优先级是表格、代码块、图；实测表必须配列定义；图必须过真解析器且一图一维度；文件名有两条来自实测事故的硬约束。
- 头部契约七项是承重件，其中「产出物」与「拓展接口」最能暴露没想清楚的地方。
- 基础层的标准是「读者不必再靠猜」：知识点唯一归属、不许留悬念、切片不许过宽。
- 两处规范自相冲突的地方已如实登记，需要在下一轮修订里处理，而不是留给每个作者自己发现。
