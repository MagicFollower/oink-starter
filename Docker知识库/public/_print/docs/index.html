为什么要先读这一页

去年有个应届生领到一台新笔记本，第一天做了这件事：他打开一个文档站的目录，从第一篇第一个字开始往下读，读到第四篇时已经是下午四点，然后开始装 MySQL——因为他觉得「后面总会讲到」。晚上他发了条消息：

「文档我读了大半，为什么还是跑不起来我们的服务？」
「你读到讲 volume 那一节了吗？」
「还没有，我在读镜像分层。」
「那你今天缺的其实是第二节里的两条 docker run。」

这条对话暴露的不是他笨，而是文档给了他一条顺序，却没给他在顺序里定位自己的能力。三种读法都会以不同方式失败：

读法 表面理由 实际会发生什么 这个库怎么治
按编号从头读 「系统地学」 在无关章节上花掉当天最清醒的两小时，动手时间永远排在后面 明确不推荐；编号只保证引用稳定，不承诺阅读顺序
按搜索跳读 「我只要这个答案」 拿到一条命令，不知道为什么，换个场景就失效 每篇头部的「前置依赖」与「本篇产出物」告诉你缺什么、能拿到什么
问同事 最快 每个人给的顺序不一样，且没有沉淀 团队规范集中在 7.11，是唯一事实来源，别处只链接不复述

💡 新人小结：这个库像一座开架图书馆。书按主题分区上架（基础认知、镜像构建、运维手册……），你可以直接走向需要的区；每个书脊上贴着一张小条，写「读这本书前你得先懂哪两本」「读完你能带走什么」。编号是索书号，不是借阅顺序——图书馆从没要求任何人从 001 号开始读。 对应到这个库：分区 = 十个主题篇；书脊小条 = 每篇第一屏的七项头部契约；索书号 = 章节编号。而「实战暗线」是馆方的一条装修动线：它规定每本书里的动手例子该长在哪一步，不是给读者规划的参观路线。

这个库是怎么组织的

两条轨，主副分明：

  • 主题轨是主干。十个分类按读者的认知顺序排列——先知道为什么需要它，再会跑起来，再会造镜像，再会编排，再问原理，再上生产，最后是会坏的东西怎么修。你可以通读，也可以只查其中一篇。
  • 实战暗线是副。所有动手例子共用同一个项目（一个 Spring Boot 后端 + 一个 Vue3 前端 + MySQL + Redis + nginx），它从「本机装不上依赖」一路生长到「出事能查、查完留痕」，共八段。它是示例资产的生长骨架，不是你的阅读路线。

这个定位不是从一开始就定下来的，中间走过一条弯路，值得记下来免得再走：

方案 当时的想法 代价 结局
主线（v2.0） 给新人一条完整的路，按段通读最不容易迷路 与「按主题学习」抢路径；读者要同时维护两套顺序；查一个知识点时被迫关心它在链条第几节 放弃。它把「我为什么要现在读它」的回答绑死在链条位置上
只做增量补章节（v1.2 原样） 骨架不动，缺什么补什么，最省事 并列知识点越来越多，60 篇涨到 80 篇时每篇更孤立 放弃。这是原病灶
主题为主 + 实战为暗线（现行） 主题轨管阅读，暗线管例子的组织 必须另立判据保证例子不断链——于是有下面的「从 0 完整性三条」 采用

被放弃的方案不是没价值的：主线那条路对「完全不知道该问什么」的人仍然有用，它被保留成 0.2 里的一条推荐路径（7 天上手线），只是不再是唯一入口。

💡 新人小结：暗线像一家餐厅后厨的出菜顺序——凉菜先上、热菜随后、汤压轴。作为客人你点菜不受这个顺序约束（你可以只要汤），但它确实存在，因为如果汤先出、凉菜后出，那桌菜就坏了。 对应到这个库：你点菜 = 按主题查阅；后厨出菜顺序 = 示例链八段；「汤先出会坏」= 后一段的示例若覆盖了前一段的产物，前后对照就再也复现不了。所以下面三条判据是硬的。

示例链的从 0 完整性三条

暗线不再承担阅读路线后，「跟着例子从零做完」这件事不能再靠顺序保证，只能独立可判：

# 判据 具体要求 谁来验
1 每段自带全部前置 该段跑通所需的引擎版本、JDK/Node 版本、初始数据、机器要求，全写在该段的 README 里；禁止出现「按前面几步的准备」 在一台没跑过任何段的机器上，只看这一段 README 跑一遍；跑不通即不合格
2 后段不覆盖前段产物 演进用新文件表达（Dockerfile.v1 与 .v2 并存，开发用 compose.dev.yaml、生产用 compose.prod.yaml） 逐段检出、逐段构建
3 跳级自检成立 第 N 段声明的前置，必须能被第 1 到 N-1 段的产出满足；需要段外操作时，该段 README 必须显式写出这一步 脚本比对前置清单与产出清单

第 3 条有个反直觉的设计值得先说：链上不是每段都依赖前段。示例后端的 api-service 自带完整源码，你可以在完全没跑过前两段的情况下直接从第③段起步——因为「造镜像」这个主题需要的是一个可构建的工程，不是一个已经跑起来的开发环境。如果每段都硬咬住前一段，暗线就会以另一种形式变回主线。

头部契约七项各自解决什么

每篇正文第一屏都有这七行。它不是装饰，每一项都在堵一个具体的失败：

项 它回答的问题 缺了会怎样
实战落点 本篇的动手例子挂在示例链哪一段 例子变成与主题无关的综合大作业，读者抄不动
示例版本 用到哪个文件的哪一版、承前自哪一段 演进链断了也看不出来，前后对照复现不了
前置依赖 读这篇前必须会什么（最多 3 个） 读者在缺前置的情况下硬读，产生「讲了但没懂」
本篇产出物 读完手上多了什么可验证的东西 「理解了原理」这种无法验收，学与不学看不出差别
拓展接口 本篇的结论后面被谁复用、被谁推翻 基础篇的简化结论被后面悄悄改掉，读者以为前面写错了

自测三题 我是不是真读完了 眼睛划过一遍就当会了

「拓展接口」这项值得多说一句，因为它是这个库允许基础内容不写全的前提。基础篇可以只给一个够用的简化说法，条件是它必须自己声明在哪里会被修正。比如基础那几篇说「容器内存限制就是容器能用的内存上限」，这在单机开发里够用；到运行基线那篇要修正成「限制值还决定了 JVM 默认堆的推算」，并且要写明这是修正而不是前面写错。

对照 gitee.com                  成功（29 ms → 83 ms，两轮都是 200）

证据 本机读数 为什么够用

怎么把问题问到能答的程度

同一个故障，两种问法，得到的帮助差别很大。这不是态度问题，而是信息结构问题：排错手册按「症状 → 判据 → 命令 → 根因」组织，你的提问也要落到这四列里。

问法 实际效果
「Docker 起不来了怎么办」 无法定位。范围覆盖十个故障域，只能反问一串问题
「容器起来 3 秒就退了，ps -a 显示退出码 137，宿主机内存还剩很多」 一次命中。退出码 + 时间特征 + 已排除项，直接进对应那一行

值班可用的最小提问模板，四条信息按顺序给：

1. 症状：一条现象描述 + 原始报错文本（不要转述，原文粘贴）
2. 范围：影响单个容器 / 整个宿主机 / 整个集群
3. 已排除：已经查过并否定的假设（这比「我试了什么」更有信息量）
4. 环境：引擎版本、宿主系统、是否近期变更过

第 3 条最容易被省，也最值钱——它决定了别人要不要重复你已经走过的路。这一模板与 7.2 症状索引是同一套思路：按现象检索，而不是按原因检索，因为在出事的当下你并不知道原因。

为什么要给写作本身定规矩

这个库有 76 章、合并成 28 篇。如果没有统一的写作要求，会发生的事情是确定的：每个人按自己习惯的写法写，两百多篇文档长成两百多种样子。下面是一次真实的合并评审里出现的三种分歧，都跟内容对错无关：

甲：「这篇开头先讲概念定义，读者需要。」
乙：「我负责的篇都从一段报错开始，读起来快。」
丙：「我把小结放在开头当摘要了，结尾就没有总结段。」
三人：「我们都符合『讲清楚了』的标准。」

问题不在谁对，而在没有可检查的共同标准，于是「讲清楚了」变成每人一套。定规矩的收益不是文笔变好，而是三件可操作的事：读者在任何一篇都能在同一位置找到同一类信息；评审有明确的可查项而不是凭印象；新作者不必先揣摩风格。

💡 新人小结：给技术文档定写作要求，像连锁餐饮的标准作业书。它不是为了让每个厨师做得更有创意，而是让顾客在任何一家店、任何一位值班厨师手里，拿到同一份味道和同一套出菜顺序。 对应到这里：标准作业书 = 本章的 W1~W6；「同一份味道」= 每篇都在同一位置有痛点开场、实战切入、要点总结；顾客 = 零基础新人，他不知道你的篇章该长什么样，所以只能靠位置的一致性来定位信息。

W1 文风：三条合格线

三条各有可自查的动作，不接受「我觉得写得还行」。

维度 含义 合格线 怎么自查
严谨 每个技术断言都可被验证 数字带出处或标注核对日期；命令带真实输出；不用「通常」「一般来说」「可能」掩盖自己没验证过 全文搜这几个词，逐个改成有出处的断言；改不出来的直接删掉

深度 不停在「怎么做」，要给「为什么」和「不这样做的代价」 凡有方案选择处，写出被放弃的方案与放弃理由；凡有默认值处，说明它为什么是这个值 检查本篇是否只有「推荐做法」而没有「为什么不选另一种」

W3 新人小结：类比之后必须接机制

凡首次引入一个抽象概念，必须紧跟一段固定格式的小结。两条硬要求，缺一条即不合格：

  1. 类比之后必须接一句机制对应，把生活物件的每个部件映射到技术名词上。只有类比没有对应等于修辞——读者读完仍然不知道那个名词是什么。
  2. 类比必须在本篇的关键判据上成立。若它会在某处误导，要显式写出「这个类比在哪里失效」。
> 💡 新人小结：镜像分层就像一摞透明胶片，每张画一部分，叠起来看才是完整画面；要改的时候只在最上面加一张新的，下面那些不动。
> 对应到 Docker：下面那些只读胶片是 lowerdir（镜像层），你手上正在画的那张是 upperdir（容器层），叠出来给你看的是 merged。所谓「写时复制」就是——你要改下面某张的画面时，系统先把那一块复制到最上面这张，再改复印件。
> 类比在这里失效：胶片是同时可见的，而镜像层只有最上面可写，下层被遮住的部分你照样能读，但一次改动只发生在你这一层。

格式上有一条坑要写明：标记串必须原样写成「💡 新人小结」，中间不能加粗体符号。结构检查是按这个字面量统计篇内小结数量的，把标签包进强调标记里，检查就会把你写的小结全部数成零——这一条不是理论风险，本篇初稿就是这么被报出来又修掉的。

W4 结构化载体

优先级：能用表格就不用段落，能用代码块就不用行内命令，关系类信息优先用图。

表格

什么时候必须用表格 什么时候不要用
三个以上对象、两个以上属性要对比 只有两行，或内容本身是线性叙述
承载实测数据——此时必须配列定义：每列回答什么问题、基准值是多少、最容易怎么读错 用来罗列本该写成步骤的操作
症状 → 判据 → 命令 → 根因 这类多域对照 单元格里塞超过三句话——那是段落，拆出去

同一份文档里多张表共用口径时，写一节统一的读表键并在每张表前加指针，不要逐表重复。

代码块

  • 必须标语言，例如命令行、YAML、镜像描述文件、Java、Mermaid。
  • 命令与输出同块给出：命令带提示符前缀，输出为真实粘贴，可截断但要标注省略处。禁止手写想象中的输出。
  • 超过 20 行的完整文件放进示例目录，正文只给关键片段与文件路径。
  • 需要读者抄走的命令，必须能在贯穿示例里原样跑通。

图

用途 图型 例子
组件与调用关系 流程图 引擎架构总览
一次操作背后发生了什么 时序图 创建并启动容器的逐段调用
排查决策 带判断分支的流程图 容器立刻退出的排查路径
演进与归属映射 流程图 本库主题轨与示例链的对照

四条硬规矩：

  • 节点标签一律用双引号包裹，避免中文标点与括号触发解析错误。
  • 每张图必须过真解析器（mermaid.parse()），不接受「看着像对的」。本库的自动化检查里含这一步。
  • 一张图只表达一个关系维度，节点超过 15 个就拆。上面那张四段流程图与篇首的双轨图就是因为这个规则拆开的。
  • 需要精确排版、要导出去做汇报材料的架构图走绘图工具（源文件与导出图放静态目录）；随文档演进的图走文本图。

文件名的一条硬约束

文件与目录名只能含中文、字母、数字、连字符与下划线，且必须以 .md 结尾。两个原因都是实测来的：

违规形态 后果
名字里含顿号 站点构建会把顿号从地址里吃掉，链接检查找不到产物，整批报「无法映射」，此时「断链为零」这个数字不可信
名字不以扩展名结尾 覆盖率统计按扩展名收集条目，这类文件会被静默跳过——它照样有记录、照样被认领，却永远不会被判为「漏写」

第二种是真正的危险：它不是报错，而是让判据看不见那一格，绿灯照样全亮。

两处规范落不下去的地方（本轮实测发现）

诚实记录，因为它们需要在下一轮修订里解决，而不是让每个作者自己踩：

# 冲突 现象 建议处置
1 小结标记的字面量与排版习惯冲突 规范模板把标签写成强调格式（加粗），结构检查却按「表情符号 + 空格 + 标签」的字面量计数，于是合规写法被判零小结 已在本文改为统一字面量；结构检查宜同时接受两种形式，或在模板里明确禁止加粗
2 禁止清单与问题代号无法在规范文里被引用 检查把若干「推脱式措辞」和几个英文代号做成了字面量匹配，因此讲解这些禁令的文章不能逐字列出被禁的词与代号，否则自己先违规 被禁词表宜由脚本读取外部数据文件，或给「引用禁令」的语境加豁免；本文只按类别描述，不逐字引用

第 2 条不是纸上推演，是本轮当场付的代价：本文最初把审计脚本的按类别计数行原样粘进了实战切入那一节，于是被自己的检查抓到一次「正文出现了被禁代号」。修法是把那行改成散文描述，只保留不含代号的真实汇总行——粘贴的仍是真实读数，只是不再逐字复述代号。

这条经验值得推广成一条通用规矩：凡讲解检查规则本身的文档，不能直接粘贴规则输出；要么转述，要么让规则对被引用语境豁免。这也是「判据要能自己红」的另一面：判据也要能证明自己不会咬到描述它的那段文字。

要点总结

  • 写作要求的价值不在文笔，而在可检查：读者能在每篇的同一位置找到同类信息，评审有明确条目，新作者不用揣摩风格。
  • 正文按痛点、设计、流程、实战切入四段推进，顺序不可倒；检索型文档整体除外，判据是「读者是否带着具体现象来」。
  • 新人小结必须双段：类比 + 机制对应，并标出类比失效处；标记串要按字面量书写，加粗会让检查数成零。
  • 载体优先级是表格、代码块、图；实测表必须配列定义；图必须过真解析器且一图一维度；文件名有两条来自实测事故的硬约束。
  • 头部契约七项是承重件，其中「产出物」与「拓展接口」最能暴露没想清楚的地方。
  • 基础层的标准是「读者不必再靠猜」：知识点唯一归属、不许留悬念、切片不许过宽。
  • 两处规范自相冲突的地方已如实登记，需要在下一轮修订里处理，而不是留给每个作者自己发现。

为什么要先量自己的机器

一个真实场景：新人拿到文档，第一步是「跑一条命令看看能不能起来」，命令报错，于是他认定文档写错了。但报错文本里其实已经写明是三类完全不同的问题之一——他还没分清自己有没有装东西。

「这条命令报 command not found」
「那说明你机器上根本没有它，不是命令写错了。」
「那我照文档下一步装好就行了吧？」
「先别。你现在装，等会儿再失败一次，你会分不清是装的过程失败还是文档失败。」
「所以要先做什么？」
「先把你现在有什么、网络能不能通记下来。装完再记一次。两次一对，问题自己就跳出来了。」

本篇在本机上把这段对话实践了两遍：2026-10-25 第一轮，2026-10-27 第二轮（装上引擎与子系统之后再测）。两次读数放在同一张表里看，才有意义——单看任何一轮，都得不出「安装到底改变了什么」的结论。

三个平台各自要装什么

引擎不是一个单独的程序，它依赖平台提供隔离能力的机制。三个平台的依赖链完全不同，这是很多跨平台教程失效的原因。

平台 依赖什么 要装的东西 最容易卡在哪
Windows 11 需要 Linux 子系统提供内核；引擎跑在子系统里 子系统 + 引擎桌面版 虚拟化在 BIOS 里被关；子系统已装但处于旧版本
macOS（Apple 芯片） 靠轻量虚拟机跑一个真正的 Linux 内核 桌面版引擎 把「本机是类 Unix」当成能直接跑容器——不能，内核不是 Linux
Linux 直接用本机内核的命名空间与控制组 引擎本体 内核版本过旧；用户没加入引擎组，每条命令都要 sudo

本机第二轮的 docker info 读数可以当作「Windows + WSL2 后端装对之后长什么样」的样板：

两个常见误解要在这里点掉：

误解 事实
macOS 类 Unix，所以能像 Linux 一样原生跑容器 不能。容器需要 Linux 内核特性，macOS 内核不提供，桌面版仍是起一个虚拟机
Windows 装了引擎就等于有 Linux 内核 只在「Linux 容器」模式下成立，且依赖子系统；Windows 容器模式是另一套完全不同的东西，本库不覆盖

本库统一以 Linux 容器语义讲解。 涉及平台差异的地方会显式标注，比如宿主机地址解析、数据挂载的性能与权限表现。

装完之后怎么验（七条判据）

按顺序跑。每条都给「看到什么算过」，以及本机两轮的实测状态。

# 检查项 过 / 不过的判据 本机 2026-10-27
1 引擎命令存在 docker version 返回码 0，客户端与服务端两段都有版本号 过（Client 29.8.0 / Server 29.8.0）
2 虚拟化与子系统就绪 Windows：wsl --status 返回码 0 且默认版本为 2 过（docker-desktop，版本 2）
3 镜像域名解析正确 解析出的地址能在 443 完成 TLS 握手；仅「能返回地址」不算过 直连仍不过（64.13.192.76，6018 ms 超时）；走代理时该问句不再成立，见下一条
4 出口通畅（对照） 至少一个对照站点 TCP 与 TLS 在几十毫秒量级成功 过（55 ms / 83 ms，都 200）
5 本机时钟可信 与公开服务器的 Date 偏差在秒级；证书有效期覆盖当前时间 过（偏差 −0.1 秒，剩余 89 天）
6 镜像获取通道可用 能拉成一个几 MB 的小镜像，或返回明确状态码而非超时 不过 → 过：未配代理时返回码 1（dial tcp …:443: connectex）；配本机代理后 hello-world 与 redis:7-alpine、mysql:8.4 全部返回码 0
7 容器能跑起来 起一个容器能看到它执行并退出，参数与限制在容器内可见 过（两条路径都验了：FROM scratch 自建镜像，以及公开镜像 docker run --rm hello-world 返回码 0）

第 6 条那一行「不过 → 过」是本机状态的真实变化，不是判据变松：判据没动，是通路变了。同时注意第 3 条在配了代理之后依然不过——直连那个域名仍然拿到连不通的地址。这两件事合起来说明一个重要区别：通道问题可以靠代理绕开，但不要去"修"解析本身；把第 3 条当成必须修好的项，会白白去折腾本机 DNS。

引擎可用 ≠ 能拉镜像：这条判断在第 6 条不过的那几个小时里完全成立（第 1、2、7 条全过，第①段仍然跑不起来）；配上代理之后七条全过，第①段才真正具备起跑条件。

这段文本里有两个可直接取用的信息：dial tcp 64.13.192.76:443: connectex 说明失败在传输层（连不上），不是应用层的拒绝；because Docker Desktop has no HTTPS proxy 说明引擎没有配任何代理，走的是直连。后者顺手回答「要不要配代理」这个问题——没配。

第 1 条在 Git Bash 里有个纯读取层面的坑：系统命令返回的是 GBK 编码的中文提示，直接看会是一段乱码字节，不像「未找到」的意思。同理 wsl.exe 的输出是 UTF-16LE。

命令返回码 1，输出按 GBK 解码：信息: 用提供的模式无法找到文件。
wsl.exe --status 第一轮返回码 50，按 UTF-16LE 解码：未安装适用于 Linux 的 Windows 子系统……
第二轮返回码 0，同一解码：默认分发: docker-desktop | 默认版本: 2 | 当前计算机配置不支持 WSL1……

判据的读法要跟着调：看返回码，不要靠肉眼看输出文本。文本可能被编码破坏，返回码不会。上面那句「不支持 WSL1」也值得注意——它是 rc=0 成功输出里的一句附带提示，不是错误，别被它带偏去查 WSL1。

拉不下来该查哪一段：四段定位法

「拉取失败」在外层看是一条超时，实际可能是四个完全不同的位置。

flowchart TB
    S["现象：拉取镜像失败或超时"] --> Q1{"命令本身找得到吗"}
    Q1 -- "否，返回码 127" --> A1["引擎未安装或未进 PATH：与镜像无关，先装"]
    Q1 -- "是" --> Q2{"域名解析返回地址吗"}
    Q2 -- "不返回" --> A2["本机 DNS 配置问题：先解决解析"]
    Q2 -- "返回" --> Q3{"对返回地址 443 端口能握手吗"}
    Q3 -- "超时" --> Q4{"对照站点能正常握手吗"}
    Q4 -- "能" --> A3["地址被改写或链路被拦截：与限流无关，走加速通道或代理"]
    Q4 -- "不能" --> A4["本机整体出口问题：代理、防火墙、网络本身"]
    Q3 -- "能握手但报证书错" --> A5["中间设备替换证书，或本机时间漂移"]
    Q3 -- "能握手且返回明确状态码" --> A6["到应用层了：429 是限流，401 或 403 是认证，404 是标签不存在"]

本机两轮读数在这张图上的落点完全一致：Q1 过 → Q2 返回 → Q3 超时 → Q4 通 → A3。第 3、4 条一起看才能定到 A3，只有一条都不够。

跨解析器对照这一招现在失效了，要如实记下来。 第一轮我用三个解析器问同一个域名，得到三个不同地址（系统 31.13.70.13、223.5.5.5 给 199.59.149.238、114.114.114.114 给 185.60.219.41），而对照站点在两个解析器下答案一致，据此把「疑似被改写」钉成结论。第二轮再问那两个解析器，UDP 53 端口直接超时，这一招当场不可用。

失效之后还有两条更好拿的证据，本轮都用上了：

证据 本机读数 为什么它够用
同一个域名，答案随时间变 第一轮 31.13.70.13，第二轮 64.13.192.76；容器内第三次问，得到 108.160.166.57 一个真·权威解析不会两天给三个不同、且全都连不通的地址；对照站点两轮都稳定给出 153.3.238.x 且能握手
引擎自述它连的是哪个地址 报错里写 dial tcp 64.13.192.76:443，与我在宿主上用 getaddrinfo 问到的同一个地址 证明「宿主看到的」和「引擎实际连的」是一回事，排除「引擎走了另一条解析路径」这种解释

💡 新人小结：四段定位像查一根断掉的电线。从电表开始往家里量：先确认有没有电到门口，再确认墙上插座有没有电，最后才怀疑你插的那台机器坏了。每一段都要用同一个已知能工作的电器去试——那个电器就是「对照站点」。 对应到这里：对照站点的价值在于它能证明「量电的工具本身是好的」。没有它，你无法区分「目标不通」和「我的探测方法不通」，而这两者的读数长得一模一样。本机第二轮就差点栽在这上面：跨解析器那招超时了，如果不同时准备另外两条证据，就会被引导成「解析器全都挂了」的错误结论。

证书与时间：四段定位里最容易被跳过的一格

决策图里「能握手但报证书错」这一格要单独讲，因为它的报错文本会把人引向完全错误的方向：写着证书相关，人就去换证书或加跳过校验的开关，而实际成因常常是本机时钟。

本机方法：同时取服务器的 HTTP Date 头与本机 UTC，再读 TLS 证书有效期。

$ python -c "取服务器 Date 头、本机 UTC、TLS 证书有效期并比较"
www.baidu.com      对端 153.3.238.127   TCP+TLS 55 ms
    Date 偏差 -0.1 s | 证书剩余 89 天 | 状态行 HTTP/1.1 200 OK
gitee.com          对端 180.76.198.225  TCP+TLS 83 ms
    Date 偏差 -0.0 s | 证书剩余 116 天 | 状态行 HTTP/1.1 200 OK
观察 本机值 判据含义
本机与服务器的时间差 −0.1 秒 / −0.0 秒 秒级以内属正常。偏差到分钟级以上就要查时钟同步，证书校验会开始随机失败
证书有效期是否覆盖当前时间 覆盖 本机时钟若跑到有效期之外，任何合法证书都会被判为无效
剩余天数 89 天 / 116 天 剩余极少时容易和「刚过期」混淆，到期前一周内的失败要优先查这一项

💡 新人小结：证书校验像过海关——海关看你护照上的日期，如果你的手表慢了一年，你的护照就"过期"了，哪怕海关的系统时间完全正确。修表比换护照便宜得多，但很多人先做了后者。 对应到这里：手表 = 本机系统时钟；护照有效期 = 证书的起止时间；海关系统 = 远端服务。所以遇到证书类报错，第一条检查动作是核对本机时间，而不是去动引擎的校验开关。

三种表现要分开处置，它们看着像同一件事：

表现 优先怀疑 一条验证动作
只在某些域名报证书错，浏览器访问同一地址正常 中间设备（公司出口网关）替换了证书 对比命令行与浏览器看到的证书签发链，不同就是被替换
所有 HTTPS 目标都报证书错 本机时钟漂移 比较本机 UTC 与任一公开服务器的 Date 头，看偏差量级
报的是超时而不是证书 链路问题，回到上一节的四段定位 先跑对照站点，确认出口通畅与否

最后一条要划清边界：换证书或跳过校验不是解决方案。跳过校验会让真正的中间人问题静默消失，本库不提供这类开关的用法。

不依赖镜像仓库，仍然验证运行时（第 7 条怎么过的）

第 6 条不过时，第 7 条看起来必然也没法测——没有镜像怎么起容器？可以不用仓库。用 FROM scratch 加一个本机交叉编译出来的静态 Linux 二进制，整条链路一次网络都不碰。

# 1) 交叉编译一个静态 Linux 二进制（本机 Go，不联网）
$ GOOS=linux GOARCH=amd64 CGO_ENABLED=0 GOTOOLCHAIN=local GOPROXY=off go build -trimpath -o demo .
$ ls -l demo
-rw-r--r-- 1 ... 3314972 Oct 27 07:52 demo          # 约 3.3 MB 静态二进制

# 2) 镜像描述文件：基础镜像是空的，唯一一层来自本机文件
$ cat Dockerfile
FROM scratch
COPY demo /demo
ENTRYPOINT ["/demo"]

# 3) 构建并运行，顺带把内存上限和主机名传进去
$ docker build -t proof:local .
$ docker run --rm --memory=64m --hostname proof-01 proof:local

读数 结论

Windows 与子系统的三处初始设置

装上之后有三件事不做，后面一定会踩。第一条本轮有了实测数据，另外两条仍未实测，标注照旧。

设置 为什么 不做会怎样 本机可复现性
给子系统设内存上限 子系统默认可以吃掉一半物理内存，且长期持有不释放 宿主内存被大量占用 默认值已实测：引擎可见 47.01 GiB，宿主物理内存 95.9 GB，正好约一半。设上限的具体操作与效果未实测（本轮没改配置）。96 GB 这类机器上，把上限设到 8~16 GB 是合理起点
工程文件放在子系统内而不是 Windows 盘 跨系统挂载的文件操作性能远低于同一文件系统内 构建时大量小文件读写，耗时成倍增加 未实测
注意虚拟磁盘不自动回收 磁盘文件只会增长不会缩小，删除镜像不等于释放宿主空间 数据盘看起来「越用越小」，需要手动压缩流程 未实测。本机 C 盘 477 GB 总、316 GB 可用，容量不是当前瓶颈

这三处与更深的坑（子系统与桌面引擎的启停依赖、休眠后容器网络失效）在第七篇专门有一节，遇到时直接查那里。

代理与镜像通道

如果公司网络要求走代理，需要两处都配：桌面引擎的代理设置，以及子系统内部的 shell 代理。只配一处时会出现「浏览器能开网页但拉不下来」，这是最常见的半配状态。

判断走了哪条路：
1) 引擎配置里有代理，命令行环境变量里没有 —— 引擎自己走代理，容器内进程不走
2) 只有环境变量有代理 —— 引擎不走，容器内构建时下载依赖会走

镜像通道分两类：公开镜像加速（改引擎的仓库地址配置），和私有仓库代理缓存（在自己机房里缓存一份，见 3.10）。选哪个是团队决定，本库示例统一不假设你有可用加速通道——所有需要拉镜像的步骤，都在该段的前置清单里写明「需要一条可用的镜像获取通道」，不静默依赖某个具体加速域名。

本库的示例之所以把"镜像获取通道"写进每段的前置清单而不静默依赖某个加速域名，就是因为本机第三轮之前正卡在这里：引擎与运行时全合格，第①段要的两个公共镜像却拉不到。配好代理后该条解除，见下一节。

打通通道：代理与加速器是两条路

第三轮（同日 2026-10-27，配了本机代理之后）把第 6 条解开了。先看唯一变量是代理这组对照：

$ curl -s -o /dev/null -w "%{http_code}" --max-time 12 https://registry-1.docker.io/v2/
000                     # 直连，12 秒后 curl 返回码 28（超时）

$ curl -x http://127.0.0.1:7890 -s -o /dev/null -w "%{http_code}" --max-time 15 https://registry-1.docker.io/v2/
401                     # 走代理，0.84 秒

401 是成功信号而不是失败：/v2/ 这个端点在未认证时本来就该回 {"errors":[{"code":"UNAUTHORIZED",…}]}。真正说明问题的是它答话了，而直连那侧连 TCP 都没建起来。

引擎侧的可观测变化：

时点 docker info 的代理段 docker pull hello-world
未配代理 无（报错原文写着 because Docker Desktop has no HTTPS proxy） 返回码 1，dial tcp 64.13.192.76:443: connectex
配代理后 HTTP Proxy: http.docker.internal:3128、HTTPS Proxy: http.docker.internal:3128、No Proxy: hubproxy.docker.internal 返回码 0，Digest: sha256:11a3eb15…，Status: Downloaded newer image

拉取耗时与体积的真实读数：redis:7-alpine 5.3 秒（57.8 MB）、mysql:8.4 22 秒（1.12 GB）、hello-world 25.9 kB。

💡 新人小结：代理和加速器像两种不同的出门方式。代理是绕一段路走能通的桥，任何目的地都能到，但每次都要绕；加速器是在你楼下建个前置仓，常用的货直接就近取，货没备或者仓库挂了，你还是出不去。 对应到这里：代理改的是「引擎出网走哪条链路」，与目标无关，所以它对任意镜像都成立；加速器改的是「去哪个域名取镜像」，只对它缓存过的东西有效。两者可以叠加，但排查时要把它们分开试——先证明「走代理能通」，再谈要不要加速器。

三条判断口径：

情况 该配哪个 依据
直连超时（像本机第三轮之前） 代理 连 TCP 都建不起来，加速器域名同样要靠出网能力，先解决通路
直连能通但很慢、或某些公共库限流 加速器 已到达应用层，问题在链路质量或配额
需要拉私有仓库的镜像 都不解决 那是认证与信任问题，见 3.10 与 7.6 的 401/403、X509 分支

一处需要诚实标注的边界：http.docker.internal:3128 是桌面版引擎的内部代理入口，它再把流量转给系统层配置的代理。本轮只观测到「配了之后引擎这段从无到有、拉取随即成功」这一对变化，没有逐跳验证流量是怎么传到 127.0.0.1:7890 的——那需要看桌面版设置项与流量落点。文档只写观测到的这一层。

MySQL 侧：同一套动作，判据换成 SELECT。

宿主 127.0.0.1:3307 连接成功 8 ms，并收到 MySQL 握手包，包里的版本串是 8.4.13

这两次判定之前都被我自己的脚本骗过一回，值得单独记，因为它们比结论更容易复发：

假结果 我的写法错在哪 症状 为什么会误判
以为 MySQL 数据没挂到卷上 -v kb-p1-mysqldata:/var/lib/dockervolume，把 /var/lib/mysql 打错 挂载列表里出现两个卷：命名卷挂在那个不存在的路径上，另有一个匿名卷挂着 /var/lib/mysql 容器照跑、SELECT 照出数据，看着完全正常。但那时删掉匿名卷才算丢数据，而我没有它的名义 → 测出来的"留存"毫无意义
以为 Redis 的键没留住 手写 RESP 时给了 $3 的长度前缀，而 key 是 8 字符的 kb:proof 返回 $-1（nil）外加一条 -ERR unknown command 'oof' $-1 长得太像"键不存在＝数据丢了"。实际是服务端按 3 字节读走 kb:，把剩下的 proof 当成新命令解析。是客户端坏了，不是 Redis 坏了

两条教训合并成一句判据使用规矩：测"数据留存"之前，先确认数据到底落在哪个卷上；拿到 nil / 空结果之前，先确认你的读法本身没错（INFO 里的报错文本、挂载列表里的匿名卷，都是免费的真值来源）。

清理也是流程的一部分：本轮创建的 2 个容器、2 个命名卷、3 个镜像与构建缓存全部删除，docker system df 复核为 Images 0 / Containers 0 / Local Volumes 0 / Build Cache 0。删除前的占用规模可以当容量参考——两个卷一共 218.4 MB（MySQL 初始化数据目录就写了这么多），三个镜像合计 1.176 GB（其中 MySQL 一个就 1.12 GB）。

常见误读

你可能的理解 实际情况
解析返回了 IP 就是网络正常 五毫秒返回一个不可达的地址，比不返回更具迷惑性。判据要落到「能不能握手」
超时就是镜像站限流 限流返回明确的 HTTP 状态码与文字，不会表现为 TCP 层超时。超时说明没到应用层
装完引擎就能直接跑示例链 还要有镜像获取通道。本机头两轮就是反例：引擎、子系统、运行时全合格，第①段仍跑不了，直到把代理配上
引擎装好意味着容器能跑 这是两件事，而且要分开判。本机在拉不到任何公共镜像的状态下，仍能用一条不碰仓库的路径证明运行时可用
配了代理，解析问题就"修好"了 没有。直连那个域名依旧拿到连不通的地址（本机第 3 条至今不过），只是引擎不再依赖那条直连路径。别去折腾本机 DNS
数据挂在命名卷上就一定测得准 先确认数据真的落在那个卷。本机就写错过一次目标路径，Docker 顺手建了个匿名卷接走真实数据目录，容器照跑、查询照出，但那时的"留存"毫无意义
读到空结果就是数据丢了 先确认你的读法没错。手写协议时长度前缀写错，服务端会把余下字节当新命令，回一个 nil 外加一条怪错——看起来完全像"键不存在"
加速器配了就一劳永逸 加速通道会失效或变更。每次「拉不下来」都重跑七行，而不是先怀疑文档
命令输出看不懂就是环境问题 先看返回码。Windows 上系统命令的中文输出常被编码破坏，返回码才是可靠信号
宿主解析到的地址就是容器看到的 不一定。本机同一次运行里宿主与容器各得到不同地址

要点总结

  • 装之前先做七项体检，装之后再测一次：两次读数的差才是安装过程的结果，单次读数说明不了任何事。本篇两轮读数就摆在一起作证。
  • 判据要落在返回码与握手结果上，不落在文本观感上。Windows 上编码会把中文提示毁掉；而五毫秒返回的假地址比超时报错更危险。
  • 「拉不下来」分四段量：命令存在性、解析、握手、应用层状态码。对照站点是这套方法里唯一能证明「探针没坏」的东西。跨解析器对照这一招会因为 UDP 53 被封而失效，所以要备好另外两条证据（同一域名答案随时间变、引擎自述实连地址）。
  • 引擎可用 ≠ 能拉镜像。第 7 条可以用 FROM scratch + 本机静态二进制在不碰仓库的情况下证明，顺带还能量出控制组 v2、--memory 的真实下发值和引擎自生成的容器 DNS。
  • 本库所有示例都不静默依赖具体加速域名：镜像获取通道写进每段的前置清单，缺了就在本篇停下，不要边装边往下读。
  • 子系统默认给引擎约一半物理内存这件事，本机已实测（47.01 GiB / 95.9 GB）；设上限的操作与效果仍未实测。

为什么要先把这三件事分清楚

一个人把服务跑起来，卡了半小时：

「应用连不上我本地的 MySQL，容器明明在跑。」
「端口映射成什么的？」
「没写 -p，我在镜像里 EXPOSE 了 3306。」
「EXPOSE 不打开端口。而且你连的是 localhost:3306，宿主机上根本没有监听。」
「好，加了 -p 通了。另一个问题：我删了容器重建，数据没了。」
「那个卷是绑定挂载还是命名卷？……你把数据放容器可写层里了。」
「行。最后一个：日志时间比实际晚 8 小时，我以为数据库时钟坏了。」
「容器默认是 UTC。你的宿主是 +0800，差的是显示口径，不是时间。」

这三个坑的共同点是：它们都不是"Docker 的 bug"，而是三个不同层面的"东西在哪"被搞混了——端口在谁身上、数据落在哪个文件系统、时间按哪个时区显示。这三件事一旦分清，第二篇剩下的一半内容会顺很多。

💡 新人小结：-p 6380:6379 像公司前台转接。外面的人拨总机 6380，前台再转到你工位分机 6379；你工位上的人不需要知道总机号，也不因为总机换了号就得搬桌子。 对应到 Docker：6380 是宿主机（准确说是容器运行环境那一侧）监听的端口，6379 是容器内进程监听的端口，冒号左边是"外面拨的号"、右边是"里面接的号"。容器内进程永远只看到 6379，所以下面第一条读数里容器自己登记的端口就是 6379。

端口映射：谁在监听哪个号

五种写法都在本机跑过，读数是真实取到的。

写法 宿主侧实际监听（netstat -ano 原文） 说明
-p 6380:6379 TCP 0.0.0.0:6380 ... LISTENING、TCP [::]:6380 ... LISTENING、另有 TCP 127.0.0.1:6380 ... LISTENING 四个地址族都在，等于"任何网卡都能进"
-p 127.0.0.1:6381:6379 只有 TCP 127.0.0.1:6381 ... LISTENING 绑定地址收窄到回环。docker port 显示 6379/tcp -> 127.0.0.1:6381
-p 6379 6379/tcp -> 0.0.0.0:60993、6379/tcp -> [::]:60993 宿主端口随机分配，必须用 docker port 才查得到
-p 8080:80（本表未跑） — 结构同上，只是把容器端口换成 80
--network host 容器内 hostname 返回 docker-desktop 桌面版上「host」指那台 Linux 虚拟机的网络栈，不是你的 Windows。端口不映射，直接占 VM 的

容器那一侧看到什么，是这节最该记住的一条：

$ docker exec m-p1 sh -c "head -2 /proc/net/tcp"
  sl  local_address rem_address   st ...
   0: 00000000:18EB 00000000:0000 0A ...   uid 999

18EB 是十六进制，换算过来正是 6379。也就是说容器里那份监听表上完全没有 6380 这个数——它根本不知道外面用了哪个号。这条读数是"端口映射不影响应用内部"的最硬证据。

顺手一条判据：映射成功后从宿主发一次真实协议请求，比看状态更可靠。

$ （对 127.0.0.1:6380 发 RESP 命令 SET a1 v1 / GET a1）
+OK
$2
v1

宿主端口被占时的报错长这样，认得它能省十分钟：

$ docker run -d --name m-p5 -p 6380:6379 redis:7-alpine
docker: Error response from daemon: failed to set up container networking: driver failed
programming external connectivity on endpoint m-p5 (...): Bind for 0.0.0.0:6380 failed:
port is already allocated
[返回码 125]

判据：换宿主端口，不要去动容器端口。上面这条错误里 0.0.0.0:6380 是宿主侧的冲突点，容器侧的 6379 从没参与竞争。

容器之间怎么找到彼此

这是本篇第二个"东西在哪"：名字解析发生在哪个网络里。三条命令的对照：

场景 命令 本机读数
目标容器在默认 bridge，发起容器也在默认 bridge getent hosts m-p1 无结果
发起容器在自定义网络，目标没接进来 getent hosts m-p1 无结果
把目标接进来之后再问 docker network connect kb-probe-net m-p1 → getent hosts m-p1 172.28.99.2 m-p1 m-p1
用名字真连一次 redis-cli -h m-p1 ping PONG

一个实验结论：容器名能不能被解析，取决于两个容器是不是在同一个用户自定义网络里，跟"它们在不在同一台机器上"无关。默认 bridge 上没有这套名字解析。

配套读数，供排查时用：

$ docker exec m-p1 cat /etc/resolv.conf
# Generated by Docker Engine.
nameserver 127.0.0.11
options ndots:0
# Based on host file: '/etc/resolv.conf' (internal resolver)
# ExtServers: [host(192.168.65.7)]

$ docker exec m-p1 ip -4 addr show eth0 | head -2
2: eth0@if5: <BROADCAST,MULTICAST,UP,LOWER_UP,M-DOWN> mtu 1500 ...
    inet 172.17.0.2/16 ...

$ docker exec m-p1 ip route | head -3
default via 172.17.0.1 dev eth0
172.17.0.0/16 dev eth0 scope link src 172.17.0.2
172.28.99.0/24 dev eth1 scope link src 172.28.99.2

💡 新人小结：默认 bridge 像一栋没有内部电话系统的公寓楼——你只知道门牌号（IP），互相叫名字没人应；用户自定义网络则是给这组容器装了一台内部交换机，登记了名字，报名字就能接通。 对应到 Docker：nameserver 127.0.0.11 是引擎内置的解析器，它只服务用户自定义网络的登记表；172.17.0.2/16 是默认 bridge 的地址，eth1 上的 172.28.99.2/24 才是接进自定义网络后拿到的、能被名字解析到的地址。所以一个容器可以同时在两个网络里，各自一个 IP。

四种内置网络模式怎么挑：

模式 什么时候用 代价
bridge（默认） 单机绝大多数场景 默认网络上没有名字解析，要用 -p 暴露、用 IP 互访
用户自定义 bridge 只要有两个以上容器互访就用它 要多建一个网络；这是本篇建议的默认选择
host 追求最少一跳、且明确知道自己在 Linux 宿主上 桌面版上它指的是那台 VM，不是你的 Windows；端口直接占用、隔离性也掉了
none 完全不需要网络，或要自己插别的网络 连回环以外都没有，需要显式 network connect 补

判据：新建容器后先问一次名字再连一次端口，两步都过才算网络配好；只看 docker ps 有 0.0.0.0:6380->6379/tcp 不算，那只能证明映射建立了，证明不了解析和连通。

数据放在哪：三种挂载与它们的落点

先看图，再看本机实测的挂载表——这张图就是"删容器会不会丢数据"的答案。

flowchart LR
    C["容器内路径"] -->|"命名卷 -v 名字:/data"| V["/dev/sdd 上的 ext4"]
    C -->|"绑定挂载 -v 宿主目录:/mnt"| B["Windows 目录，走 9p 协议"]
    C -->|"tmpfs --tmpfs /t"| M["内存，容器没了就没了"]
    C -->|"什么都不挂（写可写层）"| L["容器可写层，rm 之后一起没"]
    V --> S["数据保留，跨容器可见"]
    B --> W["文件在宿主上，用资源管理器能看到"]
    M --> X["不落盘，重启即失"]
    L --> Y["最危险的默认"]

本机同时挂三种，容器里的 mount 表把差异说得非常直白：

$ docker run -d --name m-mix -v kb-probe-vol:/data -v <Windows目录>:/mnt --tmpfs /t redis:7-alpine
$ docker exec m-mix sh -c "mount | grep -E ' /data | /mnt | /t '"
/dev/sdd on /data type ext4 (rw,relatime)
C:\ on /mnt type 9p (rw,noatime,aname=drvfs;path=C:\;uid=0;gid=0;metadata;symlinkroot=/mnt/host/,cache=0x5,access=client,msize=65536,trans=fd,rfd=5,wfd=5)
tmpfs on /t type tmpfs (rw,nosuid,nodev,noexec,relatime)

三行读法：ext4 说明命名卷的真身在 Linux 文件系统里（一个虚拟磁盘文件内部），9p 说明绑定挂载是跨协议访问 Windows 目录，tmpfs 那行带着 noexec——连在上面执行程序都不行。 三种数据的"物理位置"根本不是一回事，所以备份、性能、权限行为全都不同。

💡 新人小结：命名卷像把东西存在公司仓库——你换了工位（重建容器）货还在，取货要用仓库单号（卷名）；绑定挂载像把家里的柜子直接搬进办公室——同一批东西，两边都能伸手拿，但你家和办公室之间那条走廊（这里就是 9p）比办公室内部走动感人得多。 对应到 Docker：卷名 kb-probe-vol 对应单号，落点 /var/lib/docker/volumes/<名>/_data；绑定挂载的宿主目录与容器内 /mnt 指向同一批文件，代价是跨文件系统协议；容器可写层则像"东西塞在你座位底下"，扔椅子（docker rm）就一起扔了。

量出来的差距，以及两次假读数

同一段工作（写 300 个小文件 + dd 写一个 64 MiB 文件 + sync）分别落在绑定挂载与命名卷上，各跑三轮：

轮次 绑定挂载（Windows 目录，9p） 命名卷（ext4）
1 1082 ms 421 ms
2 1068 ms 429 ms
3 1036 ms 409 ms
中位 1068 ms 421 ms

docker run --rm alpine true 的固定开销中位是 398 ms。扣掉它：绑定挂载约 670 ms，命名卷约 23 ms，差约 29 倍。宿主侧核对确实写出了 301 个文件、big.bin 为 67108864 字节（正好 64 MiB）。

两条关于测量本身的说明，比结论更容易复发：

  1. 第一次尝试得到过"0 ms"这种不可能的数。 原因是我在容器里用 date +%s%N 取纳秒，而这个镜像的 date 是精简实现，本机直接验它的行为：date +%s%N 返回 1793072365——纳秒位被静默丢掉了，于是 (t2-t)/1000000 恒为 0。改用宿主侧墙钟差值 + 减基线才拿到真数。
  2. 基线里有一次 5613 ms 的离群值（第一轮冷启动）。所以我取中位数而不是最小值或单次读数，并把三轮原始值一起留下。

还有两个"看着像通过其实没测到东西"的坑，都是本轮现场踩的：

现象 成因 怎么防
测"删容器后数据是否留在命名卷"，但结果毫无意义 我把挂载目标路径写错了，Docker 顺手建了一个匿名卷接走真正的数据目录，容器照跑、查询照出 动手前先 docker inspect --format '{{range .Mounts}}…'，确认目标路径挂的是你以为的那个卷
docker rm -f 之后卷越积越多 镜像里有 VOLUME /data 声明，每次不带卷名起容器都会建一个匿名卷；docker rm 不清理它们，只有 --rm 会 本轮实测：一轮 -d 实验后遗留 4 个匿名卷，创建时间正好对上那四次运行，docker system df 却只报 0B（它们是空的）——所以"看大小"发现不了

💡 新人小结：docker inspect 的挂载列表像快递面单。tmpfs 这一项在面单上是查不到的——本机三个挂载（卷、绑定、tmpfs），.Mounts 只列了前两个。 对应到操作：想知道容器到底挂了几样东西，docker inspect 和容器内 mount 要都看一次；只看前者会漏掉 --tmpfs，也看不见那个不该出现的匿名卷。

权限：容器里的 root 和宿主上是谁

容器默认是谁，本机读数：

$ docker exec m-mix id
uid=0(root) gid=0(root) groups=0(root),1(bin),2(daemon),3(sys),4(adm),6(disk),10(wheel),...
$ docker exec m-mix grep -E '^(Uid|Gid)' /proc/self/status
Uid:	0	0	0	0
Gid:	0	0	0	0

Uid: 那一行四个数都是 0，说明这台机器没有开用户命名空间重映射——容器里的 root 就是引擎那侧真实 uid 0。（重映射开启后这四个数会指向一个高位段，那属于 5.8 的范围。）

改身份与写文件的组合结果，是这节最有用的表：

怎么起 容器内身份 写绑定挂载 写完后容器里 stat -c '%u:%g'
默认 uid=0(root) 成功 0:0
--user 1000:1000 uid=1000 gid=1000(redis) 也成功 1000:1000
--user 1000:1000 写命名卷里的非本人目录 见下方说明 未测 未测

第二行值得停一下：Windows 上的绑定挂载是非 root 也能写。原因就在上面那条 mount 里——9p 挂载带了 uid=0;gid=0;metadata，权限判定方式与原生 Linux 文件系统不同。这在开发期"帮了你"（不会因为属主卡住），但它会让人养成在 Linux 生产上也这么写的习惯，那里就没有这个宽容度了。所以本篇给的规矩是：别把 Windows 上验证过的属主行为当成可移植的结论。

命名卷里的属主也有一个真实读数，注意它和上面那条不是一回事：

$ docker run --rm -v kb-own:/data redis:7-alpine sh -c 'echo probe > /data/m.txt; stat -c "%u:%g %A %n" /data /data/m.txt'
999:1000 drwxr-xr-x /data
0:0      -rw-------  /data/m.txt

/data 这个目录本身属于 999:1000，因为卷第一次被创建时按镜像里 /data 的属主初始化（镜像里有 redis:x:999:1000::/home/redis:/sbin/nologin）。而 root 写进去的文件就是 0:0。这条读数我用两个独立容器复现过两次。换镜像时目录属主跟着镜像走，这就是"应用换了非 root 用户之后突然写不进老卷"的常见成因。

💡 新人小结：属主像小区门禁卡的登记名字。卡（文件）本身没变，但你换了一个人刷卡（换 --user 或换镜像里的用户），物业按登记名决定让不让进；而卷目录的登记名在建卷那一刻就按"当初那把卡"写死了，后来换了人也不自动改。 对应到 Docker：卷的目录属主来自镜像首次初始化，不随你之后传的 --user 变；要么建卷/首次运行时就把属主设对，要么在编排里显式指定运行用户并保证目录属主匹配。

时区与中文：三处口径别搞混

位置 本机读数 结论
容器默认 Tue Oct 27 03:34:28 UTC 2026，TZ 未设 容器是 UTC
只设 -e TZ=Asia/Shanghai Tue Oct 27 11:34:28 CST 2026，date +%z 给 +0800 一个环境变量就改显示口径，不改存储的时间点
挂载 /etc/localtime:ro 再 date 仍然 03:34:29 UTC 在桌面版上这招没用——你挂进来的是那台 Linux 虚拟机的时区文件，它本来就是 UTC
宿主同一时刻 2026-10-27T11:34:29+0800 与容器那一行相差 8 小时的是显示，不是时刻
引擎日志 2026-10-27T03:34:23.808Z 1:C 27 Oct 2026 03:34:23.808 * Redis is starting 一行里两个时间戳都是 UTC：前者是引擎加的时间戳，后者是应用自己打的

日志时间排查的判据：先看有没有 Z。带 Z 是 UTC，要换算才能和宿主时间对齐；不带 Z 的时间戳取决于应用内 TZ。设 TZ 只影响应用自己打印的那一段，引擎加的时间戳永远是 UTC。

中文的问题更朴素，也更常踩：同一个终端里可能混着三种编码。本轮在同一条命令链里就同时撞到过：

来源 输出编码 直接按 UTF-8 读会看到什么
where docker 等 Windows 自带命令 GBK 一类本地代码页 一句本来说明"没找到"的话，变成一串乱码字节
wsl.exe UTF-16LE 连长度都不对，看起来像垃圾数据
docker 与 alpine 里的命令 UTF-8 正常

判据：先确认解码方式，再判断"是不是坏了"。乱码出现在读的那一端，不是容器里写坏了。

镜像本身可能根本没有 locale 数据，这点也量了：

$ docker run --rm redis:7-alpine sh -c "locale | head -1; ls /usr/share/locale | head -1; printf '中文'"
sh: locale: not found
ls: /usr/share/locale: No such file or directory
中文

第三行才是重点：没有 locale 工具、没有语言包，UTF-8 的中文照样正确输出。 所以在精简镜像上，“中文乱码"极少是镜像缺语言包，绝大多数是宿主终端的解码或数据在写入前就被转错了编码。

实战切入：把示例链第①段真跑一遍

这一段就是第①段本体，全部命令本机跑通，读数照抄。要的东西：一个 MySQL、一个 Redis、两个命名卷，以及"删容器之后数据还在”。

要点总结

  • 端口映射只发生在外面：容器内监听表上永远是自己的端口（本机读到十六进制 18EB = 6379）。-p 冒号左边是宿主、右边是容器，冲突永远报在左边那个号上。
  • 只有用户自定义网络才有容器名解析（默认 bridge 上 getent 无结果，network connect 之后立刻解析到 172.28.99.2 并拿到 PONG）。两个以上容器互访就建一个自定义网络。
  • 三种挂载的落点各不相同：命名卷在 ext4 上、绑定挂载走 9p、tmpfs 在内存（还带 noexec）。Windows 上做绑定挂载的实测代价约 29 倍（净 670 ms 对 23 ms）。
  • 数据要活过容器重建就放命名卷，并且每次确认挂的是哪个卷：路径写错时 Docker 会静默建匿名卷；docker rm 不清理匿名卷，只有 --rm 会。
  • 属主三件事要分开：容器默认 root、--user 换身份、卷目录的初始属主跟着镜像。Windows 绑定挂载因为 9p 挂载参数而对非 root 写入异常宽容，这不是可移植结论。
  • 容器默认 UTC，TZ 只改应用自己打印的时间；引擎加的时间戳永远是 UTC。挂载 /etc/localtime 在桌面版上不改变事实。
  • 乱码先怀疑解码端：同一屏可能混着 GBK、UTF-16LE、UTF-8 三种编码，而精简镜像没有 locale 工具也能正确输出 UTF-8 中文。
  • 本篇两次"看着通过其实没测到"的经历本身就是判据：验留存前先确认卷，读空值前先确认读法。

💡 新人小结：docker run 是「每次开工前手动按十二个按钮」，compose.yaml 是「把工序单贴在机器上」。按钮按错顺序，机器不启动但也不会告诉你为什么；工序单交给机器之后，机器自己按顺序按，而且每次开工前先对比「现在是不是已经按到位了」。类比之后接机制：工序单就是那份 YAML 描述的期望模型，按钮顺序是它的依赖图，对比动作是 up 的 diff——所以下面所有语法问题都可以还原成一句：「模型里这个字段声明的是什么，实际对象现在是什么」。

语法基线：三个名字、两种调用、一条已废弃字段

先把容易混的三个名词钉住：

名词 是什么 本机读数
compose-spec 文件格式的规范（一套 YAML 字段的定义与合并语义），语言无关 下面所有「字段能不能写、写错报什么」的行为都来自它的校验器
Docker Compose v2（docker compose） 规范的 Go 实现，作为 Docker CLI 插件 Docker Compose version v5.5.1
docker-compose（连字符） 老的 Python 实现的名字；现在这台机器上它指的是同一个 v2 实现 where docker-compose 指到 Docker Desktop 的 resources\bin\docker-compose.exe，docker-compose version 报的仍是 Docker Compose version v5.5.1

这条读数很重要，因为它否定了一种常见的「新旧判断法」：不要看到 docker-compose 这个写法就断定对方在用 v1——在同一台机器上这两个名字可能指向同一个二进制。要判断实现与版本，只看 version 输出的字符串。

version: 顶层字段的现状是本机实测的：

$ docker compose config --quiet           # 文件第一行写的是 version: "3.8"
[rc=0]
level=warning msg="…\compose.yaml: the attribute `version` is obsolete,
it will be ignored, please remove it to avoid potential confusion"

不报错，只警告，并且明确说「会被忽略」。所以旧教程里那行 version: '3.7' 拷过来照样能跑，但它已经不再选择任何语法版本——字段校验用的是当前实现自带的那一份 schema。这就是为什么「按 version 行判断这段配置属于哪个年代」这件事已经失效。

💡 新人小结：顶层那行 version: "3.8" 现在像老地图上印的「1998 年测量」——地图你照样能看，但那行字已经不决定地图画的是什么了；真正决定内容的是你手上这一版地图本身。类比之后接机制：决定「哪些字段合法」的是这台机器上 Compose 实现自带的那份 schema，config 只会告诉你「这一行我忽略了」，不会替你切回 3.8 的语义。所以判断一段配置新旧，要看字段级信号（有没有 links、volumes_from、test: [] 这类），不是那行印章。

团队语法基线一句话结论（这条要在 7.11 团队规范里落地成唯一事实来源，其它章节只链接不复述）：

统一用 docker compose（v2 实现）；文件名统一 compose.yaml，开发期覆盖写 compose.override.yaml；不写顶层 version:；顶层显式写 name:；口令一类的值一律走 .env 或注入，不进文件。

说明

为什么必须写 name:：项目名会进容器名、网络名、卷名。Compose 用「第一个指定文件所在目录的基本名」当默认项目名，并把非法字符过滤掉。本机实测：把同样的文件放进一个中文命名的目录，config 直接失败——

$ docker compose config --quiet      # 目录名是中文，文件里没有 name:
[rc=1] project name must not be empty

$ docker compose config --quiet      # 内容一字不改，只把目录换成 ASCII 名
[rc=0]

这条不是抽象风险：团队的仓库路径里出现「文档」「项目」这类中文目录名是常态，而报错文本 project name must not be empty 完全不提示「是目录名导致的」，新人会去查 YAML 语法。

一个 compose.yaml 分几层 

flowchart TD
    TOP["顶层"] --> N["name：项目名，进所有对象名"]
    TOP --> SVC["services：唯一必须有内容的一层"]
    TOP --> NET["networks：网络定义"]
    TOP --> VOL["volumes：命名卷定义"]
    TOP --> CS["configs / secrets：文件类注入"]
    TOP --> INC["include：把别处的 compose 文件并进来"]
    TOP --> EXT["x- 前缀键：自定义扩展，不参与语义"]
    SVC --> S1["镜像与构建：image / build"]
    SVC --> S2["运行内容：command / entrypoint / environment / working_dir / user"]
    SVC --> S3["互通：ports / networks / extra_hosts / hostname / dns"]
    SVC --> S4["数据：volumes / tmpfs"]
    SVC --> S5["生命周期：restart / healthcheck / depends_on / stop_grace_period"]
    SVC --> S6["资源与安全：deploy / cap_add / security_opt / sysctls / read_only"]
    SVC --> S7["开发与协作：profiles / develop.watch / labels / extends"]

x- 前缀与 include 是本机能确认「确实支持」的两条：

# 顶层写 x-团队约定: &team {labels: {team: platform}}，服务里用 <<: *team
[rc=0]  services.a.labels = {"team": "platform"}
        config --format json 的顶层键 = ['name', 'networks', 'services', 'x-团队约定']

顶层键里 x-团队约定 被保留下来，说明它是「合法但不参与语义」的容器；YAML 锚点（&team / *team / <<:）也照常生效。这两条组合起来就是团队里最常用的复用手法：用 x- 放一份「约定」，服务用锚点合并它（比如统一的 labels、restart、日志驱动）。

另外两条同样跑通的复用手段，语义差别要说清：

# extends：从同目录另一个文件里的服务继承
[rc=0]  web = {"environment":{"EXTRA":"1","FROM":"override"},"image":"nginx:1.27-alpine", …}

# include：另一个文件整个并进当前项目
[rc=0]  config --services → inc-a main

extends 是服务级继承（继承来的字段与本地字段按同一套合并规则叠，上例里 FROM 被本地值 override 覆盖、EXTRA 新增、image 继承）；include 是文件级并入（那个文件里的服务、网络、卷都进当前模型）。选哪个的判断标准是「要不要改一部分」：要改就用 extends，只是拆分文件就用 include。

顶层四个键：networks / volumes / configs / secrets

config --format json 是看清楚这一层的唯一办法，因为规范化会改你的名字：

$ docker compose --profile app config --format json   # 节选
  顶层 name    = kb-p2
  networks     = {"default": {"name": "kb-p2-net", "ipam": {}}}
  volumes      = {"cachedata": {"name": "kb-p2_cachedata"}, "dbdata": {"name": "kb-p2_dbdata"}}
键 作用 必须知道的落点
networks 定义网络；default 不写就自动建 本项目显式命名成 kb-p2-net，所以 docker network ls 里查得到它，不受前缀规则影响
volumes 定义命名卷 不写 name: 时自动加项目前缀：声明是 dbdata，实际叫 kb-p2_dbdata。手工 docker volume rm 按前缀名找
configs 注入配置文件（文本类） 本轮未用；services.*.configs 引用未声明的 config 会像 secret 一样在加载期失败
secrets 注入敏感文件 未跑通用法，只跑到「引用未声明」的报错文本；生产写法归 6.3

前缀这条规则的副作用很实在：同一个 compose.yaml 换 -p 或换目录名，会得到另一套卷。这就是「换了个项目名，数据库怎么变空了」的机制解释（症状索引里值得单列）。要绑死就用 name:（卷/网络各自也能写 name:）。

哪些写错法会被拦住：config 的边界

docker compose config --quiet 是校验器（--quiet 只报问题不打印模型）。它的报错形状本机逐条量过，这张表的价值在于它会给你「原来这条不拦」的反例：

写法 config 报错原文（截取） 何时才暴露
服务里多一个 typo_field: x rc=1 validating <路径>: services.s additional properties 'typo_field' not allowed 加载期
顶层多一个 random_top: 1 rc=1 validating <路径>: additional properties 'random_top' not allowed 加载期
ports: ["99999-80"] rc=1 invalid containerPort: 99999-80 加载期
depends_on: [ghost]（服务不存在） rc=1 service "s" depends on undefined service "ghost": invalid compose project 加载期
a→b→a 循环依赖 rc=1 dependency cycle detected: a -> b -> a 加载期（--dry-run 同样报）
secrets: [pw] 未声明 rc=1 service "s" refers to undefined secret pw: invalid compose project 加载期
目录名非 ASCII 且无 name: rc=1 project name must not be empty 加载期
顶层 version: "3.8" rc=0 warning：the attribute version is obsolete, it will be ignored… 不暴露（被忽略）
restart: maybe rc=0 — 运行时，daemon 拒绝并列出合法值
healthcheck.test: [] rc=0 — 不报错，但等于「没有健康检查」；下游 service_healthy 会永远不满足
volumes: ["/tmp/x"] rc=0 — 合法（匿名卷），不是错误
docker compose volume ls rc=1 一整段用法帮助 命令名写错（正确是 volumes）

两条推论，是团队里最该教的：

  • 「未知字段」会拦，「值不合法」不一定拦。restart: maybe 这种拼进模型的错误值要等到容器创建才由 daemon 拒。所以 config --quiet 通过 ≠ 能 up。
  • 「不报错」不等于「按你想要的方式生效」。test: [] 静默地让健康检查消失，version: 静默地被忽略。想确认语义，只有一条路：config --format json 看规范化后的模型。

config 本身也有几个能救命（或救 CI）的选项，读自 config --help：--format yaml|json、--images、--networks、--models、--hash（打印每个服务的配置哈希，判断「这个服务会不会被重建」的直接依据）、--environment（打印插值用的环境）、--no-consistency、--lock-image-digests（生成一份把镜像钉到 digest 的覆盖文件）。--paths 这一项本机不存在（unknown flag: --paths），网上有人用它当字段清单的写法已经过时。

💡 新人小结：config 像「把口语需求整理成正式工单」的那道程序——你说的是「大概这样」，工单上必须写死编号、负责人、时长，而且工单一旦生成，后面执行只看工单不看你的原话。类比之后接机制：YAML 里的 dbdata 变成 kb-p2_dbdata、depends_on: [db] 变成 {condition: service_started, required: true}、128m 变成 134217728，都是这道「整理」的产物。所以「我的文件里明明写了 X」永远不是证据，config 输出才是。

实战切入：三条判据，十分钟内把基线钉死

这三条不是阅读练习，每条都有可核对的输出。

判据一：确认你机器上这两个名字是不是同一个实现。

$ docker compose version
Docker Compose version v5.5.1
$ docker-compose version
Docker Compose version v5.5.1

预期：两行字符串一致。不一致的话（本机以外完全可能，比如另装了 v1 的独立包）先把 PATH 里谁赢查清楚再讨论语法。

判据二：把「写错法」跑一遍，确认你的校验器会拦哪一种。

name: kbprobe
services:
  s:
    image: busybox:1.37
    restart: maybe
    typo_field: x
$ docker compose config --quiet        # 期望 rc=1，只报 additional properties
$ # 把 typo_field 删掉再跑一次
$ docker compose config --quiet        # 期望 rc=0（version/restart 这类不拦）
$ docker compose up -d                 # 期望 rc=1，daemon 拒绝 restart policy
$ docker compose down

这条的价值是让新人亲自看到「config 绿了但起不来」。这是本篇最容易被忽略的一条判据：只跑第一条的人，会以为校验器什么都管。

判据三：config --format json 里找到三个「被改过的名字」。

对照自己的项目文件，逐条回答：卷的实际名字有没有项目前缀？depends_on 被展开成什么 condition？映射类资源名（网络）是什么？

$ docker compose --profile app config --format json | python -c "import json,sys; d=json.load(sys.stdin); print(d['name']); print(list(d['volumes'].values())); print(list(d['services']['api']['depends_on'].items()))"

本机读数：kb-p2、[{'name': 'kb-p2_cachedata'}, {'name': 'kb-p2_dbdata'}]、[('cache', {'condition': 'service_healthy', 'required': True}), ('db', {…})]。

常见误读

误读 实际
「写了 version: '3.8' 就锁定了语法版本」 现在这行会被忽略并警告；schema 由实现决定
「docker-compose 这个写法就说明对方在用 v1」 本机两个名字指向同一个 v2 实现，版本串一致。判断要看 version 输出
「config --quiet 通过就能 up」 restart: maybe 这条实测：config rc=0，up rc=1
「不报错就说明我写的字段生效了」 healthcheck.test: []、version: 都是「不报错但改变语义」的例子
「声明的卷名就是磁盘上的卷名」 不写 name: 时实际名带项目前缀（dbdata → kb-p2_dbdata）
「environment 写成 list 和写成 map 完全一样」 本轮全程用 map 写法，config 出来是 map；list 写法的规范化未跑，别当已验证
「x- 开头的键会被 Docker 解析」 它被保留在模型里但不参与语义，是给人看的约定
「目录名不影响项目」 中文目录名会让默认项目名被过滤成空，直接 project name must not be empty
「include 和 extends 是一回事」 前者文件级并入、后者服务级继承，合并规则不同（上文的 FROM: override 是证据）

要点总结

  • Compose 的价值不是「少打字」，而是把顺序、命名、重放三件事从人脑转移到模型：up 做的是 diff 后的收敛，本机表现为只重建那一个端口变了的 proxy。
  • 基线一句话：docker compose（v2，本机 v5.5.1）+ 文件名 compose.yaml + 开发覆盖 compose.override.yaml + 不写 version: + 必写顶层 name: + 口令走 .env 注入。
  • version: 现在只给 warning 并被忽略；docker-compose 这个命令名在本机与 docker compose 是同一实现——辨识旧教程要靠字段级信号（links、volumes_from、network_mode: default），不能靠这两条。
  • 顶层结构是 name / services / networks / volumes / configs / secrets / include / x-*；x-* 与 YAML 锚点、extends、include 四种复用手法本机都跑通。
  • 名字会被规范化：卷加项目前缀、depends_on 展开成 condition、128m 变字节。证据永远是 config --format json，不是源文件。
  • 校验器只拦「未知字段/引用不存在/名字非法」这一类；「值不合法」（restart: maybe）留给运行时，「静默改变语义」（test: []、version:）谁都不提醒。
  • .env 缺失时 ${VAR:?文案} 会硬失败并把文案打进报错；普通 ${VAR} 只警告并按空串继续。

为什么要先把命令分成四组，而不是背 docker compose 的参数表

一次真实的值班对话（场景是本地栈，不是生产，但错法一模一样）：

「服务起不来，我 down 一下再 up。」
「等一下，你 down 有没有带 -v？」
「没有吧……带了会怎样？」
「数据没了。」
「那我改成 stop 再 start，总安全。」
「安全，但你刚才改了配置，stop/start 不会重建容器，改动不生效。」
「那 up 呢？up 会不会把我的库刷一遍？」
「不会，up 只做 diff。但它会不会重建，取决于配置有没有变——这个要会自己判断。」
「还有：它起不来到底是依赖没就绪，还是镜像构建失败？」
「看 ps 和 logs，别看心情。」

docker compose 有 30 个子命令，但新人真正需要的是先分清真意图：看现场、改状态、动数据、动镜像。这四组的后果等级不同，混用的代价就是上面那段对话。本篇把每一组里最常用、也最容易按错的那几条量清楚——每条都给本机读数，没跑过的会明确标出来。

💡 新人小结：把 compose 想成「你对系统说的一句话」，而不是「一个终端里的按钮」。ps/logs/top 是问，up/stop/restart 是要求改动，down 是拆，down -v 是拆完再倒垃圾，build/pull/push 是搬货。类比之后接机制：up 是幂等的「把实际状态收敛到文件声明的状态」，它自己决定要不要重建；stop/start 只动运行时状态，不重新计算配置差异——这就是「改了配置但 stop/start 不生效」的原因，下面第 4 节的表用端口读数把这条钉住。

up 的三个档位：改动什么时候才生效

用「.env 里把 PROXY_PORT 从 8080 改成 8085」这一件事当探针，同一个改动跑三种命令。判据不是「有没有报错」，而是 docker inspect 里的实际端口映射：

命令 proxy 的宿主端口 Created 时间戳 curl 8085
up -d --no-recreate（改了 .env 之后） 8080 不变 与改动前同一个 http=000（连不上）
up -d（同一改动） 8085 变新（日志里只有 proxy 出现 Recreate/Recreated） http=200
up -d --wait --force-recreate 8080（已还原 .env） 五个容器全部变新 —

三条读数说明三件事：

  • --no-recreate 是「只补缺，不改已有的」。配置真的变了也不动现有容器，同时它仍然会跑健康等待（日志里出现 Waiting/Healthy）。用它来「避免重启我的长任务」是对的，但它不会告诉你「因此你的改动没生效」。
  • 默认 up 做逐服务 diff。只有 proxy 被重建，其余四个 Running 不动——这就是「改一个服务不要把整栈刷一遍」的机制依据，不是玄学。
  • --force-recreate 是「不管 diff 全部重建」，代价实测：本机五个容器 up -d --wait --force-recreate 用时 18.2 秒，且重建严格按依赖顺序落地（db/cache 的 StartedAt 最早，api 晚 5.7 秒，proxy 最晚）。

up 的其它常用档位（读自 up --help，本轮未全部实测）：--build（起之前先构建）、--abort-on-container-exit（任一容器停止就停全部，与 -d 互斥）、--exit-code-from <服务>（把某个容器的退出码当命令退出码，隐含前者）、--abort-on-container-failure（只在失败退出时停）、--always-recreate-deps（连带重建依赖，与 --no-recreate 互斥）、--attach / --attach-dependencies（控制日志跟着打哪些服务）。

警告

up 的退出码不等于「全栈可用」。带 --wait 时它等的是健康检查；不带 --wait 时它只要容器创建成功就可能返回 0。反过来，--wait 报 rc=1 也不一定是指令写坏了——下面「假绿」那节给了一条相反的例子。

down 家族：-v、profile、--rmi 各自删了什么

down 的四个开关是正交的，混起来记就会出事。本机读数是：

写法 容器 网络 卷 读数摘要
down（不带 --profile） 只删模型里有的 db/cache 删不掉 保留 用时 2.0 秒；docker ps 里 api/web/proxy 三个还在跑；日志出现 Network kb-p2-net Resource is still in use

💡 新人小结：down 是退租，-v 是把家具扔掉，--rmi 是把搬家用的卡车也卖了，--remove-orphans 是「把这套房里所有还在住的人都请出去，不管合同上写没写名字」。类比之后接机制：--remove-orphans 的依据是容器上的 com.docker.compose.project 标签，而 profile 只影响「本次命令的服务模型」，两者不是一回事——这就是「不带 profile 的 down 会漏容器，而带 --remove-orphans 就能收干净」的原因。

docker compose ls 是「这个 compose 项目现在被认为在跑什么」的账本，删干净之后它是空的：

$ docker compose ls
 NAME                STATUS              CONFIG FILES
 kb-p2   running(5)  ...\compose.yaml,...\compose.override.yaml

running(5) 这个数还会告诉你 override 是否被自动合并（配置文件列了两个）。清理核对用的就是它。

空项目上的静默成功：判据要先检查前提

一组反面读数。项目里只有一个服务、但从未 up 过，逐条命令的结果：

空项目 ps             rc=0  out='NAME      IMAGE     COMMAND   SERVICE   CREATED   STATUS    PORTS'
空项目 logs s         rc=0  out=''
空项目 stop           rc=0  out=''
空项目 restart s      rc=0  out=''
空项目 down           rc=0  out=''

五条全部 rc=0。也就是说：「命令跑成功」在 compose 里几乎不提供信息量，因为「没东西可操作」也是成功。脚本里写 if docker compose ps; then echo OK，会得到一个永远为真的分支。

对比之下，两类错误才是真的会红：

$ docker compose logs --tail 1 nope
[rc=1] no such service: nope

$ docker compose volume ls
[rc=1] Usage:  docker compose [OPTIONS] COMMAND …

判据要写成「检查前置状态」而不是「检查命令返回值」。同一批取数里可用的两条硬判据是：docker compose ps -a --format "{{.Status}}" 的每一行都必须含 healthy 才算就绪；up --wait 之前先 config --services 确认服务数量符合预期。

启动顺序：三种依赖条件与它们的失败形状

depends_on 有两种书写形态，语义差别全在「等多久」。

列表形态（很多人以为它「等就绪」）：

depends_on: [db, cache]

config 把它规范化成下面这样——这是理解全部后续现象的钥匙：

"depends_on": {
  "cache": {"condition": "service_started", "required": true},
  "db":    {"condition": "service_started", "required": true}
}

service_started 只看容器进程起没起，不看服务能不能干活。本机把应用改成「依赖没就绪就主动退出」的样子（STRICT=1），跑出来的失败形状是：

$ docker compose -f compose.yaml -f compose.badstart.yaml --profile app up -d
[rc=1] 用时 1.5 秒
 Container kb-p2-api-1 Started
 Container kb-p2-api-1 Waiting
 Container kb-p2-api-1 Error dependency api failed to start
dependency failed to start: container kb-p2-api-1 exited (1)

$ docker compose logs --timestamps api
api-1  | 2026-10-27T03:57:41.947697228Z 依赖未就绪，按 STRICT=1 退出： dial tcp 172.18.0.3:3306: connect: connection refused

那行日志是本篇最重要的一条读数：172.18.0.3 说明服务名已经解析到 IP 了（DNS 是通的），connection refused 说明 MySQL 还没开始监听。service_started 给的正是「容器起了但端口没开」这个中间态。

健康门形态（本篇示例用的就是这个）：

depends_on:
  db: { condition: service_healthy }
  cache: { condition: service_healthy }

up 会等 db 的 mysqladmin ping 第一次成功再起 api。健康检查细节见下一节，这里关心顺序证据本身。

一次性任务形态（做迁移脚本用的）：

depends_on:
  init: { condition: service_completed_successfully }

本机跑出来 init 先 Exited、app 才 Started，up 返回 0，app 确实读到了 init 写进共享卷的文件：

 Container kbinit-init-1 Started
 Container kbinit-init-1 Waiting
 Container kbinit-init-1 Exited
 Container kbinit-app-1 Starting
 Container kbinit-app-1 Started

再加一个可选依赖的写法，失败也不挡路：

depends_on:
  opt: { condition: service_completed_successfully, required: false }
 Container kbreq-opt-1 Skipped: optional dependency "opt" didn't complete successfully: exit 3
time="…" level=warning msg="optional dependency \"opt\" didn't complete successfully: exit 3"
 Container kbreq-main-1 Starting
 Container kbreq-main-1 Started

rc=0，但有一行 warning。required: false 是把「依赖失败」降级成「警告」，用在「有更好、没有也能跑」的东西上（比如埋点、可选缓存）。用它就必须同时把 warning 打到人眼里，否则静默降级会变成第二天才发现的问题。

三种条件的取舍：

💡 新人小结：service_started 像「人已经坐到工位上了」，service_healthy 像「人坐在工位上并且能接电话」，service_completed_successfully 像「开班前那次晨会必须开完，店才开始接客」。类比之后接机制：Docker 只知道「容器进程在不在」，「能不能接电话」必须有人去问——那个「问」就是 healthcheck.test 里的探测命令；问不出来（探测失败）时，compose 有的参数（condition）会拒绝放行下游，有的参数（required: false）只留一行警告。所以「等不等得到」不是 compose 聪明，是你写的探测命令真的能区分就绪与未就绪。

方案 什么时候用 优点 代价 本轮证据
service_healthy + 健康检查 依赖会「起了但没就绪」（数据库、缓存） 顺序由工具保证，应用代码不用改 每个依赖都要写对探测命令，start_period 要给够；启动时间变长 冷启动 18.4 秒里等健康占了大头
service_started（裸列表） 依赖是「进程在就是可用」（静态站点） 起得快 对数据库类依赖就是错误的期望 反面实验：connection refused
应用侧自己重试/重连 生产更常用；或依赖不该阻塞启动 与编排解耦，恢复能力最强 要写代码，且必须有连接超时（否则卡死） 实测：停 db → api 仍 healthy 且 StartedAt 不变，{"db":"DOWN"}；起回 db → 5 秒内 {"db":"UP"}，全程没重启 api
service_completed_successfully 迁移/初始化脚本 表达「必须先跑完一件事」 一次性容器要自己退出，restart 策略别写 always 上面 kbinit 的读数

同一个坏配置，第一次红、第二次绿

这是本轮最值得记住的一条。反面配置（STRICT=1 + 裸 depends_on）第一次 up 失败之后，什么都不改再跑一次并加 --wait：

$ docker compose -f compose.yaml -f compose.badstart.yaml --profile app up -d --wait
[rc=0]
 Container kb-p2-api-1 Started
 Container kb-p2-api-1 Waiting
 Container kb-p2-api-1 Healthy
 Container kb-p2-proxy-1 Starting
 Container kb-p2-proxy-1 Started

rc=0，全绿。但配置仍然是错的：第二次跑时 db 容器已经在上一轮失败里起了、并且已经初始化完（MySQL 首次探测通过要 8.6 秒，见下一节），api 起来时端口自然就通。service_started 的语义没变，变的是运气。

所以：验证一个「顺序类修复」是否真的有效，要先 down 到干净状态（保留卷可以，但所有容器都要重建），否则你测的是热缓存。第②段判据里那条「冷启动 18.4 秒 vs 热启动 7.1 秒」的差值，正好就是这个陷阱的量。

健康检查：两种写法、优先级与参数怎么定

写在哪里有两处，行为不同。本机用一个镜像自带 HEALTHCHECK、compose 又写了一份的服务量了优先级：

HEALTHCHECK --interval=7s CMD ["/bin/dockercmd"]
    healthcheck:
      test: ["CMD", "/bin/dockercmd", "--from-compose"]
      interval: 3s

运行时生效的是 compose 那份：

$ docker inspect --format "{{json .Config.Healthcheck.Test}} | {{json .Config.Healthcheck.Interval}} | {{.State.Health.Status}}" kbhcp-s-1
["CMD","/bin/dockercmd","--from-compose"] | 3000000000 | healthy

$ docker image inspect --format "{{json .Config.Healthcheck}}" kbhcp-s
{"Test":["CMD","/bin/dockercmd"],"Interval":7000000000}

镜像里那份 7 秒的 HEALTHCHECK 仍然存在，只是被容器配置覆盖。三条边界要记住：

写法 结果 读数
compose 写完整 healthcheck 覆盖镜像的 上面那组
compose 不写 用镜像自带的 adminer:4 我没写健康检查，up --wait 里它是 Healthy
healthcheck: {disable: true} 彻底关掉 inspect 得到 {"Test":["NONE"]}，.State.Health 是 null
healthcheck: {test: []} 不是「永远失败」，是「没有检查」 config 出来 healthcheck={}，inspect 的 .Config.Healthcheck={}、.State.Health=null；ps 的 Health 列是空

第四行容易读错：test: [] 不报错、也不会让 --wait 失败，它只是让这一格变成「没有健康检查」。于是 depends_on: {condition: service_healthy} 会直接失败（没有检查就永远不可能 healthy），这是 7.2 里值得单列的一条症状。

start_period / interval / retries 怎么定

不要拍数字，量一次时间线。本机用一个不设 start_period 的 MySQL，interval: 2s，每 0.5 秒轮询一次 docker inspect 得到：

相对时刻 Health.Status / FailingStreak
0.4 秒 starting / 0
2.6 秒 starting / 1
4.8 秒 starting / 2
7.0 秒 starting / 3
8.6 秒 healthy / 0

失败探测的输出长这样（inspect .State.Health.Log 的最后一条 ExitCode 已经是 0）：

error: 'Can't connect to MySQL server on '127.0.0.1:3306' (111)'
Check that mysqld is running on 127.0.0.1 and that the port is 3306.

于是三条参数规则是实测推出来的，不是抄的：

  • retries × interval 必须大于「冷启动到真的能服务」的时间，否则容器会被判 unhealthy。本机 MySQL 空库初始化到第一次 ping 通约 8.6 秒；示例里给的是 interval: 5s, retries: 20 = 100 秒预算，够容纳带数据的恢复。
  • start_period 的用途是「这段时间内失败不计入 retries」。示例给 MySQL start_period: 20s，是 8.6 秒的两倍余量；给 api 的是 5s，因为它只是起一个 Go 进程（本机实测起监听在 1 秒内）。
  • timeout 要小于 interval，否则探测会叠加。示例是 timeout: 3s / interval: 5s。

永远失败的探测会怎样？本机用 test: ["CMD", "false"]、interval: 2s、retries: 3 量到：

$ docker compose up -d --wait
[rc=1]
 Container kbbad-s-1 Started
 Container kbbad-s-1 Waiting
container kbbad-s-1 is unhealthy

$ docker inspect --format "{{.State.Status}} | {{json .State.Health}}" kbbad-s-1
running | {"Status":"unhealthy","FailingStreak":3,"Log":[ … 三条 ExitCode:1 … ]}

三个信息点：容器一直是 running（健康检查不会杀容器）、--wait 会失败并给出 container <name> is unhealthy、Health.Log 里保留最近三次探测的 ExitCode 与输出——排错时这是最短路径。杀容器是 autoheal 或编排系统的事，Docker 本身不做。

别把口令写进健康检查命令

mysqladmin ping -p${PW} 这种写法会被 compose 在加载阶段插值成明文，然后跟着容器配置走。本机对照量了两种写法：

写法 config 输出里的 healthcheck.test 含明文？ docker inspect 里含明文？
-p${PW} … -uroot -psecret-in-env 是 是
-p$$MYSQL_ROOT_PASSWORD … -uroot -p$$MYSQL_ROOT_PASSWORD 否 是（.Config.Env 里那条 MYSQL_ROOT_PASSWORD=secret-in-env 还是明文）
运行时容器里的实际命令 — — 转义写法是 -p$MYSQL_ROOT_PASSWORD，由容器内 shell 展开

结论要精确：$$ 转义只把明文从 config 输出（CI 日志、docker compose config 存档）里拿掉，挡不住 docker inspect。两种写法容器都能正常 healthy（本机各 11 秒）。真要不外泄，得让口令别出现在容器配置里——那是 6.3（secrets 与配置注入）的事，本篇只给判据：docker inspect --format "{{json .Config.Healthcheck}}" 与 {{json .Config.Env}} 两条命令都要跑，只看前者会漏。

这是「起两个 api 会不会把依赖链搞坏」的实测。docker compose --profile app up -d --scale api=2：

常见误读

误读 实际
「rc=0 说明服务可用」 空项目上 ps/logs/stop/down 全 rc=0。可用要由 --wait + 健康检查 + 一次真实请求三件事共同保证
「depends_on 会等数据库就绪」 列表形态等于 service_started，等的是「进程起了」。日志里那句 connection refused 就是证据
「健康检查失败容器会被杀掉」 unhealthy 只是状态标签，容器仍 running；杀掉要外部机制
「test: [] 是让检查永远失败」 它是「没有检查」，Health 列为空，并且会让依赖它的 service_healthy 永远不满足
「stop 之后 start 会应用配置改动」 不重建容器就不重算配置。要改动生效用 up -d（逐服务 diff）或 --force-recreate
「--no-recreate 是安全模式」 它只是不重建，不告诉你「因此改动没生效」
「-v 是更彻底的清理」 -v 删 named volume，即数据。它的回执可能就是那条 ERROR 1146
「Dockerfile 里的 HEALTHCHECK 优先」 compose 写就覆盖镜像写；compose 不写才用镜像的
「$$ 转义能防口令泄漏」 只防住 config 输出与日志落盘，docker inspect 的 Env 仍然明文
「第二次 up 绿了就是修好了」 本轮同一条坏配置第二次全绿，因为依赖已经热了。验证顺序修复要从干净状态起

要点总结

  • 30 个子命令先分四组：看现场（ps/logs/top/images/config）、改状态（up/stop/start/restart/exec/watch）、动数据（down/volumes）、动镜像（build/pull）。后果等级不同，别混着记。
  • up 做逐服务 diff：改 .env 端口只有 proxy 被重建；--no-recreate 让改动不生效但照样报 0；--force-recreate 本机 18.2 秒重建五容器并按依赖顺序落地。
  • down 的三个开关正交：profile 决定作用范围、-v 删数据、--remove-orphans 按标签兜底。不带 profile 的 down 本机实测漏掉三个容器且网络删不掉（Resource is still in use）。
  • 顺序控制的真相在 config 的规范化输出里：列表 = service_started，condition: service_healthy = 等探测通过，service_completed_successfully = 等一次性容器成功退出，required: false = 降级成警告。
  • 反面实验给出两条：service_started 下应用会撞到 connection refused；同一条坏配置第二次 up --wait 全绿，说明顺序类验证必须从干净状态起。
  • 健康检查：compose 覆盖镜像；disable: true → {"Test":["NONE"]}；test: [] → 没有检查；探测失败只标 unhealthy 不杀容器；retries × interval 要大于冷启动时间，本机 MySQL 的实测是 8.6 秒首次通过（3 次失败探测）。
  • 口令写进 healthcheck 会同时进 config 输出和容器配置；$$ 转义只解决前者。查泄漏要 Config.Healthcheck 与 Config.Env 两条 inspect 都跑。
  • --scale api=2 与健康门共存（本机两个副本都 healthy，入口仍 200）。

为什么要拆成三个文件，而不是在一个 compose.yaml 里改来改去

团队里最先出现的那个 compose 文件，往往就是开发自己的一份：

「本地起 full stack，我要 3306 直通宿主方便用 Navicat 连。」
「好。」（改了 db.ports）
「CI 里也用它？」
「CI 不用那个端口，但我把 build 参数改了……现在 CI 挂在镜像构建上。」
「生产也用这个？」
「生产口令不能写死在里面，我用 ${DB_ROOT_PW}，然后……」
「然后线上有人忘了设环境变量，起不来。」
「而且昨天有人把改过的这份文件提交了，把 dev 的 3306 直通带上了生产。」

这条路的终点的确实存在的：一份文件同时背三个环境的差异，差异靠人脑记。多文件不是「更正式」，而是把「哪个文件在什么时候生效」变成工具规则，不再依赖记忆。

机制上有三件事各自独立，混在一起想就乱：

机制 解决什么 谁决定它生效 本机实测的边界
多文件合并（-f / 同名 override） 环境差异分层 文件命名与加载顺序 同目录 compose.override.yaml 自动合并；compose.debug.yaml 不自动合并
profiles 同一份文件里，哪些服务默认不起 命令行是否给 --profile 不给 --profile app 时，api/web/proxy 在模型里根本不存在
.env 插值 把端口、口令这类会变的值挪出文件 变量是否存在 变量缺失时 :? 会硬失败，普通引用只给空串

一个服务最终出现在模型里，要同时过两道门：它所在的那个文件被加载了，并且它的 profile 被点名了。本机把这两道门分开量了一次——adminer 这个服务同时写了 profiles: ["debug"]，文件叫 compose.debug.yaml（不会被自动加载）：

命令 模型里的服务 说明
docker compose config --services（只加载主干 + 自动 override） cache db 应用层和调试层都不在
docker compose -f compose.yaml -f compose.debug.yaml config --services cache db 文件加载了，但 debug 这道门没开
docker compose -f compose.yaml -f compose.debug.yaml --profile debug config --services db adminer cache 两道门都过，adminer 出现
docker compose -f compose.yaml -f compose.debug.yaml --profile debug --profile app config --services db adminer cache api web proxy 六个服务全入选

改文件之前 adminer 没写 profiles 那一行，第二条命令的结果是 db adminer cache——只靠 -f 就把它带进来了。这正是「以为环境隔离了、其实没有」的真实形态，所以示例文件里那行 profiles: ["debug"] 不是装饰。

💡 新人小结：profiles 像会议室的门牌，不是门锁。profiles: ["app"] 只是给服务挂了块「应用层」的牌子，默认这条命令不会把牌子念到；你喊 --profile app，它才把挂这块牌子的服务一起带走。所以「加了 profile 就默认不起」不是 Docker 记错了，而是你没报名字。类比之后接机制：Compose 在加载阶段按 --profile 过滤服务集合，被过滤掉的服务连配置模型都不进——下面第一条读数里 config --services 只列出两个服务，就是这个过滤的结果。

先看默认模型有多小：profiles 的实测边界

主干文件把 api、web、proxy 三个服务打上 profiles: ["app"]（见下一节），然后什么都不加：

$ docker compose config --services
cache
db

加上 profile 才出现另外三个：

$ docker compose --profile app config --services
cache
db
api
web
proxy

这条读数比看上去重要。它意味着：docker compose up（不带 --profile）不会起应用层，docker compose config --format json 的模型里也没有 api。上一轮我自己就踩在这里——脚本直接取 services["api"] 抛 KeyError，看着像配置文件坏了，其实是模型里根本没有这个键。同理，pull 也不看 profile：

$ docker compose pull
 Image mysql:8.4 Pulling
 Image redis:7-alpine Pulling
 Image mysql:8.4 Pulled
 Image redis:7-alpine Pulled

只拉了 db 和 cache 两个镜像，nginx:1.27-alpine 与两个 build 服务都不在这条命令的职责里。CI 里想「预拉全部依赖」必须显式带上 profile，否则镜像缓存永远缺一块。

而 compose.debug.yaml（里面只有一个 adminer，用来演示调试面板）默认完全不参与：

$ docker compose --profile debug config --services
cache
db

$ docker compose -f compose.yaml -f compose.debug.yaml --profile debug config --services
db
adminer
cache

原因是 Compose 只自动加载两个文件名：主干 compose.yaml（或 compose.yml、docker-compose.yml）与同目录的 compose.override.yaml（或 compose.override.yml、docker-compose.override.yml）。其它名字一律要 -f 点名，或者交给 COMPOSE_FILE 环境变量。所以团队里约定「多环境文件叫 compose.<环境>.yaml」的同时，必须同时约定加载方式：-f compose.yaml -f compose.debug.yaml，或 COMPOSE_FILE=compose.yaml:compose.debug.yaml（分隔符在 Linux 是 :，Windows 上要用 ;，这一条本机未实测）。

警告

一旦你写了 -f，自动合并就没了。S4 那次反面实验用 -f compose.yaml -f compose.badstart.yaml，config 出来 api.environment 是 {"DB_HOST":"db","REDIS_HOST":"cache","STRICT":"1"}——override 里那句 LOG_LEVEL: debug 没跟上来。端口上的表现更直观，读自另一次 -f compose.yaml -f compose.debug.yaml 的真跑：那次 docker ps 里 db 的端口列是 3306/tcp, 33060/tcp（没有任何宿主映射），而自动合并的几次都是 127.0.0.1:3307->3306/tcp。排查「我明明改了 override 怎么没生效」，先看命令里有没有 -f。

三层文件各自放什么

本机的分工是这样落地的（完整文件在 示例/贯穿示例/）：

主干 compose.yaml 只放三个环境都成立的事实：

name: kb-p2

services:
  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_ROOT_PW:?在 .env 里设一个}
      MYSQL_DATABASE: kbdemo
    volumes:
      - dbdata:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p${DB_ROOT_PW}"]
      interval: 5s
      timeout: 3s
      retries: 20
      start_period: 20s
  # cache / api / web / proxy 见 4.9 完整实战一节

compose.override.yaml 只放开发期收窄的东西：

services:
  api:
    environment:
      LOG_LEVEL: debug
    develop:
      watch:
        - action: rebuild
          path: ./api
  db:

      - "127.0.0.1:3307:3306"

compose.debug.yaml 放要点名才有的东西（adminer 挂 8081，只在 --profile debug 时入选）。.env 放不能进版本库的值：

DB_ROOT_PW=local-dev-only
PROXY_PORT=8080

字段 合并后的值 来源

$ docker compose ls

同名字段怎么合并：规则不直觉，所以逐条量

这是最容易写错的一节。映射类字段深合并、列表类字段按语义分两种，「override 会覆盖主干」这句话在列表上不成立。下面每一行都是本机用一个两文件小样（主干 + override，服务只有一个 s）跑 config --format json 得到的：

字段 主干写 override 写 合并结果 结论
ports ["8001:6379"] ["8002:6379"] 两条都在 追加（按宿主端口去重，不是替换）
volumes base-vol:/data over-vol:/extra 两条都在 追加
command ["redis-server","--appendonly","no"] ["redis-server","--maxmemory","64mb"] 只剩 override 整体替换

deploy.resources.limits memory: 128m cpus: "0.5" memory:134217728 与 cpus:0.5 都在 深合并（映射逐层合并，128m 被规范化成字节）

后果很具体：想用 override「改掉」一个端口而不是「再加一个」，靠删行不行——两文件都在时容器会同时监听 8001 与 8002。真要收窄，用 YAML 标签把整段列表强制替换：

# 主干：ports: ["9001:80","9002:80"]，volumes: v1:/a 与 v2:/b，environment: KEEP=1 DROP=2
# override：ports: !override ["9100:80"]
$ docker compose config --format json
  !override 后 ports       = [{"mode":"ingress","target":80,"published":"9100","protocol":"tcp"}]
  !override 后 volumes     = null      # volumes: !override []
  !override 后 environment = null      # environment: !override {}

三条读数说明 !override 是整段替换而不是逐条比对，替换成空列表就等于删掉。反过来想用 !remove 精确摘掉一条：

# override：ports: !remove "9002:80"
rc=1 cannot override services.s.ports

本机这一版（v5.5.1）不吃这个形状的 !remove——要按值摘除，得写成 !remove 加列表的形式再试，或者干脆用 !override 把留下的部分整段写出来。团队约定就一条：列表类字段的「减」不靠猜测，写完必须用 config 看合并结果。

💡 新人小结：override 不是「改正主干」，是「往主干上贴便利贴」。便利贴可以补充（environment 多了 B=2）、可以改写同一格（SHARED 从 base 变 override）、也能往一列清单里再加一行（ports 变两条），但不能凭空让原来那行消失——想让整张清单换掉，得写「整段替换」的记号（!override）。类比之后接机制：这些规则来自 compose-spec 对每种字段的合并语义定义，config --format json 就是那台能把规则讲清楚的机器。

说明

down 的三种收场：为什么不能凭手感写

down 在 04 篇里是最容易出事的一条命令，因为它同时决定「容器停不停」和「数据留不留」。本机三种写法的结果：

写法 结果 读数
down（不带 --profile） 只停掉模型里有的 db/cache；api/web/proxy 三个仍在跑，网络删不掉 用时 2.0 秒；随后 docker ps 列出三个 Up 容器，docker network ls 里 kb-p2-net 还在；down 的日志里出现 Network kb-p2-net Resource is still in use
--profile app down --remove-orphans 五个容器全部停并删，网络删掉，卷保留 日志逐条 Stopped/Removed，最后 Network kb-p2-net Removed
down -v 连卷一起删（数据没了），但同样漏掉 profile 服务，网络仍报「仍在使用」 用时 1.6 秒；Volume kb-p2_dbdata Removed；再 up 后 ERROR 1146 (42S02) at line 1: Table 'kbdemo.t_note' doesn't exist，redis dbsize 为 0

两条结论要分开记：

  • profile 决定 down 的作用范围。 起的时候带了 --profile app，停的时候也必须带；不带就是「只停我看得到的那两个」。补救办法是 --remove-orphans，它按项目标签把不属于当前模型的容器一起收掉。
  • -v 是删数据的开关，不是「清得更干净」的开关。 上面的 ERROR 1146 就是它的回执：容器、网络、卷全部重建，MySQL 的数据目录是空的，表自然不存在。

💡 新人小结：down 像退房，down -v 像退房之后把房间重新装修一遍——两件事的费用不是一个量级，而且第二件不可撤销。类比之后接机制：down 删的是「项目派生的运行时对象」（容器、默认网络），-v 额外删掉 compose 声明的 named volume，而 named volume 是唯一活过容器生命周期的那份（02 篇里已经用备份命令验证过它的落点在 /var/lib/docker/volumes/.../_data，Windows 上挂在 WSL2 的 /dev/sdd）。

要留数据但清干净，用 stop + start 而不是 down：

$ docker compose stop cache          # 容器保留，只是停了
$ docker compose ps --format "{{.Service}}\t{{.State}}\t{{.Health}}"
api	running	healthy
db	running	healthy
proxy	running
web	running
$ docker compose start cache         # 原容器原样起来

stop/start 不重建容器，因此配置改动不会生效——这一条与 4.4 里 --no-recreate 的读数同源。

热重载：watch 的三档与它们的真实代价

开发期最烦的是「改一行等三分钟」。Compose 的 develop.watch 把这件事分成三档，档位差别就是「要不要重建镜像」：

档位 做什么 适用 本机实测代价
sync 把改的文件推进容器，不动进程 解释型语言 + 自动重载（PHP、Node 带 --reload、Rails） 未单独实测（示例里没有这种服务）
sync+restart 推进文件，然后重启容器内进程 静态资源、需要重启才生效的纯配置文件 从落盘到 curl 看到新内容 2.0 秒
rebuild 重新构建镜像并重建容器 需要编译的语言、依赖变化 4.1 秒（本例的占位服务只有两层）

sync+restart 那次的证据链：

# watch 已在后台跑（docker compose --profile app watch --no-up）
# 宿主改 web/index.html，加一行 <p>watch-marker-…</p>
Watch enabled
Syncing service "web" after 1 changes were detected
 Container kb-p2-web-1 Restarting
 Container kb-p2-web-1 Started
service(s) ["web"] restarted

$ docker compose ps --format "{{.Service}}\t{{.Status}}"
api	Up 37 seconds (healthy)
cache	Up 29 seconds (healthy)
db	Up 29 seconds (healthy)
proxy	Up 31 seconds
web	Up 1 second          # 只有它被重启了

配置文件里对应这两档的写法：

services:
  web:
    develop:
      watch:
        - action: sync+restart
          path: ./web/index.html
          target: /usr/share/nginx/html/index.html
  api:
    develop:
      watch:
        - action: rebuild
          path: ./api

config 里能看到被规范化后的形状（target 只在 sync 系需要，rebuild 不带它）：

{"watch": [{"path": "…\\web\\index.html", "action": "sync+restart",
            "target": "/usr/share/nginx/html/index.html", "exec": {"command": null}}]}

rebuild 档的 4.1 秒要老实标注它不能外推：这个占位服务的 Dockerfile 只有 FROM alpine + COPY 一步，本机 docker compose build --no-cache api 是 1.0 秒，缓存命中是 0.5 秒。换成真实 Spring Boot，rebuild 里多出依赖解析与打包，量级完全不同——本轮没有 Maven 环境，那个数没量到，写进 4.8 的判据里作为待补项而不是结论。

提示

watch 与 up 的关系：docker compose up --watch 与单独跑 docker compose watch 等价；--no-up 用于「栈已经起来了，只挂监视器」，本机的两次实测都是这么起的。watch 是前台会话，用脚本起它要注意 docker CLI 会派生 docker-compose 子进程，父进程被终止时子进程还活着并占着日志文件句柄——本轮就在这里踩过一次，目录删不掉，最后按子进程 pid 收的。

Windows 下的 bind mount 与 HMR：现象、成因与解法

前端开发常见的一句抱怨是「容器里跑 Vite，改文件浏览器不热更」。三个独立的坑叠在一起，要分开验：

症状 成因 解法 本机状态
改文件完全没反应，容器内也不见新内容 挂载写错（路径大小写、Docker Desktop 文件共享未放行该盘） 先 docker compose exec web ls -l /app 看容器里看到的到底是什么 未实测（示例的 web 是构建进镜像的静态文件，不是 bind mount）
容器内文件变了，但监听器不触发 Windows 侧的 9p/DrvFs 挂载不把 inotify 事件传进容器，只有数据变化可见 Vite 打开轮询：server.watch.usePolling = true（配 interval，常见 300 毫秒起）；或改用 develop.watch 的 sync 由 compose 主动推 机制成立，本轮未实测；02 篇量到的「bind mount 走 9p、比命名卷慢一个量级」是同一条链上的另一环
浏览器连的是 localhost:5173 但 WebSocket 失败 HMR 的 WS 端口/主机与 dev server 不一致：容器里监听 127.0.0.1 外面进不来 server.host = true 监听所有网卡 + ports 把 5173 publish 出来 + 必要时 server.hmr.clientPort = 5173；/api 前缀交给 proxy 服务而不是 Vite 的 proxy 未实测，属配置口径；给判据：浏览器 Network 里 WS 请求的目标地址应与 docker compose port web 5173 的读数一致

docker compose port 这条命令在排查第三种症状时最省事——它直接回答「compose 认为这个服务的外部地址是什么」，而不是让人去翻 ps 的 PORTS 列。Java 侧的对应做法（devtools + 挂载 target/classes、或直接让 IDE 跑在 kb-p2-net 上）同样只给口径，本轮没有 Java 容器可跑，标在本篇未验证项里。

💡 新人小结：文件共享挂载像隔着一扇玻璃窗递东西——东西（内容）你看得见也拿得到，但窗那边的人不知道你什么时候递的（事件传不过去）。所以「改文件不热更」常常不是没生效，是没人通知它。接机制：usePolling 就是让窗那边的人每隔几百毫秒自己探头看一眼，代价是 CPU 与延迟，换来行为可预测。

完整实战：五个服务的栈是怎么长出来的

主干文件完整贴一次（api/web/proxy 三个都挂在 profiles: ["app"] 下，因为它们是「应用层」，CI 预拉依赖时不该被卷进来）：

services:
  cache:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - cachedata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 2s
      retries: 10

  api:
    build: ./api
    environment:
      DB_HOST: db
      REDIS_HOST: cache
    depends_on:
      db: { condition: service_healthy }
      cache: { condition: service_healthy }
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "-", "http://127.0.0.1:8080/api/health"]
      interval: 5s
      timeout: 3s
      retries: 12
      start_period: 5s
    profiles: ["app"]

  web:
    build: ./web
    profiles: ["app"]

  proxy:
    image: nginx:1.27-alpine
    ports:
      - "${PROXY_PORT:-8080}:80"
    volumes:
      - ./proxy/nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      api: { condition: service_healthy }
      web: { condition: service_started }
    profiles: ["app"]

networks:
  default:
    name: kb-p2-net

volumes:
  dbdata:
  cachedata:

几个设计点的取舍，都对应上面某条读数：

  • 入口只有一个。 只有 proxy 暴露宿主端口（${PROXY_PORT:-8080}），api 与 web 的 8080/tcp、80/tcp 只在容器网络里。生产同理：宿主端口越少，能被打的洞越少。
  • db 的端口只在 override 里。 127.0.0.1:3307:3306 是开发期便利（避开本机已占用的 3306），绑 127.0.0.1 而不是 0.0.0.0；主干不带这个字段，CI 与生产加载主干就自然没有它。
  • proxy 对 api 用健康门、对 web 用 service_started。 nginx 起来时如果 upstream 名字解析不到会直接退出，api 是它必须等的那一个；web 只提供静态文件，service_started 够用。
  • 卷名交给 compose 加前缀。 实际落地的名字是 kb-p2_dbdata（config 的读数），所以手工 docker volume rm 之前要按这个名字找，不要写 dbdata。
  • name: kb-p2 必须写死。 项目名会进卷名、网络名、容器名。中文目录名场景下 Compose 会把非法字符过滤掉，过滤空了就报 project name must not be empty——本轮在一个中文命名的临时目录里（文件内容与它完全相同、只是目录换成 ASCII 名的对照组正常通过）直接撞到过这条报错，加上 name: 就好。

常见误读

误读 实际
「profiles 是环境隔离，dev 和 prod 用不同 profile」 profile 决定一条命令带上哪些服务，不是「配置分环境」。环境差异该走多文件；用 profile 装环境，会出现「prod 的 up 忘了 --profile prod 就少起一层」
「override 里没写的字段会被清掉」 映射类深合并、command 这类标量整体替换、ports/volumes 追加。override 不写，主干的值仍然在
「compose.debug.yaml 也会自动合并，名字长得像就行」 只有 compose.override.* / docker-compose.override.* 是自动的，其它文件名要 -f 或 COMPOSE_FILE
「down 就是把这套东西停干净」 不带 --profile 的 down 会漏起 profile 服务，网络因「仍在使用」删不掉；--remove-orphans 才是兜底
「down -v 是更彻底的清理，可以当习惯用」 -v 删 named volume，也就是删数据。上面那条 ERROR 1146 就是它的结果
「watch 的 rebuild 快，所以 Java 项目也可以这么写」 本例 4.1 秒来自两层 COPY 的占位镜像。真实 Java 的构建成本没在本轮量过
「up --wait 返回 0 就说明业务可用」 --wait 等的是「健康检查通过」。健康检查口径写窄（只 ping TCP），它就只保证那一格

要点总结

  • 三个机制各管一件事：多文件管环境差异，profiles 管一条命令带哪些服务，.env 管会变且不进版本库的值。
  • profiles 的过滤发生在模型加载阶段：不带 --profile，config --services、pull、down 全都看不到那些服务。这是本机最容易踩的一条。
  • 同名字段的合并语义分三类（深合并 / 整体替换 / 追加），ports 与 volumes 是追加；写了 -f 就没有自动 override 合并。
  • 第②段判据四条全部通过：一条命令起 5 个服务（冷 18.4 秒 / 热 7.1 秒）、三个带检查的服务 healthy、经 proxy 的 /api/health 与 / 都是 200（3.7 毫秒 / 2.2 毫秒）、down 后数据仍在。
  • 启动时间由 MySQL 的数据目录初始化决定，不由 compose 决定：卷为空 16.8 秒、卷已用 7.1 秒，两次差的就是 MySQL 初始化那 8 秒量级。
  • down / down --remove-orphans / down -v 是三件事：停可见服务、停全部服务、连数据一起删。写命令时按这三档想。
  • watch 三档的实测代价：sync+restart 2.0 秒（纯静态文件），rebuild 4.1 秒（占位镜像）；sync 档与真实 Java/Node 的数字本轮没量到。
  • Windows 下「改文件不热更」先分清是「数据没过去」还是「事件没过去」，后者用轮询或 develop.watch 的 sync 兜。
