## 背景

本站（Java 笔记）是一个纯静态站点，由 Hugo 构建、部署在本地或内网环境，**没有后端服务器**。这意味着传统的「搜索请求 → 服务端查询 → 返回结果」模式完全不可用。

那么问题来了：**一个没有后端的静态站点，如何实现全文搜索？**

本文对本站的搜索技术栈做一次完整的拆解。

---

## 技术栈总览

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| **索引生成** | Hugo 模板引擎 | 构建时遍历所有页面，生成 JSON 索引文件 |
| **搜索引擎** | Lunr.js v2.3.9 | 客户端全文搜索引擎，vendored 离线使用 |
| **CJK 支持** | 自定义子串匹配 | 针对中日韩文字的补充搜索路径 |
| **UI 组件** | Command Palette | 自定义 `<dialog>` 弹窗，支持键盘导航 |
| **配置开关** | `offline_search: true` | hugo.yaml 中一行开启 |

```
整体架构

① Hugo 构建时 → 遍历所有页面 → 生成 offline-search-index.zh.json（~253KB）
② 用户按 / 或点击搜索 → 打开 Command Palette 弹窗
③ 弹窗加载 JSON 索引 → 初始化 Lunr 索引 + CJK 子串匹配器
④ 用户输入关键词 → 自动检测 CJK / 拉丁文 → 走对应搜索路径
⑤ 结果按得分排序 → 分组展示 → 键盘/鼠标选择跳转
```

## 第一层：构建时索引生成

### 工作原理

索引不是运行时生成的，而是在 `hugo --minify` 构建时就完成了。核心逻辑在主题的 [offline-search-index.json](file:///e:/github/Java-Doc-Site/oink-main/oink-main/assets/json/offline-search-index.json) 模板中：

```
索引生成流程

① 遍历 .Site.Pages 中所有 Kind 为 page 或 section 的页面
② 过滤掉 search_exclude: true 的页面
③ 对每个页面提取：title / headings / description / body / tags / categories
④ 组装为 JSON 文档（每页一条记录）
⑤ 输出为 offline-search-index.{lang}.json
⑥ 生产构建时追加 MD5 指纹（缓存破坏）
```

### 索引内容

每页生成的 JSON 文档包含以下字段：

| 字段 | 来源 | 用途 |
|------|------|------|
| `ref` | `.RelPermalink` | 页面链接（也是 Lunr 的文档标识） |
| `title` | `.Title` | 标题，搜索权重最高（boost: 5） |
| `headings` | `.TableOfContents` | 所有标题文本，boost: 3 |
| `description` | `.Description` 或 `.Summary` | 摘要，boost: 2 |
| `body` | `.Plain`（全文纯文本） | 正文内容，boost: 1 |
| `tags` | `.Params.tags` | 标签，boost: 3 |
| `categories` | `.Params.categories` | 分类，boost: 3 |
| `excerpt` | 摘要截断（默认 70 字） | 搜索结果预览 |

### 索引规模

| 指标 | 数值 |
|------|------|
| 主索引文件大小（未压缩） | ~253 KB |
| 收录页面数 | ~146 页 |
| 索引范围 | `content`（全文） |
| 索引语言 | `zh`（中文） |

> ### 💡 新人小结：为什么要把索引做成文件？
>
> 想象你在图书馆找书：
> - **传统搜索**：问图书管理员（服务器），他帮你查目录 → 返回结果
> - **本站的做法**：把整本目录册（JSON 索引）直接给你 → 你自己翻
>
> 目录册有 253KB，第一次打开时加载一下，之后搜索就是纯本地操作——**断网也能搜**。

## 第二层：Lunr.js 搜索引擎

### 什么是 Lunr.js

[Lunr.js](https://lunrjs.com/) 是一个轻量级的客户端全文搜索引擎，灵感来自 Solr 和 Elasticsearch，但体积只有 ~8KB（gzip）。它在浏览器中构建倒排索引，支持：

- 词干提取（stemming）
- 通配符查询（`*term*`）
- 模糊匹配（编辑距离 2）
- 字段权重提升（boost）
- 布尔查询

本站使用 **v2.3.9**，直接 vendored 在 `assets/third_party/lunr/` 目录下，无需网络请求。

### 字段权重配置

在 [search-engine.js](file:///e:/github/Java-Doc-Site/oink-main/oink-main/assets/js/search-engine.js) 中，Lunr 索引的字段权重如下：

| 字段 | Boost 权重 | 含义 |
|------|-----------|------|
| `title` | **5** | 标题匹配最重要 |
| `keywords` | **4** | 关键词次之 |
| `categories` | **3** | 分类匹配 |
| `tags` | **3** | 标签匹配 |
| `headings` | **3** | 章节标题匹配 |
| `description` | **2** | 摘要匹配 |
| `body` | **1** | 正文匹配（默认权重） |

这意味着：如果搜索词出现在标题中，其得分是出现在正文中的 **5 倍**。

### 拉丁文搜索路径

对于英文、代码等拉丁文字，Lunr 的查询逻辑：

```java
// 伪代码展示 Lunr 的查询策略
对每个搜索词 token：
  ① 精确匹配（boost: 100）    // "Optional" 精确命中
  ② 通配符匹配（boost: 10）   // "*Opt*" 前后缀模糊
  ③ 编辑距离 2（默认 boost）   // "Optinal" 拼写纠错
```

三层递进：先精确找，再模糊找，最后容错找——确保拼写错误也能命中。

## 第三层：CJK 双路径搜索

### 问题

Lunr.js 的搜索引擎基于**空格分词**——这对英文天然友好，但对中文完全失效。

```
英文："hello world" → Lunr 分词为 ["hello", "world"] ✅
中文："你好世界"    → Lunr 分词为 ["你好世界"]（一整块）❌
```

中文没有空格分隔词语，Lunr 无法正确分词，搜索命中率极低。

### 解决方案：双路径架构

本站的搜索引擎实现了**自动检测 + 双路径分发**：

```
用户输入关键词
│
├─ 包含 CJK 字符？（正则: /[぀-ヿ㐀-䶿一-鿿]/）
│   ├─ 是 → queryCjk()：子串匹配路径
│   │       遍历所有文档，对每个字段做 indexOf() 子串搜索
│   │       按命中字段加权：title=100, keyword=80, heading=50, desc=30, body=10
│   │
│   └─ 否 → queryLatin()：Lunr 倒排索引路径
│           利用 Lunr 的倒排索引，支持通配符和编辑距离
```

### CJK 子串匹配的评分逻辑

| 命中字段 | 得分 | 说明 |
|---------|------|------|
| `title` | 100 | 标题包含搜索词 |
| `keywords` | 80 | 关键词包含搜索词 |
| `headings` | 50 | 章节标题包含搜索词 |
| `description` | 30 | 摘要包含搜索词 |
| `body` | 10 | 正文包含搜索词 |

最终得分 = 字段得分 × 页面 boost 系数（如果有的话），按总分降序排列。

> ### 💡 新人小结：为什么要两条路径？
>
> 想象你在查字典：
> - **英文**：用索引查（Lunr 倒排索引）——快，支持模糊查找
> - **中文**：逐页翻找（子串匹配）——慢一点，但能找对
>
> 搜索引擎会自动判断你输入的是中文还是英文，走对应的查找方式。你不需要关心底层细节。

## 第四层：Command Palette UI

### 交互设计

搜索界面不是传统的搜索框，而是一个 **Command Palette**（命令面板），类似 VS Code 的 `Ctrl+Shift+P`。

| 特性 | 说明 |
|------|------|
| **触发方式** | 点击搜索图标 / 按 `/` 键 |
| **弹窗模式** | `<dialog>` 原生弹窗，`role="dialog"` + `aria-modal` |
| **键盘导航** | `↑↓` 选择结果，`Enter` 打开页面，`Esc` 关闭 |
| **无障碍** | 完整的 ARIA 属性（`combobox` / `listbox` / `aria-expanded`） |
| **国际化** | 所有文案通过 i18n 配置，支持中文 |

### 搜索结果分组

搜索结果按页面所属的**根分类**自动分组：

```
搜索结果

📂 Java 基础
  ├─ Optional 优雅处理空值
  └─ final 类与 final 方法

📂 开发工具
  ├─ Lombok 与 MapStruct 实战
  └─ 可运行 JAR 包

📂 算法
  ├─ 01 背包问题
  └─ 二分查找
```

### 配置参数

所有搜索相关参数均在 [hugo.yaml](file:///e:/github/Java-Doc-Site/hugo.yaml) 中配置：

| 参数 | 当前值 | 说明 |
|------|--------|------|
| `offline_search` | `true` | 开启本地索引与命令面板 |
| `offline_search_max_results` | 未设置（默认 10） | 搜索结果最大显示数 |
| `offline_search_index` | 未设置（默认 `content`） | 索引范围：`title` / `heading` / `summary` / `content` |
| `offline_search_summary_length` | 未设置（默认 70） | 摘要截断长度（字符） |

## 性能分析

| 指标 | 数值 | 评价 |
|------|------|------|
| 索引文件大小（未压缩） | ~253 KB | 中等，首次加载约 50-100ms（本地） |
| 索引文件大小（gzip） | ~40-60 KB（估算） | 可接受 |
| 搜索响应时间 | <10ms（CJK 子串匹配） | 极快，146 页全文扫描在现代浏览器中几乎无感 |
| 内存占用 | ~2-5 MB（索引 + Lunr 实例） | 低 |
| 零运行时依赖 | ✅ | 不需要服务器、不需要 API key |

### 可扩展性瓶颈

| 页面规模 | 预期表现 |
|---------|---------|
| <500 页 | 完全无感，搜索 <10ms |
| 500-2000 页 | 仍然可用，CJK 子串匹配可能到 30-50ms |
| >2000 页 | 建议考虑切换到 `heading` 或 `summary` 索引范围以减小索引体积 |

## 与替代方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **本站方案（Lunr + 离线索引）** | 零后端依赖、离线可用、CJK 支持 | 索引随页面增长、首次加载有延迟 | 静态站点、内网/离线环境 |
| Algolia DocSearch | 搜索质量极高、支持分面搜索 | 需要网络、需要 API key、有配额限制 | 公共文档站 |
| Elasticsearch / Meilisearch | 搜索能力最强、支持复杂查询 | 需要独立部署服务端 | 大型站点 |
| Google CSE | 免费、无需部署 | 依赖 Google、有广告、无法离线 | 不敏感内容站点 |
| Pagefind | 构建时索引、零 JS 运行时 | 较新、社区生态小 | 中小型静态站 |

## 要点总结

1. **纯离线架构**：索引在 Hugo 构建时生成 JSON 文件，搜索在浏览器端完成，零后端依赖
2. **Lunr.js v2.3.9**：客户端倒排索引引擎，支持通配符、模糊匹配、字段权重
3. **CJK 双路径**：自动检测中日韩文字，切换为子串匹配 + 字段加权评分
4. **Command Palette UI**：原生 `<dialog>` + 完整 ARIA + 键盘导航 + 结果分组
5. **当前规模**：146 页 / 253KB 索引，搜索响应 <10ms，完全够用
6. **扩展建议**：页面超过 2000 时，缩小索引范围（`heading` 或 `summary`）控制体积
