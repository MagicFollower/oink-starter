以下是一份 **RocketMQ 4.9.8 生产环境高可用部署方案**，采用与之前操作手册一致的结构化格式。核心架构选用 **2m-2s-async（双主双从异步复制）** ，这是 4.x 生产环境中最经典、在性能与可靠性之间取得最佳平衡的模式。

---

## 0. 架构选型与可靠性决策

### 为什么选 2m-2s-async？

2m-2s-async 意味着两个 Master 各自配备一个 Slave，消息写入 Master 后立即向生产者返回成功，随后**异步复制**到 Slave。它的核心优势在于：

- **无单点故障**：每个 Master 都有数据副本，单台服务器宕机不影响另一组 Broker 的工作。
- **性能几乎无损**：异步复制对发送延迟的影响在毫秒级别，吞吐量与纯多 Master 模式基本持平。
- **消费不中断**：Master 宕机后，消费者可以自动切换到 Slave 继续消费（需开启 Slave 读权限）。

### 可靠性升级选项：何时改用 2m-2s-sync？

如果业务对**消息零丢失**有严格要求（如金融交易、支付核心链路），应将 `brokerRole` 从 `ASYNC_MASTER` 改为 `SYNC_MASTER`。此时消息必须同时写入 Master 和 Slave 才算成功，代价是发送延迟增加、吞吐量下降约 30%–50%。**常规业务推荐 ASYNC_MASTER + ASYNC_FLUSH，兼顾性能与可靠性**。

### 关于自动主从切换（Dledger / Controller）

标准的 2m-2s 主从架构**不支持自动故障切换**：Master 宕机后，Slave 只能提供读消费，写入需要人工介入或依赖外部工具。如果希望实现秒级自动选主，4.x 时代可采用 **DLedger 模式**（基于 Raft），在 Broker 配置中启用 `enableDLegerCommitLog=true` 并配置至少 3 个 DLedger 节点。但需注意：DLedger 对部署复杂度、节点数量和运维能力要求更高，且官方在 5.x 已转向 Controller 模式。**如果团队没有成熟的自动切换运维体系，标准的 2m-2s-async + 完善的故障演练流程，是 4.9.8 生产环境中更稳妥的选择。**

## 1. 节点规划与硬件基线

### 1.1 节点分布

以下以 **4 台物理机/虚拟机**为例（Broker 与 NameServer 可混合部署，但 Broker 建议独占资源）：

| 节点 | 角色 | 部署组件 |
|---|---|---|
| node-1 | NameServer + Broker | `broker-a` (Master) |
| node-2 | NameServer + Broker | `broker-a-s` (Slave of a) |
| node-3 | NameServer + Broker | `broker-b` (Master) |
| node-4 | NameServer + Broker | `broker-b-s` (Slave of b) |

**关键原则**：`broker-a` 与其 Slave `broker-a-s` **必须部署在不同物理节点上**，否则单节点故障会同时带走 Master 和 Slave，主从复制的意义将完全丧失。

NameServer **至少部署 2 台，推荐 3 台**。NameServer 之间无状态、不通信，Broker 会向所有 NameServer 注册，客户端轮询访问，单节点故障对客户端透明。3 台还便于后续 Controller 内嵌部署时形成奇数法定多数。

### 1.2 硬件建议（单节点）

| 组件 | CPU | 内存 | 磁盘 | 网络 |
|---|---|---|---|---|
| NameServer | 4 核 | 8 GB | SSD / SATA 100 GB+ | 1 Gbps+ |
| **Broker** | **16 核以上** | **32–64 GB** | **NVMe SSD，1 TB 起** | **万兆网卡优先** |

- **磁盘是 Broker 的生命线**：RocketMQ 严重依赖磁盘顺序写和 PageCache，**必须使用 SSD，NVMe 更优**；RAID 5 写惩罚严重，应避免，优先 RAID 10 或单盘裸设备。
- **内存与 PageCache**：Broker 的 JVM 堆不应超过物理内存的 70%，剩余内存留给操作系统作为 PageCache，这是 RocketMQ 高吞吐的关键。
- **网络**：跨节点复制会占用带宽，高吞吐场景建议万兆网卡，至少保证 Broker 节点间低延迟互通。

## 2. NameServer 集群配置与启动

NameServer 无状态，集群部署的核心只是**在所有节点上以相同的端口启动，并让 Broker/客户端知道全部地址**，节点之间无需任何配置同步。

### 2.1 配置文件（`conf/namesrv.properties`，各节点一致）

```properties
# ============================================================
# RocketMQ 4.9.8 NameServer 生产配置
# ============================================================

# NameServer 监听端口，集群内各节点保持一致
listenPort=9876

# 生产环境建议显式绑定内网 IP（按节点修改），而不是 0.0.0.0
# bindAddress=0.0.0.0

# 是否启用集群测试模式，生产环境必须为 false
clusterTest=false
```

> 如果服务器有多块网卡，`bindAddress` 应显式指定为**内网通信 IP**，避免绑定到公网或无关网卡。

### 2.2 启动命令（Linux，各节点分别执行）

```bash
cd $ROCKETMQ_HOME

nohup sh bin/mqnamesrv -c conf/namesrv.properties > namesrv_startup.log 2>&1 &
```

3 台 NameServer 全部启动后，Broker 的 `namesrvAddr` 应配置为：

```
namesrvAddr=node-1:9876;node-2:9876;node-3:9876
```

**分号分隔，不要有空格**。

### 2.3 NameServer 层验证

```bash
# 各节点检查端口
ss -tlnp | grep 9876

# 各节点日志确认
grep "boot success" ~/logs/rocketmqlogs/namesrv.log
```

由于 NameServer 之间不通信，**每个节点都需要独立验证**。后续 Broker 启动后，`mqadmin clusterList -n node-1:9876` 和 `-n node-2:9876` 都应返回相同的集群信息。

## 3. Broker 主从配置文件模板

RocketMQ 4.9.8 发行包的 `conf/2m-2s-async/` 目录下自带四个参考配置文件：`broker-a.properties`、`broker-a-s.properties`、`broker-b.properties`、`broker-b-s.properties`。下面给出基于生产实践的完整模板，**Master 与 Slave 的差异已用注释标出**。

### 3.1 Master 配置模板（`broker-a.properties` / `broker-b.properties`）

```properties
# ============================================================
# Broker Master 生产配置 (broker-a.properties 示例)
# ============================================================

# ---------- 身份标识 ----------
brokerClusterName=DefaultCluster

# broker-a 和 broker-a-s 必须使用相同的 brokerName
brokerName=broker-a

# 0 表示 Master
brokerId=0

# ---------- 网络与注册 ----------
# 全部 NameServer 地址，分号分隔
namesrvAddr=node-1:9876;node-2:9876;node-3:9876

listenPort=10911

# 【关键】多网卡环境必须显式指定对外服务 IP
# 不配置时 RocketMQ 可能自动选中错误的网卡
brokerIP1=node-1的内网IP

# 【关键】Master 的 brokerIP2 应配置为 Slave 可访问的同步 IP
# Slave 通过此地址连接 Master 进行主从复制
brokerIP2=node-1的内网IP

# ---------- 角色与刷盘 ----------
# 常规业务：异步复制，高性能
# 金融级零丢失要求：改为 SYNC_MASTER
brokerRole=ASYNC_MASTER

# 推荐 ASYNC_FLUSH；若要求单机掉电不丢消息，改为 SYNC_FLUSH（性能下降明显）
flushDiskType=ASYNC_FLUSH

# ---------- 存储路径 ----------
# 强烈建议挂载独立 SSD，且 commitlog 与 consumequeue 分盘存放
storePathRootDir=/data/rocketmq/store/broker-a
storePathCommitLog=/data/rocketmq/store/broker-a/commitlog
storePathConsumeQueue=/data/rocketmq/store/broker-a/consumequeue

# ---------- 生产环境必关开关 ----------
# 生产环境应关闭自动创建 Topic/Group，由运维统一管理
autoCreateTopicEnable=false
autoCreateSubscriptionGroup=false

# ---------- 文件清理 ----------
deleteWhen=04
# 根据消息量和磁盘容量调整，单位小时
fileReservedTime=72

# 磁盘使用率超过此阈值后拒绝写入，预留缓冲
diskMaxUsedSpaceRatio=85

# ---------- 性能调优（按核数调整） ----------
# 16 核节点建议 32 左右，不宜超过核数过多
sendMessageThreadPoolNums=32
pullMessageThreadPoolNums=32

# CommitLog 单文件保持 1GB，过大会拖慢异常恢复速度
mapedFileSizeCommitLog=1073741824
```

### 3.2 Slave 配置模板（`broker-a-s.properties` / `broker-b-s.properties`）

Slave 配置与对应的 Master 高度一致，**只需修改以下几项**：

```properties
# 与所属 Master 保持完全一致
brokerClusterName=DefaultCluster
brokerName=broker-a

# 【关键】Slave 的 brokerId 必须 > 0，且同一组内不能重复
brokerId=1

namesrvAddr=node-1:9876;node-2:9876;node-3:9876
listenPort=10911

# Slave 自身对外 IP（供消费者读取时访问）
brokerIP1=node-2的内网IP

# 角色：Slave 必须配置为 SLAVE
brokerRole=SLAVE

flushDiskType=ASYNC_FLUSH

# 【关键】同一台机器上如果部署多个 Broker，存储路径必须不同
storePathRootDir=/data/rocketmq/store/broker-a-s
storePathCommitLog=/data/rocketmq/store/broker-a-s/commitlog
storePathConsumeQueue=/data/rocketmq/store/broker-a-s/consumequeue

autoCreateTopicEnable=false
autoCreateSubscriptionGroup=false
```

> **Slave 的 `brokerIP2` 不需要配置**；Slave 是通过读取 Master 上配置的 `brokerIP2` 来发起同步连接的。

## 4. 分步启动与四层验证

### 4.1 启动顺序

**NameServer 全部就绪 → 启动所有 Master → 启动所有 Slave。**

Slave 启动时会连接对应 Master 进行数据同步，Master 先就绪可以避免 Slave 在启动阶段反复重试连接。

```bash
# 在各 Broker 节点上执行，以 broker-a (Master) 为例
cd $ROCKETMQ_HOME
nohup sh bin/mqbroker -c conf/2m-2s-async/broker-a.properties \
  > broker-a_startup.log 2>&1 &
```

其他三个 Broker 将 `broker-a.properties` 替换为对应的配置文件即可。Windows 下使用 `start mqbroker.cmd -c ../conf/2m-2s-async/broker-a.properties`。

### 4.2 验证层一：进程与端口

```bash
# 每个 Broker 节点
jps -l | grep BrokerStartup
ss -tlnp | grep 10911
```

### 4.3 验证层二：注册与主从关系（最终判据）

```bash
# 在任意一台能访问 NameServer 的机器上
sh bin/mqadmin clusterList -n node-1:9876
```

**正常输出应显示 `2m-2s-async` 的完整拓扑**：`broker-a` 和 `broker-b` 各有一个 Master（ID 0）和一个 Slave（ID 1），且 Slave 的地址指向不同节点。如果 Slave 未出现在列表中，或 `clusterList` 中某组只有 Master，说明 Slave 未成功同步或注册失败。

### 4.4 验证层三：主从同步状态

```bash
sh bin/mqadmin brokerStatus -n node-1:9876 -b node-1的内网IP:10911
```

关注 Slave 是否在线以及同步延迟。在异步复制模式下，正常运行时 Slave 落后 Master 的消息数应处于**毫秒级对应的少量条数**；如果持续增长，说明复制链路出现问题。

### 4.5 验证层四：实际读写

```bash
# 快速收发验证（使用 tools，Topic 需已手动创建或临时开启自动创建）
export NAMESRV_ADDR=node-1:9876;node-2:9876;node-3:9876
sh bin/tools.sh org.apache.rocketmq.example.quickstart.Producer
sh bin/tools.sh org.apache.rocketmq.example.quickstart.Consumer
```

生产者在 `2m-2s-async` 下应观察到消息分散到两个 Master 的队列中；消费者应能持续消费。

## 5. 故障演练（部署完成后必须执行）

高可用架构的价值只有在演练中才能被验证。以下演练应在**业务低峰期**进行，至少完成 3 次完整循环。

### 演练一：Master 宕机，消费者切换

1. 在 `broker-a` 的 Master 节点上执行 `kill <pid>`（模拟进程崩溃）。
2. 观察消费者是否在心跳周期内感知到 Master 不可用，并**自动切换至 `broker-a-s` 继续消费**（前提是客户端开启了从 Slave 读）。
3. 观察生产者发送到原 `broker-a` 队列的消息是否出现短暂失败/重试。
4. 重启原 Master，观察主从关系是否恢复，Slave 是否重新跟随。

**预期结果**：消费不中断（或仅有秒级停顿）；生产端有短暂重试，由客户端重试机制兜底。

### 演练二：Master 宕机，生产者路由切换

1. 停掉 `broker-a` Master。
2. 持续发送消息，观察生产者是否将新消息路由到 `broker-b`（另一个 Master）。
3. 确认 `clusterList` 中 `broker-a` 组降级为仅 Slave（或短暂消失后以 Slave 状态可见）。

**关键认知**：在标准 2m-2s-async 中，**Master 宕机后该组不再接受写入**（Slave 只读），写入能力会降级为单 Master。如果业务无法接受写入能力减半，需要在架构层考虑 Dledger/Controller 或 3 Master 方案。

### 演练三：Slave 宕机

1. 停掉 `broker-a-s`。
2. 确认 `broker-a` Master 的写入**不受影响**（异步复制下，Slave 短暂离线只影响数据冗余，不影响写入）。
3. `brokerStatus` 中应看到 Slave 离线；Slave 恢复后应自动重新同步。

## 6. 生产运维关键注意事项

### 6.1 JVM 调优（启动前必须做）

RocketMQ 默认的 JVM 参数面向大内存机器，**生产部署必须根据实际硬件调整** `bin/runbroker.sh` 和 `bin/runserver.sh`。Broker 堆内存建议设为物理内存的 **50%–70%**，剩余留给 PageCache；NameServer 轻量，4–8 GB 堆通常足够。未调整默认参数直接启动，可能在中小规格节点上触发 OOM 或频繁 Full GC。

### 6.2 `brokerIP1` / `brokerIP2` 不可省略

在多网卡、容器化或云主机环境中，RocketMQ 自动探测 IP 的行为不可靠。**生产环境必须显式配置 `brokerIP1`；Master 必须显式配置 `brokerIP2`**，否则 Slave 可能连接到错误的地址，主从同步无法建立。

### 6.3 关闭自动创建 Topic 与 Group

`autoCreateTopicEnable=false` 和 `autoCreateSubscriptionGroup=false` 是生产环境的基本纪律。自动创建会导致 Topic 命名混乱、队列数不可控，并可能在无意中产生大量低质量 Topic。Topic 和 Group 应通过 `mqadmin` 或 Dashboard 统一管理。

### 6.4 磁盘水位与文件清理

`diskMaxUsedSpaceRatio` 建议设为 **85** 而非默认 90，为文件清理和突发写入预留缓冲。`fileReservedTime` 根据磁盘容量和消息保留需求设置（72 小时是常见起点）。**磁盘写满会导致 Broker 直接拒绝写入**，这是生产环境最常见的故障之一。

### 6.5 监控必看指标

至少接入以下监控项：**Broker 进程存活、主从同步延迟（Slave 落后条数）、磁盘使用率、CommitLog 写入延迟、消费堆积（diff 总量）** 。`mqadmin statsAll` 和 `consumerProgress` 可作为手动巡检的补充。

### 6.6 客户端配合

高可用不仅取决于服务端。生产端应配置**合理的发送超时与重试次数**；消费端应实现**幂等处理**（RocketMQ 保证 at-least-once），并在 Master 故障切换后能够通过 Rebalance 自动接管队列。服务端主从切换的“最后一道防线”在客户端。

## 7. 关键决策速查表

| 你的需求 | 推荐配置 |
|---|---|
| 常规业务，性能与可靠性平衡 | `ASYNC_MASTER` + `ASYNC_FLUSH` + 2m-2s |
| 金融级零丢失，可接受延迟上升 | `SYNC_MASTER` + `SYNC_FLUSH`（或至少 `SYNC_MASTER` + `ASYNC_FLUSH`） |
| 必须自动主从切换，不愿人工介入 | 评估 **DLedger**（4.x）或升级 5.x 使用 Controller |
| NameServer 节点数 | **3 台**（最低 2 台） |
| Broker 存储盘 | **NVMe SSD**，commitlog 与 consumequeue 分盘 |
