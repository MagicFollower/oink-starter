# 为什么接口需要「自带实现」？

先看一段 Java 8 之前注定失败的代码：

```java
// ========== Java 8 之前：给接口加一个方法 ==========
public interface Iterable<T> {
    Iterator<T> iterator();
    // 想加一个 forEach，让所有集合都能直接遍历？
    // void forEach(Consumer<? super T> action);
}
```

只要把 `forEach` 这行的注释去掉，**全世界所有实现了 `Iterable` 的类瞬间编译报错**——它们都没有实现这个新方法。这就是 Java 8 之前接口的「化石困境」：

```text
接口新增方法 → 所有实现类必须同步实现 → JDK 不敢动、开源库不敢动、你也不敢动
        ↓
二十年间接口只能当「一次性合同」：签完就不能改
```

Java 8 引入 Lambda 时撞上了这堵墙：`Collection.forEach`、`List.sort`、`Comparator.comparing`……函数式的组合器**必须**长在既有接口上，否则 Lambda 没有落点。解法就是 **default 方法**——接口自带默认实现，实现类不写就继承，写了就覆盖。

| 对比项 | Java 8 之前 | Java 8 之后（default 方法） |
|--------|------------|---------------------------|
| 接口加方法 | 所有实现类编译报错 | 实现类无感继承默认实现 |
| 接口能力 | 只有抽象契约 | 契约 + 可继承行为 + 静态工厂 |
| 函数式组合器 | 无处安放 | `Comparator.reversed()` 等直接长在接口上 |

> ### 💡 新人小结：default 方法是什么？
>
> 把接口想象成**快递单模板**：
> - 以前模板只有待填格子，每个网点必须自己填满 —— 抽象方法，实现类必须实现
> - default 方法是**模板背面印好的标准附则**：网点不另写就按附则办，写了以网点为准
> - 接口静态方法是**总部直接下发的标准操作规程**：不依赖任何网点，按单号直接办
>
> **一句话总结：default 方法让接口从「一次性合同」变成「可持续修订的合同」。**

**学习路线图**

```
default 基础 → 冲突三规则 → 接口静态方法 → 演进对比 → 函数式基建 → 设计准则 → Q&A
语法与覆盖    菱形怎么办    工厂新家        旧补丁对比   Comparator范本  防滥用    出错怎么办
```

**本文涉及的专有名词**（先解释后使用；SAM、@FunctionalInterface 见《自定义函数接口与高阶函数》）：

| 术语 | 全称 | 含义（用自己的话） | 在本文中的角色 |
|------|------|--------------------|----------------|
| 接口演化 | interface evolution | 发布接口后继续给它加方法而兼容旧实现 | default 方法的动机 |
| 菱形继承 | diamond problem | 一个类经两条路径继承到同一个方法，产生歧义 | 冲突三规则的由来 |
| 方法解析 | method resolution | 编译器/JVM 决定「这个调用到底用哪个实现」 | 三规则的判定过程 |
| 伴生工具类 | companion class | 与接口配套的静态工具类（如 Collections） | 演进对比中的旧方案 |

## 核心概念：default 与 static 的语法

```java
public interface DeliveryService {
    // 抽象方法：网点必须实现（占 SAM 名额）
    void deliver(String pkg);

    // default 方法：模板背面的标准附则
    default String track(String pkg) {
        return "默认查询：" + pkg + " 状态为【运输中】";
    }

    // 接口静态方法：总部标准规程，通过接口名直接调用
    static DeliveryService expressOnly() {
        return pkg -> System.out.println("只收 Express：" + pkg);   // 接口也能用 Lambda 实例化
    }
}
```

```java
// ========== 实现类：只写必须写的，default 白拿 ==========
class StandardStation implements DeliveryService {
    @Override
    public void deliver(String pkg) {
        System.out.println("派送：" + pkg);
        // 没重写 track() —— 直接继承接口的默认实现
    }
}

public class Demo {
    public static void main(String[] args) {
        StandardStation station = new StandardStation();
        station.deliver("包裹001");                      // 输出: 派送：包裹001
        System.out.println(station.track("包裹001"));    // 输出: 默认查询：包裹001 状态为【运输中】

        DeliveryService s = DeliveryService.expressOnly();  // 静态工厂：接口名直接调用
        s.deliver("包裹002");                            // 输出: 只收 Express：包裹002
    }
}
```

**参数解释**：

| 成员 | 调用方式 | 能否重写 | 占用 SAM 名额 |
|------|---------|---------|--------------|
| 抽象方法 | 实例调用 | 必须实现 | 占用 |
| `default` 方法 | 实例调用（`实例.track()`） | 可选重写 | 不占用 |
| `static` 方法 | **接口名**调用（`接口.expressOnly()`） | 不参与继承，不能被实现类重写 | 不占用 |

**注意**：接口静态方法只能通过 `接口名.方法()` 调用——**实现类不会继承它**，这一点与类的静态方法继承行为不同，编译器不提供多态。

## 主体内容

### 冲突三规则：菱形继承怎么办

一个类可以implements多个接口，两个接口又可能提供同名 default 方法——菱形由此产生。Java 8 给出**三条解析规则**，按顺序判定：

```text
规则 1（类胜于接口）：类或父类中的具体方法 优先于 任何接口的 default 方法
规则 2（更具体者胜）：子接口的 default 覆盖 父接口的 default
规则 3（都不让步时）：两个接口的 default 冲突 → 编译报错，必须显式选择
```

**规则 1：类的方法永远赢（甚至赢 Object 的方法）。**

```java
interface Greeter {
    default String hello() { return "接口默认问候"; }
}

class Base { public String hello() { return "父类问候"; } }   // 具体方法

class Child extends Base implements Greeter { }
// Child 的 hello() = "父类问候" —— 规则 1，无需任何显式声明
// 同理：任何接口 default 的 toString 都赢不过 Object.toString
```

**规则 2：更具体的子接口覆盖。**

```java
interface A { default String hello() { return "A"; } }
interface B extends A { default String hello() { return "B"; } }   // 子接口覆盖
class Impl implements B { }
// Impl 的 hello() = "B" —— 规则 2：B 比 A 具体且是 default 来源
```

**规则 3：真冲突时必须显式仲裁。**

```java
interface A { default String hello() { return "A"; } }
interface B { default String hello() { return "B"; } }

// ❌ class Both implements A, B { }
//    编译错误：class Both inherits unrelated defaults for hello() from types A and B

class Both implements A, B {
    @Override
    public String hello() {
        return A.super.hello() + "+" + B.super.hello();   // ✅ 显式指定：接口名.super.方法()
    }
}
```

**参数解释**：`A.super.hello()` 读作「按 A 接口的 default 实现来执行」——这不是调用父类，而是从两个接口的 default 中**点名一个**。三规则的核心直觉：**类的能力 > 更具体接口的能力 > 需要人仲裁的平局**。

> ### 💡 新人小结：三规则像什么？
>
> 像快递纠纷的**仲裁流程**：
> - 网点自己有规程 → 按网点的（类胜于接口）
> - 网点没规程、省区细则比总部细则具体 → 按省区的（子接口胜）
> - 两个平级总部规程打架 → 总部必须拍板指定一个（显式 `接口名.super.方法()`）
>
> **一句话总结：先问类，再问更具体的接口，最后人类拍板——三步走完必有结论。**

### 接口静态方法：伴生工具类的「收编」

Java 8 之前，接口的配套工具只能放在**伴生类**里（`Collection` ↔ `Collections`、`List` ↔ `Lists`）。Java 8 起静态方法直接长在接口上：

```java
// ========== 旧习惯：工具类里找方法 ==========
Collections.sort(list, comparator);        // 伴生类静态方法
Collections.unmodifiableList(list);        // 满屏 Collections.xxx

// ========== 新习惯：方法归位到接口 ==========
list.sort(comparator);                     // List 的 default 方法（Java 8）
Comparator<String> natural = Comparator.naturalOrder();          // 接口静态工厂
Comparator<String> byLen  = Comparator.comparing(String::length); // 接口静态工厂
```

**参数解释**：

| 归位方式 | 例子 | 好处 |
|----------|------|------|
| 行为归位为 default | `list.sort(...)`、`collection.stream()` | 在对象上直接调用，IDE 补全即文档 |
| 工厂归位为接口 static | `Comparator.comparing(...)` | 「造比较器」这件事在比较器接口上找，不用记忆工具类 |

**注意 Java 8 边界**：`List.of(...)`、`Set.of(...)` 这类接口静态工厂是 Java 9 才有的；Java 8 中建不可变列表仍用 `Collections.unmodifiableList(Arrays.asList(...))`。

### 演进对比：伴生抽象类 vs default 方法

Java 8 之前想给接口「预置实现」，标准做法是**配套抽象类**（`List` ↔ `AbstractList`、`Map` ↔ `AbstractMap`）。用「给遍历加默认行为」统一对比：

**旧方案：抽象骨架类。**

```java
// ========== 旧方案：接口 + 骨架抽象类，实现类必须二选一地继承 ==========
interface OldIterable<T> { java.util.Iterator<T> iterator(); }

abstract class AbstractOldIterable<T> implements OldIterable<T> {
    public void forEach(java.util.function.Consumer<? super T> action) {   // 预置实现
        for (java.util.Iterator<T> it = iterator(); it.hasNext(); ) { action.accept(it.next()); }
    }
}

class MyBag<T> extends AbstractOldIterable<T> { ... }   // 被迫占用唯一的 extends 名额
// 若 MyBag 还需要继承别的类 → 骨架能力拿不到，只能自己手写 forEach
```

**当前方案：接口 default 方法。**

```java
// ========== 当前方案（Java 8 实际做法，Iterable 就是这么演化的） ==========
interface NewIterable<T> {
    java.util.Iterator<T> iterator();
    default void forEach(java.util.function.Consumer<? super T> action) {
        for (java.util.Iterator<T> it = iterator(); it.hasNext(); ) { action.accept(it.next()); }
    }
}

class MyBag<T> implements NewIterable<T> { ... }   // extends 名额保住了，forEach 白拿
```

**对比分析表**：

| 对比维度 | 旧方案：骨架抽象类 | 当前方案：default 方法 |
|----------|-------------------|----------------------|
| 写法差异 | 需要「接口 + 抽象类」两件套，实现类必须继承骨架 | 一份接口文件内完成，实现类只管 implements |
| 行为差异（单继承限制） | 骨架占用唯一的 extends；多重继承场景能力丢失 | 不占 extends 名额，任何实现类无成本获得默认行为 |
| 行为差异（演化） | 骨架类自身演化同样要兼容子类，问题只是被推迟 | 新增 default 全体实现类即时受益（如 JDK 8 的 `stream()`） |
| 行为差异（菱形风险） | 类单继承无菱形 | 引入三规则与显式仲裁成本（本文冲突三规则） |
| 迁移成本 | — | 大型接口加 default 仍需评估「默认实现是否对所有实现类正确」 |
| 旧方案适用场景 | 需要为骨架**持有状态字段**时（接口无字段，default 无法替代） | 为无状态的行为/组合器提供默认实现 |

结论：default 方法取代的是骨架类的「**行为预置**」职能；一旦需要字段与状态，抽象类仍不可替代——两者是分工，不是替代。

### 与函数式编程的关系：default 是 Lambda 的基建

回看整个函数式目录，组合器体系全部踩在 default/static 之上：

```text
Lambda 要好用 → 标准函数接口要自带组合能力 → andThen/compose/and/or/negate 长在接口上
        ↓ 只能是 default/static（接口不能要求实现类去写组合器）
Comparator.reversed()（default）、Comparator.comparing（static）、
Iterable.forEach（default）、Collection.stream()（default）
        ↓
「接口 = SAM 最小核心 + default 组合器 + static 工厂」成为 Java 8 之后 API 设计范式
```

这正是《自定义函数接口与高阶函数》中 `RiskRule.and(...)`、`Validator.rule(...)` 的设计依据：**组合器放 default，工厂放 static，SAM 保持单一**。

## 官方 / 社区实践

```java
// ========== Comparator：default + static 的满分范本（同《自定义函数接口》） ==========
Comparator<User> c = Comparator.comparing(User::getAge)   // static 工厂
        .thenComparing(User::getName)                     // default 组合器
        .reversed();                                      // default 组合器

// ========== Iterable.forEach：接口演化的标志性一役 ==========
names.forEach(n -> System.out.println(n));   // 全世界集合无感获得，零实现类改动

// ========== Collection.stream()/removeIf：函数式的入场券 ==========
names.stream().filter(s -> s.length() > 3);  // stream() 本身就是 default 方法
```

**参数解释**：`stream()` 是 default 方法意味着**任何自定义集合自动具备流能力**——不需要继承任何基类。这是 default 方法「能力平权」价值的最佳注脚。

社区实践中，MyBatis-Plus 的 `Wrapper` 接口、JDK 后续版本的 `Map.getOrDefault`（Java 8）/`Map.computeIfAbsent`（Java 8），都是沿「default 扩能力」路线生长的接口 API。

## 高频问题与踩坑排查（Q&A）

**Q1：default 方法能被 Lambda 实现吗？**

不能。Lambda 只负责实现接口的**抽象方法**；default 方法是接口自带的，所有实例直接共享。这也是为什么函数接口要保持 SAM 纯度——default 越多，Lambda 需要写的东西越少，而不是越多。

**Q2：实现两个接口都有同名 default，又不想仲裁怎么办？**

没有「都保留」的选项——规则 3 强制显式选择。折中做法是在实现类里写一个合并实现（如 `A.super.hello() + B.super.hello()`），或重新审视接口划分是否合理。**编译错误是设计问题的警报，不是语法麻烦**。

**Q3：接口 static 方法为什么实现类不能用类名直接调？**

接口静态方法属于接口本身，不参与继承（设计上避免「实现类成为静态方法的伪命名空间」）。想用就得写 `接口名.方法()`。这与类的 static 方法「子类也能以子类名调用」不同。

**Q4：default 方法里能用 `synchronized` 或给实现加 `final` 吗？**

都不能——接口方法（含 default）不能声明 `final`、`synchronized`、`protected`。深层原因：接口不持有锁对象与状态，同步语义应由**持有状态的实现类**负责。default 方法设计上就应该是**无状态的纯行为**。

**Q5：default 方法会破坏「接口是纯抽象」的编程习惯吗？**

会带来新风险：default 实现「悄悄」成为所有实现类的行为，若默认实现依赖了不该依赖的细节（如调用顺序假设），实现类无感继承后埋雷。准则：default 方法体只调用接口自身的抽象方法（像 `forEach` 只调 `iterator()`），不引入魔法默认值。

---

**Q6：接口能有字段吗？default 方法运行时的 `this` 是什么？**

接口只能有 `public static final` 常量（编译器隐式修饰），**没有实例字段**——default 方法里的 `this` 指向**运行时的实现类实例**。这决定了 default 方法只能通过 this 调用接口的其他抽象方法/default 方法（派发到实现类的真实行为），不能像抽象类那样依赖字段状态。理解了这一点，也就理解了 Q4 中「default 不能 synchronized」的根源：没有字段，就没有锁对象。

**Q7：实现类重写 default 方法时，还能「借用」接口的默认实现吗？**

能，语法与菱形仲裁相同——方法体内用 `接口名.super.方法()`：

```java
class PriorityStation implements DeliveryService {
    @Override
    public String track(String pkg) {
        String base = DeliveryService.super.track(pkg);   // 先复用默认实现
        return "[优先件] " + base;                          // 再做增强
    }
}
// 输出: [优先件] 默认查询：包裹001 状态为【运输中】
```

这是「装饰式重写」：默认实现不再是只能整体抛弃的备胎，而成了可组合的积木。注意该语法只在**实现类或子接口内部**可用——外部代码只能看到重写后的最终版本。

**Q8：接口 static 方法能被 Lambda / 方法引用用起来吗？**

能。`java.util.function.Supplier<DeliveryService> factory = DeliveryService::expressOnly;` 是合法的静态方法引用——接口静态方法除了调用方式受限（必须 `接口名.方法()`），其余待遇与类静态方法无异。组合起来正好构成「工厂 + 产品」的最小闭环：接口自己提供工厂，实现类负责产品。

## 要点总结

1. **default 方法解决接口演化困境**：新方法带默认实现，全体实现类无感继承——Lambda 与组合器得以长进 JDK 既有接口。
2. **冲突三规则**：类方法 > 更具体接口的 default > 强制显式仲裁（`接口名.super.方法()`）。
3. **接口静态方法**：通过接口名调用、不参与继承，是伴生工具类方法的「归位」；Java 8 的 `Comparator.comparing` 是标配范例。
4. **default ≠ 抽象类的替代**：无状态行为归接口，有字段有状态归抽象类，按职责分工。
5. **设计范式**：`接口 = 单一 SAM + default 组合器 + static 工厂`——自定义函数接口照此结构设计。

> ### 💡 新人小结：default 方法学完了，记住这 3 点
>
> 1. **模板背面印附则，网点不写也能办** —— default 让接口能安全演化
> 2. **纠纷按三步仲裁**：问类、问更具体的接口、人类拍板
> 3. **组合器的家在接口上** —— andThen/reversed/comparing 全是 default/static，这是函数式 API 的标准长相
>
> **一句话总结：default 方法打通了「接口只管契约、不管行为」的旧世界，让行为可以随接口一起发布。**
