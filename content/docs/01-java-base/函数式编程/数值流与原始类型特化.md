# 为什么需要数值流？

用泛型流做数值计算，会遇到两层尴尬：

**尴尬一：泛型流没有 `sum()`。**

```java
// ========== 泛型流：求和只能绕行归约 ==========
java.util.List<Integer> weights = java.util.Arrays.asList(12, 5, 30);

int total = weights.stream().reduce(0, Integer::sum);        // 绕：手动归约
int total2 = weights.stream().mapToInt(n -> n).sum();        // 绕：转数值流才能 sum()
```

`Stream<Integer>` 的方法集里根本没有 `sum`/`average`——因为流里是「对象」，库无法假设对象能做加法。

**尴尬二：每个数字都是一个对象（装箱）。**

```text
泛型流的每个元素：
    int 12（栈上 4 字节） → 装箱 → Integer 对象（堆上 16 字节 + GC 管理）
        ↓
一百万个元素 ≈ 一百万个 Integer 对象：内存膨胀 4 倍以上，计算时再逐个拆箱
```

根因是 Java 泛型的历史约束：**泛型参数只能是引用类型**（类型擦除机制下 `Stream<int>` 不存在），数值进泛型流必然装箱。Java 8 的解法是**原始类型特化**——为 int/long/double 修三条专用通道：

```java
// ========== 数值流：数字以原始类型直接流动，零装箱 ==========
int total = weights.stream()          // Stream<Integer>
        .mapToInt(n -> n)             // 换乘 IntStream —— 拆箱只发生一次
        .sum();                       // 数值流原生支持 sum
```

| 对比项 | `Stream<Integer>` 泛型流 | `IntStream` 数值流 |
|--------|--------------------------|--------------------|
| 元素形态 | Integer 对象（堆分配） | int 原始值（栈/寄存器） |
| `sum()/average()` | 无，需 reduce 绕行 | 原生提供 |
| 内存（百万元素） | 约 16MB+ 对象头开销 | 约 4MB 原始数组 |
| 适用数据 | 业务对象流 | 纯数值计算流 |

> ### 💡 新人小结：数值流是什么？
>
> 泛型流像**把每颗螺丝钉单独装进小纸箱再上流水线**——通用，但每个箱子都有包装成本（装箱）。
> 数值流是**标准托盘**：int/long/double 三种高频散货直接裸装运输。
> - 上托盘的动作 = `mapToInt`/`mapToLong`/`mapToDouble`
> - 托盘专属工具 = `sum`/`average`/`summaryStatistics`/`range`
>
> **一句话总结：数值流 = 泛型流 + 脱掉包装（去装箱）+ 补上数值专属操作。**

**学习路线图**

```
装箱之痛 → 三大数值流 → 创建方式 → 专属操作 → boxed 往返 → 演进对比 → Q&A
对象代价    Int/Long/Double  上带五种姿势   sum/range/统计  回对象世界  泛型流对比  出错怎么办
```

**本文涉及的专有名词**（先解释后使用；可变归约、幺元见《Stream终端操作与归约》）：

| 术语 | 全称 | 含义（用自己的话） | 在本文中的角色 |
|------|------|--------------------|----------------|
| 装箱 / 拆箱 | boxing / unboxing | int ↔ Integer 的自动包装与拆包 | 泛型流的隐性成本 |
| 原始类型特化 | primitive specialization | 为 int/long/double 各做一套非泛型接口 | 数值流的设计手法 |
| 类型擦除 | type erasure | 泛型信息编译后被擦除，运行期只有原始类型 | 「为什么没有 Stream\<int\>」的根源 |
| 区间 | range | 从起值到止值的连续整数序列 | `range`/`rangeClosed` 的语义 |

## 核心概念：三大数值流与换乘站

```text
Stream<T>（泛型流）
   ├── mapToInt(IntFunction)     → IntStream     ↔ boxed()/mapToObj → 回对象流
   ├── mapToLong(ToLongFunction) → LongStream    ↔ boxed()/mapToObj
   └── mapToDouble(ToDoubleFunction) → DoubleStream ↔ boxed()/mapToObj

IntStream ──asLongStream()──→ LongStream ──asDoubleStream()──→ DoubleStream（单向拓宽，防溢出）
```

**换乘规则**：

| 方法 | 方向 | 说明 |
|------|------|------|
| `mapToInt/mapToLong/mapToDouble` | 对象流 → 数值流 | 元素从包装类型换成原始类型 |
| `boxed()` / `mapToObj` | 数值流 → 对象流 | 需要对象 API、收集进 `List<Integer>` 时换乘回来 |
| `asLongStream()/asDoubleStream()` | 数值流之间拓宽 | int 累计防溢出升 long，见 Q&A |

## 主体内容

### 五种创建方式：数值流怎么上带

```java
import java.util.stream.*;

public class CreateNumeric {
    public static void main(String[] args) {
        // 1. 数组直达：Arrays.stream 对原始类型数组直接产出数值流
        IntStream s1 = java.util.Arrays.stream(new int[]{12, 5, 30});

        // 2. range / rangeClosed：区间生成（半开 / 闭区间）
        IntStream s2 = IntStream.range(1, 5);         // 1,2,3,4（不含 5）
        IntStream s3 = IntStream.rangeClosed(1, 5);   // 1,2,3,4,5（含 5）

        // 3. of 零散元素
        IntStream s4 = IntStream.of(12, 5, 30);

        // 4. generate / iterate：无限流（与泛型流同规则，必须短路）
        IntStream s5 = IntStream.iterate(1, n -> n * 2).limit(5);   // 1,2,4,8,16

        // 5. Random.ints：随机数流（Java 8 新增的随机源流）
        IntStream s6 = new java.util.Random().ints(3, 0, 100);     // 3 个 [0,100) 随机数

        System.out.println(s2.boxed().collect(Collectors.toList())); // 输出: [1, 2, 3, 4]
        System.out.println(s3.sum());   // 输出: 15
        s5.forEach(n -> System.out.print(n + " "));   // 输出: 1 2 4 8 16
        System.out.println();
        s6.forEach(n -> System.out.print(n + " "));   // 输出: 随机 3 个数
    }
}
```

**参数解释**：

| 方式 | 签名要点 | 坑 |
|------|---------|-----|
| `Arrays.stream(int[])` | 直接得 `IntStream` | `Integer[]` 得到的是 `Stream<Integer>`（对象数组按对象处理） |
| `range(b, e)` / `rangeClosed(b, e)` | 半开 `[b, e)` / 闭 `[b, e]` | 差 1 事故高发：循环 n 次用 `range(0, n)`，含末值用 `rangeClosed` |
| `Random.ints(count, origin, bound)` | 指定个数与范围 | 无参 `ints()` 是无限流 |

### 数值流专属操作：泛型流没有的「原生待遇」

```java
public class NumericOps {
    public static void main(String[] args) {
        int[] weights = {12, 5, 30};
        IntStream s = java.util.Arrays.stream(weights);

        // 1. sum：直接返回值；空流返回 0（加法幺元兜底）
        System.out.println(s.sum());                       // 输出: 47

        // 2. max/min：返回 OptionalInt —— 空流「无最值」语义显式化
        java.util.OptionalInt max = java.util.Arrays.stream(weights).max();
        System.out.println(max.getAsInt());                // 输出: 30

        // 3. average：返回 OptionalDouble（空流无均值）
        java.util.OptionalDouble avg = java.util.Arrays.stream(weights).average();
        System.out.println(avg.getAsDouble());             // 输出: 15.666666666666666

        // 4. summaryStatistics：一次归约全拿（替代四段 reduce）
        IntStream statsSrc = java.util.Arrays.stream(weights);
        IntSummaryStatistics stat = statsSrc.summaryStatistics();
        System.out.printf("max=%d min=%d sum=%d avg=%.1f count=%d%n",
                stat.getMax(), stat.getMin(), stat.getSum(), stat.getAverage(), stat.getCount());
        // 输出: max=30 min=5 sum=47 avg=15.7 count=3
    }
}
```

**参数解释**：

| 操作 | 返回类型 | 空流行为 |
|------|---------|---------|
| `sum()` | int/long/double | 返回 0（加法幺元，天然兜底） |
| `max()/min()` | `OptionalInt/Long/Double` | `Optional.empty()`——「没有元素就没有最值」 |
| `average()` | `OptionalDouble` | `Optional.empty()` |
| `summaryStatistics()` | `IntSummaryStatistics` 等 | 全零统计对象 |

`sum` 有幺元兜底、`max` 没有——这与《Stream终端操作与归约》reduce 单参/双参的分野完全一致：**有自然零值的操作直接出值，没有的返回 Optional**。

### 业务对象流的典型换乘：mapToInt 首位

业务开发里数值流最常见的入口是**从对象流提取数值字段**：

```java
// 订单金额合计：一次换乘，全程原始类型
double total = orders.stream()
        .mapToDouble(Order::getAmount)     // 换乘 DoubleStream
        .sum();

// 金额最高的订单：数值流算出极值，再回对象世界找订单（两段式）
double maxAmount = orders.stream()
        .mapToDouble(Order::getAmount)
        .max()
        .orElse(0.0);

// 收集到 List<Integer>：boxed 回对象世界
List<Integer> weightList = java.util.Arrays.stream(weights)
        .boxed()                           // IntStream → Stream<Integer>
        .collect(Collectors.toList());
```

**参数解释**：`mapToInt(ToIntFunction<T>)` 的函数返回 int——`Order::getAmount` 若返回 Double 包装类型，注意方法引用匹配的是 `doubleValue()` 层级的拆箱（一次），随后全程无装箱。`boxed()` 与 `mapToObj(IntFunction<R>)` 等价，后者还能在回程顺便转换（`mapToObj(n -> "包裹" + n)`）。

> ### 💡 新人小结：换乘像什么？
>
> - `mapToInt` = **散货上托盘**：对象脱壳成裸数字，后续零包装成本
> - `boxed`/`mapToObj` = **托盘换纸箱**：要进对象世界的仓库（List、对象 API）时才换
> - `summaryStatistics` = **托盘一次过磅**：max/min/sum/avg/count 一张单全出
>
> **一句话总结：数值字段一进场就换乘数值流，只在需要对象 API 时再换回来。**

### 演进对比：泛型流 vs 数值流

统一场景：订单金额合计 + 平均值。

**旧方案：泛型流绕行。**

```java
// Stream<Double>（装箱流）：sum 缺席，只能手动归约
Double total = orders.stream()
        .map(Order::getAmount)                     // Stream<Double>，每个元素都是包装对象
        .reduce(0.0, Double::sum);                 // 手动归约补上 sum

double avg = orders.size() == 0 ? 0 :
        orders.stream().mapToDouble(Order::getAmount).average().orElse(0);
```

**当前方案：一次换乘数值流。**

```java
DoubleSummaryStatistics stat = orders.stream()
        .mapToDouble(Order::getAmount)
        .summaryStatistics();                      // sum/avg/min/max/count 一次全出
double total2 = stat.getSum();
```

**对比分析表**：

| 对比维度 | 旧方案：泛型流绕行 | 当前方案：数值流特化 |
|----------|-------------------|---------------------|
| 写法差异 | reduce 手补 sum、判空手写 | `sum()/summaryStatistics()` 一词到位 |
| 行为差异（内存） | 每元素一个包装对象，大集合 GC 压力显著 | 原始值直排，无对象分配 |
| 行为差异（表达力） | 统计口径要逐个 reduce 拼装 | summaryStatistics 一趟全出 |
| 迁移成本 | — | 需记住三套 Optional 返回类型（OptionalInt 等） |
| 旧方案适用场景 | 元素本就是业务对象、数值只是顺手一算的小集合 | 纯数值计算、大集合聚合、报表统计 |

结论：数值流的价值随**数据量**放大——千级集合以可读性优先，万级以上的数值聚合应默认走特化通道；但**不要退回 for 循环**：`IntStream.range(0, n).sum()` 经 JIT 内联后与手写 for 几乎同速，声明式不需要性能赎金。

## 官方 / 社区实践

```java
// ========== 1. IntStream.range 替代传统 for 下标遍历（声明式下标） ==========
java.util.List<String> stations = java.util.Arrays.asList("华东站", "华南站", "华北站");
IntStream.range(0, stations.size())
         .forEach(i -> System.out.println((i + 1) + ". " + stations.get(i)));
// 输出: 1. 华东站   2. 华南站   3. 华北站

// ========== 2. String.chars 处理字符（Java 8：字符按 int 流出） ==========
String manifest = "aabbc";
long aCount = manifest.chars().filter(c -> c == 'a').count();
System.out.println(aCount);    // 输出: 2

// ========== 3. Random.ints 造测试数据 ==========
List<Integer> mockWeights = new java.util.Random().ints(10, 1, 100)
        .boxed().collect(Collectors.toList());
```

**参数解释**：`chars()` 返回 IntStream（字符就是 int 的 UTF-16 码点）——字符统计、校验位计算类需求从此一行流；`range` 版下标遍历保留索引语义，又享受链式与短路能力，是「for i 情结」的声明式出口。

## 高频问题与踩坑排查（Q&A）

**Q1：为什么没有 `Stream<int>`？**

泛型经类型擦除后运行期只有引用类型，JVM 字节码层面的泛型容器装不下原始值——这是 Java 泛型的历史设计，不是 Stream 偷懒。JDK 的应对就是原始类型特化：为 int/long/double 三个高频类型手写非泛型接口家族（`IntStream` 等），其余类型（short/byte/char/float）统一升位到 int/double 处理。

**Q2：`sum()` 空流返回 0，`max()` 空流却返回 Optional，为什么不统一？**

因为「零个数的和」有自然定义（加法幺元 0），「零个数的最大值」没有（对任意答案都能反驳）。与 reduce 双参/单参的分野一致：**有幺元出值，无幺元出 Optional**。`average` 因分母为 0 无定义，同样出 OptionalDouble。

**Q3：range 和 rangeClosed 总是差 1，有稳妥的记法吗？**

绑定语义记：`range(1, n)` = 数学半开区间 `[1, n)`，元素个数 `n-1`；`rangeClosed(1, n)` = 闭区间 `[1, n]`，元素个数 n。遍历「第 0 到 n-1」用 `range(0, n)`，遍历「1 到 n 次编号」用 `rangeClosed(1, n)`。写完用 `count()` 抽查一次即可锁死习惯。

**Q4：IntStream 求和会溢出吗？**

会。int 上限约 21 亿，大额累加（如毫秒时间戳之和）悄悄溢出为负。防溢出手法：换乘 long 通道——`intStream.asLongStream().sum()`，或源头就用 `LongStream`。Double 同理存在精度问题，金额计算建议换 BigDecimal 通道（`mapToObj` 出对象后归约）。

**Q5：装箱到底有多贵？需要 JMH 压测才能决定吗？**

量级感受：Integer 对象约 16 字节（含对象头）vs int 4 字节；千万级集合装箱引入千万次堆分配与 GC 压力。经验法则先行：**万级以上纯数值聚合用数值流**；千级以下业务流按可读性选泛型流即可，不必上基准测试工具。

**Q6：`mapToInt(Order::getAmount)` 编译不过，为什么？**

方法引用匹配 `ToIntFunction<Order>` 要求返回 int。`getAmount` 若返回 `Double`（包装类型），自动拆箱不发生在「方法引用匹配」这一步——改用 `mapToDouble(Order::getAmount)` 匹配 Double，或把实体字段设计为原始类型（实体字段用包装类型的初衷是「可空」，金额这类必有值字段用 double 更顺）。

**Q7：`summaryStatistics()` 对空流返回什么？里面的 max/min 是 0 吗？**

不是 0——空流返回**全零统计对象**：`count=0`、`sum=0`，但 `max=Integer.MIN_VALUE`、`min=Integer.MAX_VALUE`（没有元素可比，初值停在类型极值上）。判断「有没有数据」必须用 `stat.getCount() == 0`，看 max/min 是否为 0 会踩出隐蔽 bug。

**Q8：`DoubleStream` 能用来算金额吗？**

能跑但**不该用**：二进制浮点无法精确表示 0.1 这类十进制小数，`0.1 + 0.2 = 0.30000000000000004` 的经典误差在归约累加中不断放大。金额计算两条正路：①以**最小货币单位（分）**建模，走 `LongStream`；②回对象世界用 `BigDecimal` 归约。数值流擅长的是「量纲无关的数」（次数、字节数、权重），不是钱。

```java
// ❌ DoubleStream 累加金额：误差随笔数放大
java.util.List<java.math.BigDecimal> amounts =
        java.util.Arrays.asList(new java.math.BigDecimal("0.10"), new java.math.BigDecimal("0.20"));
double bad = amounts.stream().mapToDouble(java.math.BigDecimal::doubleValue).sum();

// ✅ 以分为单位走 LongStream（movePointRight(2) 即元转分，longValueExact 防溢出截断）
long cents = amounts.stream()
        .mapToLong(a -> a.movePointRight(2).longValueExact())
        .sum();
```

**冷知识：装箱缓存的错觉**

小数据下装箱流「看起来」毫无开销，是个温柔的陷阱：

```java
java.util.List<Integer> small = java.util.Arrays.asList(1, 2, 3);
int s = small.stream().mapToInt(n -> n).sum();   // 与 Stream<Integer> 归约的差距：测不出来
```

原因：`Integer.valueOf` 对 **-128 ~ 127** 的值返回**缓存的同一个对象**——小数值装箱根本不分配新对象。于是「装箱很慢」在小数据演示里无法复现，容易被当成谣言。数据一上万，缓存不再命中，堆分配与 GC 压力立刻现形（回顾本文开头一百万 Integer 的内存账单）。缓存上限可用 `-XX:AutoBoxCacheMax` 调整——但正确姿势永远是：数值计算直接走特化通道，不依赖缓存兜底。

**Q9：`chars()` 出来的 IntStream 能优雅地转回 String 吗？**

没有现成的收集器可用（`Collectors.joining` 只对 `CharSequence` 流），要走可变归约三板斧：

```java
String noSpace = "AB C 123".chars()
        .filter(c -> c != ' ')
        .collect(StringBuilder::new, StringBuilder::appendCodePoint, StringBuilder::append)
        .toString();
System.out.println(noSpace);   // 输出: ABC123
```

`appendCodePoint` 按 Unicode 码点追加，中文等增补字符也安全——比强转 `(char) c` 稳。这类「数值流 ↔ 字符」的往返正是 `chars()` 的定位：字符当 int 处理，处理完再拼回去。

## 要点总结

1. **装箱是泛型流的隐性税**：int 4 字节 vs Integer 16 字节 + GC 压力；根因是泛型只认引用类型。
2. **三大数值流**：`IntStream`/`LongStream`/`DoubleStream`，由 `mapToInt` 系换乘，`boxed`/`mapToObj` 换回。
3. **专属操作**：`sum`/`average`/`max`/`min`/`summaryStatistics`/`range`；有幺元的出值，无幺元的出 Optional。
4. **区间两兄弟**：`range` 半开、`rangeClosed` 闭区间；`chars()` 让字符按 int 流动。
5. **量级决策**：万级以上数值聚合默认特化；声明式下标遍历（`range`）与 for 同速，不必为性能退回循环。

> ### 💡 新人小结：数值流学完了，记住这 3 点
>
> 1. **散货别装纸箱** —— 数值字段一进场就 `mapToInt/mapToDouble` 换托盘
> 2. **一次过磅省四趟** —— 统计口径多于一个时直上 `summaryStatistics`
> 3. **空箱有讲究** —— sum 空流是 0（幺元兜底），max 空流是 Optional（无幺元）
>
> **一句话总结：数值流是泛型流的「裸装通道」——脱掉包装、补上算术，大数据聚合不再付装箱税。**
