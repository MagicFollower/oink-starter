# 为什么需要自定义函数接口？

JDK 自带 42 张「标准快递单」（`java.util.function` 全家），覆盖了绝大多数场景。但用久了会遇到三个格子对不上的瞬间：

**缺口一：标准接口不认「特殊审批栏」（受检异常）。**

```java
// ========== 想在 Function 里调用一个声明了 IOException 的方法 ==========
static String loadConfig(String path) throws IOException { ... }   // 受检异常

Function<String, String> loader = p -> loadConfig(p);
// ❌ 编译错误：unreported exception IOException; must be caught or declared to be thrown
//    Function.apply 没有声明 throws，Lambda 体必须就地吞掉异常
```

**缺口二：领域语义丢失。**

```java
Function<Order, Boolean> rule = o -> o.getAmount() > 10000 && o.isVip();
// ❌ 问题：函数类型看不出这是「大额 VIP 订单风控规则」
//    100 个地方写 100 个 Function，读代码的人无法知道哪个 Function 承载业务规则
```

**缺口三：需要「函数生成函数」。**

```java
// 想预配置运费率：makeRate(0.9) 得到一个「打九折」的新函数，makeRate(0.8) 得到另一个
// Function 只有单层签名，怎么表达「配置一个函数」这件事？
```

三个缺口的共同解法：**自己设计函数接口**——只要守住「单一抽象方法」这条底线，任何接口都能接 Lambda。本文讲清楚怎么设计、怎么兜住异常、怎么玩转「函数的函数」。

| 对比项 | 只用标准接口 | 标准 + 自定义函数接口 |
|--------|-------------|----------------------|
| 异常处理 | Lambda 体内到处 try-catch | 接口签名直接声明异常 |
| 领域语义 | `Function<Order,Boolean>` 无业务含义 | `RiskRule` 一眼看出用途 |
| 函数工厂 | 表达不了 | 柯里化/部分应用 |

> ### 💡 新人小结：什么时候自己印快递单？
>
> 标准快递单（42 个接口）是通用格式，三种情况需要**自己印单**：
> - 货物需要特殊审批栏（方法要抛受检异常）—— 异常友好接口
> - 单子上的名字必须体现业务（不能都叫「格式单」）—— 领域命名接口
> - 需要「用单子印单子」（函数生成函数）—— 柯里化与高阶设计
>
> **一句话总结：先翻标准单，标准单不够才自定义——自定义的每一张单都要有存在的理由。**

**学习路线图**

```
设计契约 → 异常友好接口 → 柯里化 → 组合管道 → 演进对比 → 设计准则 → Q&A
@FunctionalInterface  Throwing家族  函数生成函数  校验流水线   try-catch对比  防过度设计  出错怎么办
```

**本文涉及的专有名词**（先解释后使用；SAM、目标类型见《Lambda表达式详解》）：

| 术语 | 全称 | 含义（用自己的话） | 在本文中的角色 |
|------|------|--------------------|----------------|
| 柯里化 | Currying | 把「多参数函数」改造成「每次吃一个参数、返回新函数」的链条 | 函数工厂的实现手法 |
| 部分应用 | partial application | 预先固定一部分参数，得到一个「参数更少的新函数」 | 柯里化的实用目的 |
| 包装器 | adapter/wrapper | 包住原接口做类型转换的一层薄壳 | unchecked 转换器的实现方式 |
| 骨架实现 | skeletal implementation | 接口配套的抽象类，提供部分公共实现 | Comparator 就是官方骨架范本 |

## 核心概念：@FunctionalInterface 是契约不是开关

先纠正一个常见误解：**不写 `@FunctionalInterface`，单抽象方法接口同样能接 Lambda**。这个注解不产生任何运行时行为，它的价值是**契约**：

```java
// ========== 自定义领域接口：风控规则 ==========
@FunctionalInterface
public interface RiskRule {
    boolean check(Order order);                 // 唯一抽象方法 —— Lambda 的落点

    // ✅ default 方法不计入 SAM 约束
    default RiskRule and(RiskRule other) {
        return order -> this.check(order) && other.check(order);
    }

    // ✅ static 方法同样不计入
    static RiskRule alwaysPass() {
        return order -> true;
    }
}

// ✅ 编译器强制检查：加一个抽象方法立刻报错
//    Invalid '@FunctionalInterface' annotation; RiskRule is not a functional interface
```

**参数解释**：

| 成员类型 | 是否占用 SAM 名额 | 说明 |
|----------|------------------|------|
| 抽象方法 | 占用（且必须恰好 1 个） | 接口默认继承的 `Object` 公共方法（`toString` 等）不算 |
| `default` 方法 | 不占 | 组合器放这里（学 Comparator） |
| `static` 方法 | 不占 | 工厂方法、常量规则放这里 |

设计要点：接口名用**领域词汇**（`RiskRule` 而不是 `OrderFunction`），抽象方法名用**动词**（`check`/`apply`/`verify`）——读调用代码时，签名即文档。

## 主体内容

### 异常友好接口：把受检异常写进签名

解决缺口一。思路：设计一个**签名里带 `throws` 的函数接口家族**：

```java
@FunctionalInterface
public interface ThrowingFunction<T, R> {
    R apply(T t) throws Exception;              // 关键差异：签名声明了异常

    // ✅ 转换器：把「会抛异常的函数」包成「普通 Function」
    static <T, R> Function<T, R> unchecked(ThrowingFunction<T, R> fn) {
        return t -> {
            try {
                return fn.apply(t);
            } catch (Exception e) {
                // 兜底翻译：受检异常 → 运行时异常，保持 Lambda 调用面干净
                throw new RuntimeException(e);
            }
        };
    }
}
```

使用效果：

```java
// ========== 旧写法：每个调用点都长一段 try-catch ==========
List<String> configs = paths.stream().map(p -> {
    try {
        return loadConfig(p);
    } catch (IOException e) {
        throw new RuntimeException(e);
    }
}).collect(Collectors.toList());

// ========== 新写法：转换器一次性兜住，业务链保持干净 ==========
List<String> configs2 = paths.stream()
        .map(ThrowingFunction.unchecked(MyConfig::loadConfig))   // 签名带 IOException 的方法直接引用
        .collect(Collectors.toList());
```

**参数解释**：

- `ThrowingFunction`：接口签名允许抛异常，Lambda 体里调用 `loadConfig` 不再需要就地 catch。
- `unchecked(...)`：**包装器方法**，把 throwing 版本适配成 JDK 标准的 `Function`——标准 API（Stream.map 等）只认标准接口，转换器是两者之间的桥。
- 兜底翻译成 `RuntimeException` 是最常见的策略；更讲究的做法是自定义 `BusinessException` 或按异常类型分发，原则是**不要静默吞掉**。

同一思路可复制出 `ThrowingConsumer`、`ThrowingSupplier`、`ThrowingRunnable`，形成异常友好家族。

> ### 💡 新人小结：异常友好接口像什么？
>
> 把受检异常想象成**需要盖章的特种货物**：
> - 标准快递单没有「审批栏」，特种货物根本填不了单 —— Function 签名不允许 throws
> - 自印一张带审批栏的生鲜专递单 —— ThrowingFunction 签名声明异常
> - 再配一个「代办柜台」把特种单翻译成普通单进主流水线 —— unchecked 转换器
>
> **一句话总结：异常不该被消灭在 Lambda 里，而该被设计进接口签名里。**

### 柯里化：函数生成函数

解决缺口三。核心手法：**让函数的返回值本身又是一个函数**。

```java
public class CurryingDemo {
    public static void main(String[] args) {
        // 两参函数的标准形态：BiFunction
        java.util.function.BiFunction<Double, Double, Double> freight =
                (weight, rate) -> weight * rate;

        // 柯里化形态：先吃运费率，返回「只等重量」的新函数
        java.util.function.Function<Double, java.util.function.Function<Double, Double>>
                curriedFreight = rate -> weight -> weight * rate;

        // 部分应用：预配置不同线路的费率，生成一组「成品函数」
        java.util.function.Function<Double, Double> eastRate = curriedFreight.apply(0.9);
        java.util.function.Function<Double, Double> southRate = curriedFreight.apply(0.8);

        System.out.println(eastRate.apply(100.0));   // 输出: 90.0
        System.out.println(southRate.apply(100.0));  // 输出: 80.0
        System.out.println(freight.apply(100.0, 0.9)); // 输出: 90.0（等价的两参调用）
    }
}
```

**参数解释**：

- `rate -> weight -> weight * rate` 从右往左读：内层 `weight -> weight * rate` 是「算一个包裹的运费」；外层 `rate -> (内层函数)` 是「配置一个费率，发一张新函数」。
- `eastRate`/`southRate` 就是**部分应用**的产物——费率已固化，每个站点拿到的是只差重量参数的现成函数。
- 与 `BiFunction` 的本质差别：`BiFunction` 必须**两个参数同时到位**才能执行；柯里化允许**分批到位**，先到位的信息可以被固化。

典型工程落点：日志器工厂（`logFactory(level)` 生成各级别记录函数）、校验器工厂（`rule(message, predicate)` 生成带错误信息的规则）——都是「先给配置，后给数据」。

### 组合管道：用自定义接口搭一条校验流水线

把「领域接口 + 组合器 + 函数工厂」合体，实现一个可扩展的校验管道（责任链的函数式雏形，完整重构见《Lambda重构设计模式》）：

```java
@FunctionalInterface
public interface Validator {
    /** 返回错误信息，通过则返回 null —— 校验语义一目了然 */
    String validate(Order order);

    default Validator and(Validator next) {
        return order -> {
            String first = this.validate(order);
            return first != null ? first : next.validate(order);   // 短路：前一个失败就不再查
        };
    }

    static Validator rule(String message, java.util.function.Predicate<Order> condition) {
        return order -> condition.test(order) ? null : message;    // 函数工厂：规则 + 提示语 → 校验器
    }
}

// ========== 业务装配：规则全部声明为值 ==========
Validator pipeline = Validator.rule("金额必须为正", o -> o.getAmount() > 0)
        .and(Validator.rule("VIP 可免最低消费", o -> o.isVip() || o.getAmount() >= 100))
        .and(Validator.rule("地址必填", o -> o.getAddress() != null));

String error = pipeline.validate(order);
if (error != null) { /* 拒单并提示 error */ }
```

**参数解释**：

- `rule(message, condition)` 是**函数工厂**：用柯里化思想把「规则描述」与「判断逻辑」绑成一个具名校验器。
- `and` 是**组合器**（对齐 Predicate 的用法，但带上了领域错误信息）。
- 新增校验 = 追加一行 `.and(rule(...))`，校验管道的生长成本从「改类」降到「改表达式」。

### 演进对比：内联 try-catch vs 异常友好接口

统一场景：Stream 中逐个加载配置文件（方法声明了 `IOException`）。

**旧方案：每个 Lambda 调用点内联 try-catch。**

```java
List<String> configs = paths.stream().map(p -> {
    try {
        return loadConfig(p);
    } catch (IOException e) {
        throw new RuntimeException(e);            // 同样的四行样板，散落在 N 个调用点
    }
}).collect(Collectors.toList());
```

**当前方案：Throwing 接口 + unchecked 转换器。**

```java
List<String> configs = paths.stream()
        .map(ThrowingFunction.unchecked(MyConfig::loadConfig))   // 方法引用直进，样板集中一处
        .collect(Collectors.toList());
```

**对比分析表**：

| 对比维度 | 旧方案：内联 try-catch | 当前方案：Throwing 接口 |
|----------|----------------------|------------------------|
| 写法差异 | 每个 Lambda 多 4 行包装样板，链式结构被拉断 | 异常处理集中在转换器一处，链面干净 |
| 行为差异（一致性） | 各调用点的异常翻译策略容易漂移（有人吞、有人抛、有人记日志） | 统一出口，异常策略全局一致可审计 |
| 行为差异（异常信息） | 直接 `new RuntimeException(e)` 丢失业务上下文 | 可在转换器统一补充「加载哪份配置失败」等上下文 |
| 迁移成本 | — | 需新建接口 + 团队约定统一走 unchecked 入口 |
| 旧方案适用场景 | 只有一两处调用、异常策略本就各不相同 | 同一类 IO 操作在多个流水线中反复出现 |

结论：内联 try-catch 的成本随调用点数量**线性增长**，而 Throwing 接口把成本**一次性前置**到接口设计上——调用点越多，收益越大。

## 官方 / 社区实践

**`Comparator<T>` 是自定义函数接口的官方满分范本**——把本文所有手法用了个遍：

```java
@FunctionalInterface
public interface Comparator<T> {
    int compare(T o1, T o2);                                  // 唯一抽象方法（SAM）

    default Comparator<T> reversed() { ... }                  // default 组合器
    default Comparator<T> thenComparing(Comparator<? super T> other) { ... }
    static <T, U extends Comparable<? super U>> Comparator<T> comparing(
            Function<? super T, ? extends U> keyExtractor) { ... }   // static 工厂
}
```

**参数解释**：抽象方法只定义「怎么比一对」，组合器与工厂负责「怎么拼装」——正是本文「SAM 最小化 + default/static 补生态」的结构。自己设计接口时，照着 Comparator 的骨架走不会错。

另一个官方先例是 `Callable` 与 `Runnable` 的分工：两者唯一差别就是 `call()` 声明了 `throws Exception`——**用签名区分「会抛异常的任务」与「不会抛的任务」**，正是异常友好接口思路的源头。

社区实践方面，MyBatis-Plus 的 `LambdaQueryWrapper`、Spring Data 的 `Specification`，本质都是「领域函数接口 + 组合器」的工程化放大版；掌握本文的自定义手法，看懂这些框架的 API 设计只是顺带的事。

## 高频问题与踩坑排查（Q&A）

**Q1：不写 `@FunctionalInterface` 行不行？**

行——单抽象方法接口天然能接 Lambda。但强烈建议写：注解让编译器替你守住 SAM 约束，防止后人手滑加第二个抽象方法，导致所有 Lambda 调用点突然编译失败。它是写给「未来维护者」的保险。

**Q2：自定义函数接口可以继承其他接口吗？**

可以，但继承后必须仍然只有**一个**未实现的抽象方法（父接口的抽象方法 + 自己的抽象方法合计为 1）。继承另一个函数接口再加 default 方法是合法且常见的（如 `ThrowingFunction` 继承 `Function` 风格的接口再做适配）。

**Q3：unchecked 转换器会不会把异常「弄丢」？**

不会丢，但要防「吞」。转换器必须显式抛出（或包装后抛出）；真正的危险是有人在转换器里 catch 后只打日志不抛——那才是异常黑洞。代码评审时把 unchecked 实现列为必查项。

**Q4：柯里化链很长（三四个参数）值得吗？**

谨慎。两层柯里化（配置 → 数据）是工程甜点；三层以上可读性急剧下降，调用方要脑内展开嵌套泛型。参数超过三个时优先考虑：参数对象封装、或保留多参方法 + 少量预配置工厂。

**Q5：自定义接口的抽象方法该不该直接抛 `Exception`？**

「异常友好接口」为了通用抛 `Exception` 可以接受，但更精确的设计是声明具体异常类型（`throws IOException`），让调用方的处理范围更小、意图更明确。通用性与精确性按团队规模权衡：小工具从宽，公共库从严。

---

**Q6：自定义函数接口能享受方法引用吗？**

能——方法引用匹配看的是**目标接口的抽象方法签名**，与接口是谁定义的无关：`RiskRule` 的抽象方法是 `boolean check(Order)`，那么 `Order::isVip`、`this::bigOrderCheck` 都能直接当 `RiskRule` 用。这正是「领域接口」路线的隐藏红利：自定义接口免费继承 Lambda、方法引用、组合器的整套生态，调用方几乎无感知成本。

**Q7：自定义接口的抽象方法名必须叫 `apply` 或 `check` 吗？**

完全自由——SAM 判定只看「抽象方法数量」，不看名字。但命名要选**领域动词**（`validate`/`convert`/`render`），因为调用处写的是 `rule.check(order)` 还是 `rule.apply(order)`，直接决定读代码的人看到的是业务语言还是泛型语言。Lambda 的参数名同理：`order -> ...` 永远优于 `x -> ...`。

## 要点总结

1. **@FunctionalInterface 是契约**：不写也能接 Lambda，写了由编译器守住 SAM 约束；default/static 方法不占名额。
2. **异常写进签名**：Throwing 接口家族 + unchecked 转换器，把散落各处的 try-catch 样板收敛到一处。
3. **柯里化 = 函数的返回值还是函数**：先固化配置生成部分应用函数，是「函数工厂」的标准手法。
4. **领域接口 > 通用接口**：`RiskRule`/`Validator` 让签名即文档；Comparator 是官方范本，照骨架设计。
5. **防过度设计**：先查标准 42 接口，确实对不上（异常/语义/工厂需求）才自定义。

> ### 💡 新人小结：自定义接口学完了，记住这 3 点
>
> 1. **自印单的三种理由**：特殊审批栏（异常）、业务抬头（语义）、用单印单（工厂）——没有理由别印
> 2. **审批栏进签名，代办柜台做翻译** —— Throwing 接口 + unchecked，异常处理一次到位
> 3. **先固化配置，后喂数据** —— 柯里化让同一份逻辑长出一族函数
>
> **一句话总结：自定义函数接口的本质，是把「这段业务的特殊性」升格为类型系统的正式成员。**
