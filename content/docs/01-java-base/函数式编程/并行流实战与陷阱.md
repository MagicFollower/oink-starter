# 为什么并行流会「帮倒忙」？

大数据量处理慢，有人告诉你：「加个 `parallel()` 就能并行提速」。于是你照做了，然后遇到三连暴击：

```java
// ========== 事故一：加了 parallel 反而更慢 ==========
java.util.List<Integer> small = new java.util.ArrayList<>();
for (int i = 0; i < 100; i++) { small.add(i); }

long r = small.parallelStream()          // 100 个元素开多线程：线程切换开销 > 计算收益
        .mapToLong(Integer::longValue)
        .sum();

// ========== 事故二：并行 forEach 累加，结果每次都不一样 ==========
java.util.List<Integer> big = new java.util.ArrayList<>();
for (int i = 0; i < 1_000_000; i++) { big.add(1); }

java.util.List<Integer> unsafe = new java.util.ArrayList<>();   // 共享可变容器
big.parallelStream().forEach(unsafe::add);                      // 多线程同时往一个 List 塞
System.out.println(unsafe.size());      // 每次运行输出不同，且远小于 1000000（丢数据 + 偶发异常）
```

**根源**：并行流不是「免费加速器」，而是一套**分治 + 多线程 + 合并**的完整机制——它有自己的适用边界。本文讲清机制、给出测量方法、列全陷阱清单，让你能判断「这一单该不该开多分拣中心」。

| 对比项 | 串行流 | 并行流 |
|--------|--------|--------|
| 执行者 | 调用线程单干 | 公共 ForkJoinPool 多线程分片 |
| 前提 | 无 | 数据量足、可切分、操作无共享状态 |
| 典型收益 | — | CPU 密集 + 百万级元素 2~4 倍（视核数） |
| 典型翻车 | — | 小数据、难切分源、有状态操作、阻塞任务 |

> ### 💡 新人小结：并行流是什么？
>
> 把串行流想象成**一个分拣中心干活**，并行流就是**把货堆切成 N 份，N 个分拣中心同时处理，最后合并结果**：
> - 切货的人 = Spliterator（决定货好不好切）
> - 分拣中心 = ForkJoinPool 的线程（默认核数减一个）
> - 合并结果 = combiner（各中心的账拼总账）
>
> **一句话总结：并行流 = 分治框架接管你的流水线，收益与翻车都来自「切分」与「合并」。**

**学习路线图**

```
分段合并模型 → 切分器 Spliterator → 何时有效 → 五大陷阱 → 演进对比 → Q&A
机制先立起来   货好不好切          启用三前提    翻车现场清单   串行并行对比   出错怎么办
```

**本文涉及的专有名词**（先解释后使用；combiner、幺元、结合律见《Stream终端操作与归约》）：

| 术语 | 全称 | 含义（用自己的话） | 在本文中的角色 |
|------|------|--------------------|----------------|
| ForkJoinPool | Fork/Join 线程池 | 「分而治之」的线程池：大任务 fork 成小任务，结果 join 回来 | 并行流的执行引擎 |
| 公共池 | commonPool | 全 JVM 共享的 ForkJoinPool 实例 | 所有并行流的默认线程来源，被阻塞会殃及全局 |
| 工作窃取 | work-stealing | 空闲线程从忙碌线程的队列尾部「偷任务」 | ForkJoin 高效的机制保证 |
| Spliterator | splittable iterator | 可切分的迭代器：trySplit 把数据源切两半 | 决定数据源「好不好并行」 |
| 数据竞争 | data race | 多线程无同步地读写同一共享变量 | 陷阱一的根源 |

## 核心概念：分段合并模型

并行流的执行不是「多线程轮流处理同一流水线」，而是**每段独立一条完整流水线，最后合并**：

```text
串行流（垂直单道）：   元素1→工位A→工位B ⊕ 元素2→工位A→工位B ⊕ ... 逐个累积

并行流（分道合力）：
    数据源 ──Spliterator.trySplit──→ [分段1] [分段2] [分段3] [分段4]
                                          ↓        ↓       ↓       ↓
                                     各段独立执行完整流水线（中间操作逐元素垂直流动）
                                          ↓        ↓       ↓       ↓
                                     accumulator 各自累积 ──combiner──→ 合并总结果
```

**两条硬前提**（与《Stream终端操作与归约》的归约数学一脉相承）：

1. **累积算子满足结合律**——合并顺序不定，不满足则结果随合并顺序漂移；
2. **各段之间无共享可变状态**——每段的累积必须封闭在自己的容器/变量里。

好消息：`sum`/`collect(Collectors...)` 等标准操作天然满足；坏消息：你手写的 Lambda 一旦引用外部 List/计数器就当场违约（陷阱一）。

**切分质量决定收益上限**：

| 数据源 | 可切分性 | 并行友好度 |
|--------|---------|-----------|
| `ArrayList`、普通数组、`IntStream.range` | 优秀：按索引对半切，O(1) | 高 |
| `HashMap`/`HashSet` | 良好：按桶切 | 中高 |
| 平衡二叉树（`TreeMap`） | 良好 | 中 |
| `LinkedList` | 差：逐个遍历才能切 | 低 |
| `Stream.iterate`/`generate` | 差：本身逐个生成 | 低 |

## 主体内容

### 正确的启用方式与性能测量

```java
// ========== 两种启用方式（等价） ==========
long r1 = bigList.parallelStream()        // 创建即并行
        .mapToLong(Integer::longValue)
        .sum();

long r2 = bigList.stream()                // 先串行构建，中途切并行
        .filter(n -> n > 0)
        .parallel()                       // 从这里开始并行（对终端操作生效）
        .mapToLong(Integer::longValue)
        .sum();

// ========== 简易计时：先测串行基线，再测并行，用数据说话 ==========
static long time(java.util.function.Supplier<Long> task) {
    long start = System.nanoTime();
    long result = task.get();
    System.out.printf("%d ms%n", (System.nanoTime() - start) / 1_000_000);
    return result;
}
// time(() -> bigList.stream().reduce(0, Integer::sum));
// time(() -> bigList.parallelStream().reduce(0, Integer::sum));
```

**参数解释**：

- `parallel()` 是**流阶段的开关**，对之后的终端操作生效；`sequential()` 可切回串行（多次切换以最后一次为准）。
- 简易 `nanoTime` 计时适合课堂级对比；生产决策请用 JMH 类基准工具（排除 JIT 预热、GC 干扰），并多轮取均值。

**正确的并行收益案例**（CPU 密集 + 大数据 + 可切分）：

```java
// 统计 0~2000 万中质数的个数：每元素计算量大，CPU 密集，并行收益明显
long primes = IntStream.rangeClosed(2, 20_000_000)
        .parallel()                                  // 收益点：每段独立算质数
        .filter(n -> isPrime(n))
        .count();
```

### 五大陷阱清单

**陷阱一：共享可变状态（最高频事故）。**

```java
// ❌ 并行 forEach 往共享 List 塞——数据竞争（见开头事故二）
// ✅ 正解：收集交给 collect，各段独立容器 + combiner 合并
List<Integer> safe = bigList.parallelStream()
        .filter(n -> n > 0)
        .collect(Collectors.toList());   // 并行下线程安全：分段建容器，最后合并
```

**陷阱二：难切分的数据源。** `Stream.iterate` 生成的一百万元素，切分器只能一个一个摸——切分本身把收益吃光，甚至退化成串行。这类源先 `collect` 成 ArrayList 再开并行。

**陷阱三：公共池被阻塞任务占死。** 所有并行流共用一个 commonPool（默认线程数 = CPU 核数 - 1）。任何一个并行流里做 IO/远程调用/睡眠，都会让全 JVM 其他并行流的任务排队饿死：

```java
// ❌ 反模式：在并行流里调远程接口——公共池 8 个线程全部挂起等待 IO
orders.parallelStream().forEach(o -> remoteService.notify(o));   // 全局并发被限死在 7
// ✅ 正解：批量远程调用用线程池/异步框架（CompletableFuture），与并行流分工
```

**陷阱四：顺序性代价。** 并行流下 `forEach` **乱序输出**（分段完成即输出）；`findFirst` 要协调各分片按遇到顺序出结果，代价大——只求「有一个就行」用 `findAny`（呼应《Stream终端操作与归约》）。`sorted`/`distinct` 这类**有状态操作**在并行下需要跨段合并全量信息，开销远高于串行。

```java
// 并行 forEach 乱序演示
java.util.Arrays.asList("A", "B", "C", "D", "E", "F", "G", "H").parallelStream()
        .forEach(s -> System.out.print(s + " "));
// 可能输出: E A F B G C H D —— 每次不同；要顺序用 forEachOrdered（牺牲并行度）
```

**陷阱五：装箱流并行。** `Stream<Integer>` 上并行：切分开销 + 装箱开销 + 线程开销三座大山，百万级以下几乎必亏。先 `mapToInt` 特化再并行（呼应《数值流与原始类型特化》）。

> ### 💡 新人小结：五大陷阱像什么？
>
> 多分拣中心的五种翻车：
> - 共享一本总账本你记我也记 → **账目撕毁**（数据竞争）
> - 货堆根本没法对半切 → **切货比干活久**（难切分源）
> - 分拣中心全员去等一个远程电话 → **其他中心全部停摆**（公共池阻塞）
> - 硬要求「华东的件必须最先出库」→ **协同成本吃掉并行收益**（顺序性代价）
> - 每颗螺丝钉都先装小纸箱再分发 → **包装比运输贵**（装箱并行）
>
> **一句话总结：并行是把双刃剑——切得开、算得纯、合得拢才拿得起。**

### 演进对比：串行 vs 并行

统一场景：统计 2000 万以内质数个数。

**旧方案：串行流。**

```java
long primes = IntStream.rangeClosed(2, 20_000_000)
        .filter(ParallelDemo::isPrime)      // 单线程逐个判定，约数秒（视机器）
        .count();
```

**当前方案：一行切并行。**

```java
long primes = IntStream.rangeClosed(2, 20_000_000)
        .parallel()                          // 切成核数-1 段，各段独立 filter+count
        .filter(ParallelDemo::isPrime)
        .count();
```

**对比分析表**：

| 对比维度 | 旧方案：串行 | 当前方案：并行 |
|----------|-------------|---------------|
| 写法差异 | 无并行意识 | 多一个 `parallel()` 声明 |
| 行为差异（本场景） | 单核打满，耗时 T | 多核分摊，约 T/核数（理想上界），实测 2~4 倍提升 |
| 行为差异（小数据） | 稳定高效 | 切分+线程调度开销 > 收益，反而更慢 |
| 行为差异（顺序） | forEach 有序 | forEach 乱序；需顺序用 forEachOrdered 付协同代价 |
| 迁移成本 | — | 需评估数据量/可切分性/算子纯度三前提，并实测 |
| 旧方案适用场景 | 小集合、难切分源、含 IO 阻塞的流程 | CPU 密集、大数据、纯计算、无共享状态的场景 |

结论：`parallel()` 的正确心智不是「性能开关」，而是**一个需要论证的架构决策**——三前提不满足时，串行就是最优解。

## 官方 / 社区实践

```java
// ========== 1. JDK 文档的经典并行归约（无共享状态的标准姿势） ==========
double avgAge = persons.parallelStream()
        .mapToDouble(Person::getAge)
        .average()
        .orElse(0.0);

// ========== 2. 大集合分组报表（收集器并行安全） ==========
Map<String, Long> byRegion = bigOrders.parallelStream()
        .collect(Collectors.groupingBy(Order::getRegion, Collectors.counting()));

// ========== 3. 公共池线程数调优（JVM 参数，全局生效） ==========
// -Djava.util.concurrent.ForkJoinPool.common.parallelism=8
```

**参数解释**：标准收集器/归约在并行下自动分段合并，**不需要**任何额外同步代码——前提是你的 Lambda 纯净（无副作用）。公共池线程数是全局 JVM 参数，调大只解决「核多线程少」的匹配问题，救不了「任务本身阻塞」。

## 高频问题与踩坑排查（Q&A）

**Q1：`parallelStream()` 和 `stream().parallel()` 有区别吗？**

结果等价，只是书写位置不同：前者创建即并行，后者先串行搭工位、临终端前切并行。工程上更推荐后者——流水线意图清晰，并行是最后一步「决策」。

**Q2：并行流能自己指定线程池吗？**

不能直接指定。并行流写死使用 commonPool。变通做法是把流提交进自定义 ForkJoinPool 里执行（利用「fork/join 任务在提交它的池里运行」的规则）：

```java
java.util.concurrent.ForkJoinPool customPool = new java.util.concurrent.ForkJoinPool(16);
long result = customPool.submit(() ->
        bigList.parallelStream().mapToLong(Integer::longValue).sum()).get();
```

但这是官方不推荐的 hack（池生命周期、异常传播都要自己管）——真需要独立线程池的场景，直接用 CompletableFuture/线程池任务更正。

**Q3：怎么快速判断「我的并行流为什么更慢」？**

按清单排查：数据量是否上万？（小数据必亏）数据源是否 ArrayList/数组？（iterate/LinkedList 切分差）是否装箱流？（先 mapToInt）是否含 sorted/distinct 等有状态操作？（跨段合并昂贵）是否含 IO/锁等待？（公共池阻塞）五项全过关仍慢，再用 JMH 精测。

**Q4：并行流里 collect 真的线程安全吗？**

安全——标准收集器的容器是**每段一个**，最后 combiner 合并，全程无共享写。前提仍是 Lambda 无副作用：如果收集器内部引用了外部 List（如 `toCollection(() -> sharedList)`），安全承诺即刻作废。

**Q5：并行 forEach 想要顺序输出怎么办？**

换 `forEachOrdered`——它按遇到顺序输出，但要求各段协调等待，并行收益大幅缩水。先问自己：顺序对这个消费动作真的重要吗？多数「顺序执念」其实来自把打印当验证手段——换成 collect 后用结果集合验证更可靠。

**Q6：组内线程数越多并行越快吗？**

不是。计算密集型任务的收益上界是 CPU 核数；线程多于核数只增加调度与上下文切换成本。公共池默认「核数 - 1」正是这个道理。收益真正取决于「切得开 + 算得纯 + 合得拢」三件事。

**Q7：并行流里抛了异常，会怎么传播？**

任何一个分片的 Lambda 抛出 RuntimeException，**整个终端操作以该异常失败**：调用线程收到异常，其余分片的计算被放弃——没有「部分成功」的中间态，也不存在分片级的 try-catch 隔离。想在流式处理中对坏数据「跳过继续」，只能靠业务层前置兜底（filter 前先校验、map 里先规整），不能指望并行机制容错。

**Q8：嵌套并行（外层 parallelStream 里再 parallelStream）会怎样？**

内层流同样去抢公共池的线程——外层任务占着线程等内层，内层又在等空闲线程，极端时形成**线程饥饿**：所有线程都在等还没跑起来的任务。解法：内层保持串行（多数嵌套场景内层数据量小，串行更快），或按 Q2 的思路给内层配专属池隔离。

**Q9：并行流和 CompletableFuture / 线程池怎么分工？**

一句话：**并行流管「算」，线程池管「等」**。并行流适合 CPU 密集、元素间独立、单元素计算短的数据变换；凡是任务里有大段等待（调远程接口、查库、读写文件），用 CompletableFuture 或线程池编排——等待型任务塞给并行流，等于把公共池变成候车室（陷阱三）。分工速记：**瓶颈在 CPU 用并行流，瓶颈在 IO 用线程池**。

### 进阶：顺序语义与 unordered()——用顺序换潜能

有序性不是并行流的天性，而是**需要付钱维护的特性**：

```text
有序源（ArrayList 等）+ 有序终端（findFirst/forEachOrdered/sorted）
        ↓ 各分片必须按遇到顺序协调合并（协同成本随核数上升）
unordered() 声明之后：放弃顺序承诺，各分片谁来算完谁先算
        ↓ 换来：保序簿记（尤其 distinct/sorted 类的跨段合并）得以裁剪
```

```java
// unordered() 不打乱数据，只声明「我不在乎遇到顺序」——给并行优化留空间
bigList.parallelStream()
       .unordered()                     // 放弃遇到顺序
       .distinct()                      // 无序 distinct 用「见到的就保留」策略，合并更省
       .collect(Collectors.toSet());    // Set 本无序，保序本就是伪需求
```

**参数解释**：`unordered()` 是一个中间操作声明，串行流下几乎无感，并行流下裁掉「顺序协调」类开销。使用前提：**结果容器本身无序（Set/Map），或消费方不关心元素顺序**——List 输出、打印顺序敏感的场景不要用。与陷阱四联动理解：`forEachOrdered`/`findFirst` 的协同代价，本质上是在为 ORDERED 特性付费；「只要结果不要顺序」时，`unordered()` + `findAny` 是最快组合。

Spliterator 的切分行为由**特性位**（characteristics）决定。日常业务用不到自定义切分器，但这张表能解释「为什么我的源并行没收益」：

| 特性 | 含义 | 对并行的意义 |
|------|------|-------------|
| ORDERED | 源有遇到顺序 | 保序操作有依据；无序源可省协调 |
| SIZED | 知道确切元素数 | 一次对半切准，无需试探切分 |
| SUBSIZED | 切出的子切分同样 SIZED | 分治全程保持精确定长 |
| NONNULL | 保证无 null 元素 | 免去判空分支 |
| IMMUTABLE | 源不可变 | 切分无需考虑并发修改 |
| CONCURRENT | 源线程安全、可并发写 | 分片可直接共享源 |

`ArrayList`/数组同时具备 ORDERED + SIZED + SUBSIZED，是「教科书级」并行源；`LinkedList` 缺 SIZED（长度要逐个数），切分前还得先遍历——这就是陷阱二「难切分」的底层原因。

**Q10：数据源切不动，并行流会报错吗？**

不会报错，但会**悄悄退化**：`trySplit` 拆不动的源（如逐个生成的 `Stream.iterate`）整条流落在一个分片里跑，其他线程全程围观——并行开销照付，收益为零，往往比纯串行更慢。这正是陷阱二处方「先 `collect` 成 `ArrayList` 再开并行」的底层依据：先把难切的货码成标准托盘。

**Q11：公共池大小怎么定？默认「核数 - 1」要不要改？**

默认值已经贴合「计算密集 + 不与业务线程抢核」的定位，**多数应用不要动**。值得调整的只有两种情况：容器环境 CPU 限额导致自动探测失真（显式 `-D...parallelism` 指定）；核数极多的机器上跑大量小任务（适当调小减少切分开销）。调大救不了阻塞型任务——那是 Q9 的分工问题，不是池大小问题。

**一句话决策**：先问三前提（数据量、可切分、纯计算），再跑基线对比，最后才谈池参数——顺序反了，就是在错误的层面调优。

---

## 要点总结

1. **分段合并模型**：Spliterator 切源 → 各段独立走完整流水线 → combiner 合并；前提是结合律 + 无共享状态。
2. **三前提**：大数据量（万级以上）、易切分数据源（ArrayList/数组优，iterate/LinkedList 差）、纯计算无阻塞。
3. **五大陷阱**：共享可变状态、难切分源、公共池被 IO 占死、顺序性代价、装箱并行。
4. **顺序语义**：并行 forEach 乱序；findFirst 保序有代价，findAny 求快不保序；forEachOrdered 是顺序的赎金。
5. **先测后开**：`parallel()` 是架构决策不是性能开关——串行基线 → 并行实测 → 数据说话。

> ### 💡 新人小结：并行流学完了，记住这 3 点
>
> 1. **并行流是多个分拣中心，不是一个超级员工** —— 收益来自切分合力的结构，不是线程数量
> 2. **账本不能共享** —— 收集/归约交给 collect 的分段合并，外部 List 一出现就翻车
> 3. **开多中心前先称货** —— 数据量、可切分性、算子纯度三关不过，老老实实串行
>
> **一句话总结：parallel() 一行字，背后是分治框架的全套契约——读懂契约，刀刃才在正确的地方。**
